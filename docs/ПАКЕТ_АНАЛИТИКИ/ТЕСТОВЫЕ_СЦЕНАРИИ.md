# Тестовые сценарии (шаблон)

## Инструкция по заполнению

> Относится к шаблону, а не к проектному артефакту.

- **Кто заполняет:** QA совместно с аналитиком и разработчиком.
- **Источники:** приёмочный тест (поле `Scenario-id` = `AC-id`), реестр требований (`R-id`, класс важности `К1`/`К2`/`К3`), пользовательские истории (`US-id`), сценарии использования (`UC-id`); термины — [ГЛОССАРИЙ_МЕТОДОЛОГИИ.md](../../МЕТОДОЛОГИЯ/ДОКУМЕНТЫ/ГЛОССАРИЙ_МЕТОДОЛОГИИ.md).
- **Обязательные поля:** `TC-id`, привязки (`R-id`, `US-id`, `UC-id`, `AC-id`), класс важности, тип, статус жизненного цикла, предусловия, тестовые данные, шаги с ожидаемым результатом.
- **Типовые ошибки:** кейс без привязки к требованию (строка в матрице не закрывается); переписывание Gherkin словами вместо детализации до шагов; слияние двух статусов (жизненный цикл и результат прогона — разные поля); кейс в `готов` без единого прогона помечают как `пройден`.

## Назначение и область действия

Тестовые сценарии (тест-кейсы) — пошаговое описание того, как именно человек воспроизводит и проверяет поведение системы, с конкретными данными, окружением и зафиксированным результатом прогона. Доказательство ручного прогона поведения системы.

Область действия — сценарии, у которых уже есть приёмочный тест (`AC-id`): тест-кейс детализирует приёмочный тест до исполнимых шагов и не заменяет его.

Тест-кейс отвечает на вопрос **«как именно это проверить руками?»** — в отличие от приёмочного теста и реестра требований:

| Артефакт | На какой вопрос отвечает | Уровень |
|---|---|---|
| Приёмочный тест ([ПРИЁМОЧНЫЕ_ТЕСТЫ.md](ПРИЁМОЧНЫЕ_ТЕСТЫ.md), Gherkin) | «Что значит готово?» — бизнес-условие, Дано/Когда/Тогда | поведение, без навигации по интерфейсу |
| Тест-кейс (`TC-id`) | «Как именно проверить руками?» — шаги, поля, кнопки, конкретные значения | исполнимые шаги + данные + окружение |
| Реестр требований, колонки трассировки ([РЕЕСТР_ТРЕБОВАНИЙ.md](РЕЕСТР_ТРЕБОВАНИЙ.md)) | «Где цепочка R → … → проверка?» — связь, а не содержание | строка требования |

Тест-кейс **не переписывает Gherkin другими словами**. Он детализирует его до исполнимых шагов и ссылается на сценарий через `AC-id`. Бизнес-условие живёт только в Gherkin; конкретика (данные, окружение, навигация) — только в тест-кейсе.

## Соглашения

- Идентификатор кейса: `TC-001`, `TC-002`, … (`TC` — Test Case); сквозная нумерация, **не переиспользуется** после удаления кейса.
- Идентификатор сценария `AC-id` присваивается в [ПРИЁМОЧНЫЕ_ТЕСТЫ.md](ПРИЁМОЧНЫЕ_ТЕСТЫ.md) (поле `Scenario-id`): `AC-<номер R-id, который сценарий проверяет><буква сценария>`, напр. сценарии на `R-007` — `AC-007a` (позитивный), `AC-007b` (негативный). Тест-кейс ссылается на этот `AC-id`; в колонке `AC-id / TC-id` реестра требований рядом с `AC-id` дописываются `TC-id`.
- Привязки: минимум один `R-id` — иначе проверка не связывается с требованием. `US-id` и `UC-id` — источники контекста; класс важности (`К1`/`К2`/`К3`) наследуется от привязанного требования или `AC-id`.
- Тип кейса: **позитивный**/**негативный**/**граничный**.
- Статус жизненного цикла (жизнь кейса): `черновик → готов → выведен из работы`.
- Результат прогона (итог запуска): `пройден`/`провален`/`заблокирован`/`пропущен`/`не запускался`.

> Два «статуса» — это **разные поля, не сливать**. Статус жизненного цикла описывает готовность кейса; результат прогона — итог конкретного запуска. `готов` не равно `пройден`: кейс в `готов` может ещё ни разу не прогоняться (`не запускался`).

## Карточка тест-кейса

### Шапка

| Поле | Значение |
|---|---|
| **ID** | _TC-NNN_ |
| **Привязки** | _R-id, US-id, UC-id, AC-id_ |
| **Класс важности** | _К1 / К2 / К3 (наследуется от требования/AC)_ |
| **Тип** | _позитивный / негативный / граничный_ |
| **Статус (жизненный цикл)** | _черновик / готов / выведен из работы_ |
| **Автор** | _(опц.) если ведёте в git — берётся из истории, не дублировать_ |

> Поля **«Приоритет» нет**: приоритет в методологии — это класс важности `К1`/`К2`/`К3` ([КЛАССЫ_ПРИОРИТЕТА_ФУНКЦИЙ.md](../../МЕТОДОЛОГИЯ/ДОКУМЕНТЫ/05_АНКЕТЫ_И_КАТАЛОГИ/КЛАССЫ_ПРИОРИТЕТА_ФУНКЦИЙ.md)); отдельная шкала P1/P2/P3 дублировала бы его. **«Серьёзность» в шапке нет**: серьёзность относится к дефекту, а не к кейсу, и заполняется только в блоке «Прогон» при провале.

### Предусловия

Состояние системы **до** шагов, не входит в проверку (обеспечивает повторяемость и изоляцию):

1. _<напр.: продукт развёрнут на стенде, страница доступна>_
2. _<напр.: ответственный менеджер подключён к каналу уведомлений>_
3. _<напр.: в базе данных нет заявки с тестовым телефоном>_

### Тестовые данные

Конкретные значения, не «валидный телефон», а `+7 999 123-45-67`:

- _<Поле>: <значение>_
- _<Поле>: <значение>_

### Шаги

Нумерованные, атомарные, в повелительном наклонении; исполнимы человеком, не знающим функцию. Ожидаемый результат точный (не «работает», а «появляется сообщение «…»»). Для `К1` — ожидание на каждом шаге; для `К2`/`К3` достаточно итогового.

| № | Действие | Ожидаемый результат | Факт. результат | Статус |
|---|---|---|---|---|
| 1 | \_<шаг>\_ | \_<точное ожидание>\_ | \_<пусто в черновике>\_ | — |
| 2 | \_<шаг>\_ | \_<точное ожидание>\_ |  | — |

### Постусловие

_(опц.)_ Состояние системы **после**; нужно, если кейс меняет данные (очистка).

### Прогон

_Пусто в черновике; заполняется при исполнении._

| Поле | Значение |
|---|---|
| Результат прогона | _пройден / провален / заблокирован / пропущен / не запускался_ |
| Фактический результат | _что наблюдали (обязателен при провале/блокировке)_ |
| Серьёзность (только при провале) | _блокер / серьёзный / незначительный_ |
| Окружение / конфигурация | _стенд, браузер+версия, ОС, версия сборки_ |
| Исполнитель прогона | \_<логин>\_ |
| Дата | _ДД.ММ.ГГГГ_ |
| Дефект | _(опц.) ссылка на запись о дефекте при провале_ |

## Пример заполнения

Согласован с [ПРИЁМОЧНЫЕ_ТЕСТЫ.md](ПРИЁМОЧНЫЕ_ТЕСТЫ.md): те же `R-007, R-008 / US-003 / UC-001 / К1`. Сценариям присвоены `AC-007a` (позитивный) и `AC-007b` (негативный) — по схеме «AC-<R-id>».

### TC-014 — Создание заявки с минимальным обязательным набором полей

| Поле | Значение |
|---|---|
| **ID** | TC-014 |
| **Привязки** | R-007, R-008, US-003, UC-001, AC-007a |
| **Класс важности** | К1 |
| **Тип** | позитивный |
| **Статус (жизненный цикл)** | готов |

### Предусловия

1. Продукт развёрнут на стенде, страница «Оставить заявку» доступна.
2. Ответственный менеджер подключён к каналу уведомлений.
3. В базе данных нет заявки с телефоном из тестовых данных.

### Тестовые данные

(заполнены только обязательные поля формы; необязательное «Комментарий» намеренно пропущено — это и делает набор минимальным)

- Имя:        Анна
- Телефон:    +7 999 123-45-67
- Тип услуги: Консультация
- Комментарий: (не заполняется)

### Шаги

(ожидание на каждом шаге, т.к. `К1`)

| № | Действие | Ожидаемый результат | Факт. результат | Статус |
|---|---|---|---|---|
| 1 | Открыть страницу «Оставить заявку» | Форма заявки видна; поля Имя/Телефон/Тип услуги пустые; «Комментарий» — необязательное | форма отобразилась, 3 обязательных поля пустые | пройден |
| 2 | Ввести Имя и Телефон, выбрать Тип услуги (тестовые данные), «Комментарий» оставить пустым | Значения приняты, подсветки ошибок нет | значения приняты, ошибок нет | пройден |
| 3 | Нажать «Отправить» | Появляется сообщение «Заявка принята, мы свяжемся в течение 24 часов» | сообщение появилось дословно | пройден |
| 4 | Открыть базу данных, найти заявку по телефону | Создана заявка: телефон совпал, статус «новая», комментарий пуст | заявка №1042, статус «новая», телефон совпал | пройден |
| 5 | Проверить канал уведомлений менеджера | Пришло уведомление о новой заявке с именем и телефоном | уведомление пришло за ~3 сек | пройден |

**Постусловие:** в базе данных остаётся 1 заявка со статусом «новая» (удалить при очистке).

### TC-015 — Блокировка отправки при невалидном телефоне (негативный)

| Поле | Значение |
|---|---|
| **ID** | TC-015 |
| **Привязки** | R-007, R-008, US-003, UC-001, AC-007b |
| **Класс важности** | К1 |
| **Тип** | негативный |
| **Статус (жизненный цикл)** | готов |

**Предусловия:** страница доступна; в базе данных нет заявки с тестовым телефоном.

### Тестовые данные

- Имя:        Анна
- Телефон:    123  (невалидный — меньше 10 цифр)
- Тип услуги: Консультация

### Шаги

| № | Действие | Ожидаемый результат | Факт. результат | Статус |
|---|---|---|---|---|
| 1 | Открыть страницу | Форма отображается | — | — |
| 2 | Ввести Имя и телефон `123` | При уходе с поля «Телефон» поле подсвечивается как ошибочное | — | — |
| 3 | Нажать «Отправить» | Кнопка не отправляет форму; под полем «Телефон» текст «Введите корректный номер» | — | — |
| 4 | Проверить базу данных | Запись заявки не создана | — | — |

**Прогон:** результат `не запускался` (жизненный цикл = `готов`, ещё не прогонялся).

### TC-016 — Граничная длина номера: 10 цифр (граничный)

```text
Привязки:        R-007, US-003, UC-001, AC-007a
Класс важности:  К1, Тип: граничный, Статус (жизненный цикл): черновик
Тестовые данные: телефон 9991234567 (ровно 10 цифр — нижняя граница валидной длины)
Ожидаемый итог:  телефон принят как валидный, заявка создаётся со статусом «новая»
```

> Привязка к `AC-007a` (а не `AC-007b`): исход граничного теста — «заявка создана», то есть это положительная граница того же правила валидации, что и позитивный сценарий.

**Связь в реестре требований** ([РЕЕСТР_ТРЕБОВАНИЙ.md](РЕЕСТР_ТРЕБОВАНИЙ.md), строка требования `R-007`, колонка `AC-id`/`TC-id`):

```text
AC-007a; TC-014, TC-016, AC-007b; TC-015
```
