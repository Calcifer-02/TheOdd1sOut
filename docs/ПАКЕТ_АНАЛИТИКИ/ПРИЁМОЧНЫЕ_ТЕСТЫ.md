# Приёмочные тесты

## Паспорт артефакта

| Версия | Дата | Автор | Обоснование |
|---|---:|---|---|
| 1.0 | 22.09.2026 | Александр Прокошев | первичное заполнение: критерии приёмки служебных точек и области «справочники» перед реализацией серверной части |

## Назначение и область действия

Приёмочные тесты — формализованные критерии приёмки требования в виде исполняемых (или квази-исполняемых) сценариев. Каждый тест проверяет конкретное требование и даёт бинарный ответ «выполняется / не выполняется» — это метрика приёмки функциональности.

## Соглашения

- Формат: Gherkin (`Given`/`When`/`Then`) или его русская версия (Дано / Когда / Тогда).
- Идентификатор сценария (`AC-id`): `AC-<номер проверяемого требования R-id><буква>`, напр. для `R-007` — `AC-007a`, `AC-007b`. Единая точка склейки с матрицей трассируемости и тестовыми сценариями.
- Привязка обязательна: каждый сценарий связан с требованием (`R-id`), пользовательской историей (`US-id`) и сценарием использования (`UC-id`).
- Класс важности (`К1`/`К2`/`К3`) указывается в шапке `Feature`.
- Шаг `Then` формулируется проверяемо: наблюдаемый факт или состояние, а не описание реализации.

## Структура приёмочного теста

```gherkin
Feature: <название функциональности, ссылка на R-id из реестра>
  Контекст: <короткое описание для команды>

  # Связи
  # R-id: R-001, R-002
  # US-id: US-007
  # UC-id: UC-002
  # Класс важности: К1

  # Scenario-id: AC-001a
  Scenario: <название сценария>
    Given <предусловие>
    And   <дополнительное предусловие>
    When  <действие пользователя или системы>
    And   <дополнительное действие>
    Then  <ожидаемый результат>
    And   <дополнительный ожидаемый результат>
```

## Пример (форма заявки)

> Заголовок раздела взят из схемы вида `АА-12` и не описывает содержимое:
> ниже не пример, а действующие критерии приёмки проекта. Отдельного раздела
> под них вид не объявляет — единственный содержательный слот называется
> «Примером», и раздел с другим именем отклоняется проверкой состава
> (`DOC-C08`). Имя сохранено, чтобы проверка работала; несоответствие имени
> содержимому — дефект эталона, и он назван здесь, а не обойдён молча.

Заполняется по срезам реализации: критерий заводится раньше кода, который его
закрывает. Здесь — служебные точки и область «справочники»; расчёт, сделка,
доступ и ведение справочников получают свои критерии вместе со своими срезами.

Три соглашения этого раздела:

- **Пользовательские истории (`US-id`) не заведены** — документ
  [ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md](ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md) остаётся шаблоном.
  Поле не заполняется выдуманным значением: разрыв виден, а не замаскирован.
- **Проверки автоматические.** Ручные карточки тест-кейсов
  ([ТЕСТОВЫЕ_СЦЕНАРИИ.md](ТЕСТОВЫЕ_СЦЕНАРИИ.md)) не заводятся, пока нет ручного
  прогона: критерий связывается с кодом проверки якорем `@ac` по стандарту
  трассируемости, и это и есть воспроизводимое подтверждение.
- **Данные сквозные.** Везде, где нужен пример, берётся канонический набор
  договора: адрес «г Москва, ул Годовикова, д 9», группы `beton-lom` и
  `drevesina`, полигоны `vostok-timohovo` и `iksha`, дата актуальности
  17.09.2026.

### Служебные точки

```gherkin
Feature: Живость и готовность расчётной части (R-011)
  Контекст: внешний узел и оркестратор решают по этим точкам, отдавать ли
  службе трафик. Живость не должна зависеть от базы данных, иначе перезапуск
  базы выглядит как отказ службы.

  # Связи
  # R-id: R-011
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-011a
  Scenario: живость не зависит от базы данных
    Given расчётная часть запущена
    And   база данных остановлена
    When  выполняется GET /health
    Then  ответ имеет код 200
    And   тело содержит status «ok»

  # Scenario-id: AC-011b
  Scenario: готовность отличает доступную базу от недоступной
    Given расчётная часть запущена и видит базу данных
    When  выполняется GET /ready
    Then  ответ имеет код 200
    And   тело содержит status «ready» и database «reachable»

  # Scenario-id: AC-011c
  Scenario: готовность отказывает при недоступной базе
    Given расчётная часть запущена
    And   строка подключения к базе данных не задана
    When  выполняется GET /ready
    Then  ответ имеет код 503
    And   тело содержит status «not_ready» и причину отказа
```

### Адрес вывоза и подсказки

```gherkin
Feature: Адрес вывоза выбирается из подсказок и ограничен зоной обслуживания (R-012)
  Контекст: расчёт опирается на координаты, а не на набранную строку. Адрес
  без координат или вне Москвы и области считать нечем.

  # Связи
  # R-id: R-012, R-055
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-012a
  Scenario: подсказка несёт координаты и зону обслуживания
    Given справочник адресов содержит «г Москва, ул Годовикова, д 9»
    When  выполняется GET /v1/address-suggestions с запросом «Годовикова»
    Then  ответ имеет код 200
    And   каждая подсказка несёт широту, долготу и зону обслуживания
    And   зона обслуживания принимает значение «moscow» либо «moscowRegion»

  # Scenario-id: AC-012b
  Scenario: адрес вне зоны обслуживания в подсказках не появляется
    Given справочник адресов содержит адрес в Твери
    When  выполняется GET /v1/address-suggestions с запросом «Тверь»
    Then  ответ имеет код 200
    And   список подсказок пуст

  # Scenario-id: AC-012c
  Scenario: слишком короткий запрос отклоняется
    When  выполняется GET /v1/address-suggestions с запросом «Го»
    Then  ответ имеет код 400
    And   тип содержимого ответа — application/problem+json
    And   поле type равно «urn:imolt:problem:validation»

  # Scenario-id: AC-055a
  Scenario: недоступность внешней службы подсказок не выглядит как успех
    Given внешняя служба подсказок объявлена источником и не отвечает
    When  выполняется GET /v1/address-suggestions с запросом «Годовикова»
    Then  ответ имеет код 503
    And   поле type равно «urn:imolt:problem:distance-service-unavailable»
    And   ответ содержит заголовок Retry-After
```

### Справочник групп отходов

```gherkin
Feature: Справочник групп отходов с поиском по названию и коду каталога (R-013, R-039)
  Контекст: пользователь выбирает тип отходов из справочника проекта, а не
  вводит его словами. Цена перевозки и коэффициент плотности — свойства
  группы, и второго места их хранения нет.

  # Связи
  # R-id: R-013, R-039, R-060
  # US-id: не заведены
  # UC-id: UC-001, UC-005
  # Класс важности: К1

  # Scenario-id: AC-039a
  Scenario: карточка группы несёт все объявленные свойства
    Given справочник содержит группу «beton-lom»
    When  выполняется GET /v1/waste-groups/beton-lom
    Then  ответ имеет код 200
    And   тело содержит название, перечень кодов каталога ФККО,
          цену перевозки за тонна-километр, коэффициент плотности
          и дату актуальности
    And   цена перевозки передана строкой с двумя знаками после точки

  # Scenario-id: AC-039b
  Scenario: несуществующая группа даёт отказ, а не пустую карточку
    When  выполняется GET /v1/waste-groups/net-takoy-gruppy
    Then  ответ имеет код 404
    And   тип содержимого ответа — application/problem+json
    And   поле type равно «urn:imolt:problem:not-found»

  # Scenario-id: AC-013a
  Scenario: поиск по части названия
    Given справочник содержит группы «beton-lom» и «drevesina»
    When  выполняется GET /v1/waste-groups с запросом «бетон»
    Then  ответ имеет код 200
    And   список содержит «beton-lom»
    And   список не содержит «drevesina»

  # Scenario-id: AC-013b
  Scenario: поиск по коду каталога ФККО
    Given у группы «beton-lom» объявлен код «8 22 201 01 21 5»
    When  выполняется GET /v1/waste-groups с запросом «8 22 201»
    Then  ответ имеет код 200
    And   список содержит «beton-lom»

  # Scenario-id: AC-060a
  Scenario: страница по умолчанию ограничена десятью записями
    Given справочник содержит более десяти групп
    When  выполняется GET /v1/waste-groups без параметров страницы
    Then  ответ имеет код 200
    And   в списке ровно десять записей
    And   поле total больше десяти

  # Scenario-id: AC-060b
  Scenario: запрос страницы больше предела отклоняется
    When  выполняется GET /v1/waste-groups с limit 101
    Then  ответ имеет код 400
    And   поле type равно «urn:imolt:problem:validation»
```

### Реестр полигонов

```gherkin
Feature: Реестр полигонов с тарифами, статусом и историей юрлица (R-040, R-041)
  Контекст: полигон — точка приёма с тарифом по каждой принимаемой группе.
  Статус и дата актуальности показывают, можно ли везти сегодня; смена юрлица
  не должна обнулять накопленные тарифы.

  # Связи
  # R-id: R-040, R-041, R-048
  # US-id: не заведены
  # UC-id: UC-005, UC-006
  # Класс важности: К1

  # Scenario-id: AC-040a
  Scenario: карточка полигона несёт все объявленные свойства
    Given реестр содержит полигон «vostok-timohovo»
    When  выполняется GET /v1/landfills/vostok-timohovo
    Then  ответ имеет код 200
    And   тело содержит наименование, адрес, координаты, статус,
          дату актуальности статуса и перечень тарифов по группам
    And   у каждого тарифа указаны группа отходов, цена за тонну и дата

  # Scenario-id: AC-040b
  Scenario: реестр отбирается по принимаемой группе отходов
    Given полигон «vostok-timohovo» принимает «beton-lom»
    And   полигон «iksha» не принимает «drevesina»
    When  выполняется GET /v1/landfills с отбором по группе «drevesina»
    Then  ответ имеет код 200
    And   список не содержит «iksha»

  # Scenario-id: AC-040c
  Scenario: реестр отбирается по статусу
    Given полигон «iksha» заблокирован
    When  выполняется GET /v1/landfills с отбором по статусу «active»
    Then  ответ имеет код 200
    And   список не содержит «iksha»

  # Scenario-id: AC-041a
  Scenario: смена юрлица сохраняется историей и не теряет тарифы
    Given у полигона «vostok-timohovo» юрлицо менялось 01.03.2026
    When  выполняется GET /v1/landfills/vostok-timohovo
    Then  ответ имеет код 200
    And   тело содержит историю юрлиц с датами начала и окончания
    And   перечень тарифов остаётся непустым
```

### Отзывы о полигонах

```gherkin
Feature: Оценки полигонов как обратная связь по актуальности данных (R-031)
  Контекст: оценка относится к достоверности сведений о полигоне, а не к
  качеству услуги. Средняя оценка без отзывов не равна нулю — её просто нет.

  # Связи
  # R-id: R-031
  # US-id: не заведены
  # UC-id: UC-006
  # Класс важности: К2

  # Scenario-id: AC-031a
  Scenario: список отзывов несёт среднюю оценку
    Given у полигона «vostok-timohovo» есть отзывы с оценками 4 и 5
    When  выполняется GET /v1/landfills/vostok-timohovo/reviews
    Then  ответ имеет код 200
    And   средняя оценка равна 4.5

  # Scenario-id: AC-031b
  Scenario: у полигона без отзывов средняя оценка пуста
    Given у полигона «iksha» отзывов нет
    When  выполняется GET /v1/landfills/iksha/reviews
    Then  ответ имеет код 200
    And   список отзывов пуст
    And   средняя оценка пуста, а не равна нулю
```

### Актуальность данных

```gherkin
Feature: Дата актуальности цен и статусов видна до расчёта (R-048)
  Контекст: ценность сервиса — свежесть данных. Пользователь должен видеть,
  на какой день посчитан результат, не догадываясь об этом.

  # Связи
  # R-id: R-048, R-007
  # US-id: не заведены
  # UC-id: UC-006
  # Класс важности: К1

  # Scenario-id: AC-048a
  Scenario: сводка актуальности отдаёт обе даты
    Given цены обновлены 17.09.2026, статусы обновлены 17.09.2026
    When  выполняется GET /v1/data-freshness
    Then  ответ имеет код 200
    And   тело содержит дату актуальности цен и дату актуальности статусов

  # Scenario-id: AC-048b
  Scenario: каждый полигон несёт дату актуальности своего статуса
    When  выполняется GET /v1/landfills
    Then  ответ имеет код 200
    And   у каждой записи заполнена дата актуальности статуса
```

### Ключи внешних служб

```gherkin
Feature: Ключи внешних служб не покидают сервер (R-056)
  Контекст: ключ, ушедший в браузер, становится общедоступным — риск AR-006.
  Обращения к внешним службам идут только через расчётную часть.

  # Связи
  # R-id: R-056
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-056a
  Scenario: ответ подсказок не содержит ключа внешней службы
    Given ключ внешней службы задан переменной окружения
    When  выполняется GET /v1/address-suggestions с запросом «Годовикова»
    Then  ответ имеет код 200
    And   тело ответа не содержит значения этого ключа
    And   заголовки ответа не содержат значения этого ключа

  # Scenario-id: AC-056b
  Scenario: договор не объявляет ни одного параметра с ключом внешней службы
    When  разбирается файл договора src/back/Imolt.Api/contracts/openapi.yaml
    Then  ни один параметр запроса не называется ключом, токеном или подписью
          внешней службы
```
