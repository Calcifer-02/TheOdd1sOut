# Приёмочные тесты (шаблон)

## Инструкция по заполнению

> Относится к шаблону, а не к проектному артефакту.

- **Кто заполняет:** QA совместно с аналитиком; классы важности и состав критериев подтверждает заказчик.
- **Источники:** пользовательские истории ([ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md](ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md), секция «критерии приёмки»), сценарии использования ([СЦЕНАРИИ_ИСПОЛЬЗОВАНИЯ.md](СЦЕНАРИИ_ИСПОЛЬЗОВАНИЯ.md), основной и альтернативные потоки); терминология — [ГЛОССАРИЙ_МЕТОДОЛОГИИ.md](../../МЕТОДОЛОГИЯ/ДОКУМЕНТЫ/ГЛОССАРИЙ_МЕТОДОЛОГИИ.md).
- **Обязательные поля:** `Feature` со ссылкой на `R-id`, `Scenario-id` (`AC-id`), привязка `R-id`/`US-id`/`UC-id`, класс важности, проверяемый шаг `Then`.
- **Типовые ошибки:** сценарий без привязки к `R-id`; требование класса `К1` без приёмочного теста; `AC-id`, расходящийся с матрицей трассируемости; `Then`, который нельзя проверить наблюдаемо.

## Назначение и область действия

Приёмочные тесты — формализованные критерии приёмки требования в виде исполняемых (или квази-исполняемых) сценариев. Каждый тест проверяет конкретное требование и даёт бинарный ответ «выполняется / не выполняется» — это метрика приёмки функциональности.

## Соглашения

- Формат: Gherkin (`Given`/`When`/`Then`) или его русская версия (Дано / Когда / Тогда).
- Идентификатор сценария (`AC-id`): `AC-<номер проверяемого требования R-id><буква>`, напр. для `R-007` — `AC-007a`, `AC-007b`. Единая точка склейки с матрицей трассируемости и тестовыми сценариями.
- Привязка обязательна: каждый сценарий связан с требованием (`R-id`), пользовательской историей (`US-id`) и сценарием использования (`UC-id`).
- Класс важности (`К1`/`К2`/`К3`) указывается в шапке `Feature`.
- Шаг `Then` формулируется проверяемо: наблюдаемый факт или состояние, а не описание реализации.

## Структура приёмочного теста

```gherkin
Feature: <название функциональности, ссылка на R-id из реестра>
  Контекст: <короткое описание для команды>

  # Связи
  # R-id: R-001, R-002
  # US-id: US-007
  # UC-id: UC-002
  # Класс важности: К1

  # Scenario-id: AC-001a
  Scenario: <название сценария>
    Given <предусловие>
    And   <дополнительное предусловие>
    When  <действие пользователя или системы>
    And   <дополнительное действие>
    Then  <ожидаемый результат>
    And   <дополнительный ожидаемый результат>
```

## Пример (форма заявки)

```gherkin
Feature: Создание заявки со страницы продукта
  Контекст: посетитель оставляет заявку на услугу через форму на сайте.

  # R-id: R-007, R-008
  # US-id: US-003
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-007a
  Scenario: успешное создание заявки с минимальными данными
    Given открыта страница «Оставить заявку»
    When  пользователь заполняет имя, телефон и тип услуги
    And   нажимает «Отправить»
    Then  появляется сообщение «Заявка принята, мы свяжемся в течение 24 часов»
    And   в базе данных создаётся запись заявки со статусом «новая»
    And   ответственному менеджеру уходит уведомление

  # Scenario-id: AC-007b
  Scenario: блокировка отправки при невалидном телефоне
    Given открыта страница «Оставить заявку»
    When  пользователь вводит телефон «123»
    And   нажимает «Отправить»
    Then  поле «Телефон» подсвечивается как ошибочное
    And   появляется сообщение «Введите корректный номер»
    And   запись в базе данных не создаётся
```
