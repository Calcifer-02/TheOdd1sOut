## Назначение и область действия

Приёмочные тесты — формализованные критерии приёмки требования в виде исполняемых (или квази-исполняемых) сценариев. Каждый тест проверяет конкретное требование и даёт бинарный ответ «выполняется / не выполняется» — это метрика приёмки функциональности.

## Соглашения

- Формат: Gherkin (`Given`/`When`/`Then`) или его русская версия (Дано / Когда / Тогда).
- Идентификатор сценария (`AC-id`): `AC-<номер проверяемого требования R-id><буква>`, напр. для `R-007` — `AC-007a`, `AC-007b`. Единая точка склейки с матрицей трассируемости и тестовыми сценариями.
- Привязка обязательна: каждый сценарий связан с требованием (`R-id`), пользовательской историей (`US-id`) и сценарием использования (`UC-id`).
- Класс важности (`К1`/`К2`/`К3`) указывается в шапке `Feature`.
- Шаг `Then` формулируется проверяемо: наблюдаемый факт или состояние, а не описание реализации.

## Структура приёмочного теста

```gherkin
Feature: <название функциональности, ссылка на R-id из реестра>
  Контекст: <короткое описание для команды>

  # Связи
  # R-id: R-001, R-002
  # US-id: US-007
  # UC-id: UC-002
  # Класс важности: К1

  # Scenario-id: AC-001a
  Scenario: <название сценария>
    Given <предусловие>
    And   <дополнительное предусловие>
    When  <действие пользователя или системы>
    And   <дополнительное действие>
    Then  <ожидаемый результат>
    And   <дополнительный ожидаемый результат>
```

## Пример (форма заявки)

> Заголовок раздела взят из схемы вида `АА-12` и не описывает содержимое:
> ниже не пример, а действующие критерии приёмки проекта. Отдельного раздела
> под них вид не объявляет — единственный содержательный слот называется
> «Примером», и раздел с другим именем отклоняется проверкой состава
> (`DOC-C08`). Имя сохранено, чтобы проверка работала; несоответствие имени
> содержимому — дефект эталона, и он назван здесь, а не обойдён молча.

Заполняется по срезам реализации: критерий заводится раньше кода, который его
закрывает. Здесь — служебные точки, область «справочники» и область «расчёт»;
сделка, доступ и ведение справочников получают свои критерии вместе со своими
срезами.

Три соглашения этого раздела:

- **Пользовательские истории (`US-id`) не заведены** — документ
  [ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md](ПОЛЬЗОВАТЕЛЬСКИЕ_ИСТОРИИ.md) остаётся шаблоном.
  Поле не заполняется выдуманным значением: разрыв виден, а не замаскирован.
- **Проверки автоматические.** Ручные карточки тест-кейсов
  ([ТЕСТОВЫЕ_СЦЕНАРИИ.md](ТЕСТОВЫЕ_СЦЕНАРИИ.md)) не заводятся, пока нет ручного
  прогона: критерий связывается с кодом проверки якорем `@ac` по стандарту
  трассируемости, и это и есть воспроизводимое подтверждение.
- **Данные сквозные.** Везде, где нужен пример, берётся канонический набор
  договора: адрес «г Москва, ул Годовикова, д 9», группы `beton-lom` и
  `drevesina`, полигоны `vostok-timohovo` и `iksha`, дата актуальности
  17.09.2026.

### Служебные точки

```gherkin
Feature: Живость и готовность расчётной части (R-067)
  Контекст: внешний узел и оркестратор решают по этим точкам, отдавать ли
  службе трафик. Живость не должна зависеть от базы данных, иначе перезапуск
  базы выглядит как отказ службы.

  # Связи
  # R-id: R-067, R-068
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-067a
  Scenario: живость не зависит от базы данных
    Given расчётная часть запущена
    And   база данных остановлена
    When  выполняется GET /health
    Then  ответ имеет код 200
    And   тело содержит status «ok»

  # Scenario-id: AC-068a
  Scenario: готовность отличает доступную базу от недоступной
    Given расчётная часть запущена и видит базу данных
    When  выполняется GET /ready
    Then  ответ имеет код 200
    And   тело содержит status «ready» и database «reachable»

  # Scenario-id: AC-068b
  Scenario: готовность отказывает при недоступной базе
    Given расчётная часть запущена
    And   строка подключения к базе данных не задана
    When  выполняется GET /ready
    Then  ответ имеет код 503
    And   тело содержит status «not_ready» и причину отказа
```

### Отдача договора и документ об отказе

```gherkin
Feature: Служба отдаёт договор и отвечает об отказе объявленной формой (R-011)
  Контекст: договор — источник, по которому клиент пишет код; ответ службы
  обязан быть тем же файлом, что лежит в репозитории. Необработанный отказ
  службы не имеет кода причины, но обязан прийти в той же форме RFC 9457,
  что и отказы объявленные: иначе разбор ошибки рассыпается именно тогда,
  когда к нему прибегают.

  # Связи
  # R-id: R-011, R-002
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-011d
  Scenario: служба отдаёт договор из репозитория без изменений
    Given расчётная часть запущена
    When  выполняется GET /v1/openapi.yaml
    Then  ответ имеет код 200 и медиатип application/yaml
    And   тело ответа совпадает с файлом договора репозитория байт в байт
    And   образец денежной суммы в отдаваемом договоре совпадает с образцом,
          который служба принимает при разборе
    And   страница просмотра GET /swagger читает договор этой же службы

  # Scenario-id: AC-011e
  Scenario: необработанная поломка отвечает документом RFC 9457
    Given расчётная часть запущена с негодной строкой подключения к базе данных
    When  выполняется GET /ready
    Then  ответ имеет код 500
    And   тип содержимого ответа — application/problem+json
    And   поле type равно «about:blank», поле status равно 500
    And   документ совпадает со схемой Problem договора
```

### Адрес вывоза и подсказки

```gherkin
Feature: Адрес вывоза выбирается из подсказок и ограничен зоной обслуживания (R-012)
  Контекст: расчёт опирается на координаты, а не на набранную строку. Адрес
  без координат или вне Москвы и области считать нечем.

  # Связи
  # R-id: R-012, R-055
  # US-id: не заведены
  # UC-id: UC-001
  # Класс важности: К1

  # Scenario-id: AC-012a
  Scenario: подсказка несёт координаты и зону обслуживания
    Given справочник адресов содержит «г Москва, ул Годовикова, д 9»
    When  выполняется GET /v1/address-suggestions с запросом «Годовикова»
    Then  ответ имеет код 200
    And   каждая подсказка несёт широту, долготу и зону обслуживания
    And   зона обслуживания принимает значение «moscow» либо «moscowRegion»

  # Scenario-id: AC-012b
  Scenario: адрес вне зоны обслуживания в подсказках не появляется
    Given справочник адресов содержит адрес в Твери
    When  выполняется GET /v1/address-suggestions с запросом «Тверь»
    Then  ответ имеет код 200
    And   список подсказок пуст

  # Scenario-id: AC-012c
  Scenario: слишком короткий запрос отклоняется
    When  выполняется GET /v1/address-suggestions с запросом «Го»
    Then  ответ имеет код 400
    And   тип содержимого ответа — application/problem+json
    And   поле type равно «urn:imolt:problem:validation»

  # Scenario-id: AC-055a
  Scenario: недоступность внешней службы подсказок не выглядит как успех
    Given внешняя служба подсказок объявлена источником и не отвечает
    When  выполняется GET /v1/address-suggestions с запросом «Годовикова»
    Then  ответ имеет код 503
    And   поле type равно «urn:imolt:problem:distance-service-unavailable»
    And   ответ содержит заголовок Retry-After
```

```gherkin
Feature: Порядок списка справочника полигонов (R-088)
  Контекст: на экране расчёта полигоны упорядочиваются по итогу, перевозке,
  утилизации и расстоянию, а в справочнике и в редакторе цен порядок был один
  и незаявленный — по идентификатору записи. Сравнить полигоны по цене

  упорядоченный на клиенте, переставил бы только показанную страницу.

  # R-id: R-088
  # US-id: не заведены
  # UC-id: UC-009
  # Класс важности: К2
```
