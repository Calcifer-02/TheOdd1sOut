> Относится к шаблону и не входит в проектный артефакт.

- **Кто заполняет:** аналитик формулирует истории совместно с заказчиком; ведущий сверяет соответствие охвату и размер истории; QA проверяет возможность связать историю с критериями приёмки.
- **Источники:** матрица стейкхолдеров, видение и границы, глоссарий проекта, требования уровня `L2` из реестра требований, открытые вопросы, беседы с заказчиком и протоколы решений.
- **Форма проектного артефакта:** набор однотипных карточек. Каждая карточка является единственным источником истины по одной пользовательской истории (`US-id`). Параллельная сводная таблица пользовательских историй не ведётся.
- **Обязательные поля:** `US-id`, связанный `R-id` уровня `L2`, роль, потребность («хочу»), ценность («чтобы»), класс важности из реестра требований, подтверждение ценности, связанные `UC-id`, `AC-id` и `Q-id`.
- **Канон идентификаторов:** используются только `US-id`, `R-id`, `UC-id`, `Q-id` и `AC-id`, закреплённые в [ГЛОССАРИЙ_МЕТОДОЛОГИИ.md](../../МЕТОДОЛОГИЯ/ДОКУМЕНТЫ/ГЛОССАРИЙ_МЕТОДОЛОГИИ.md).
- **Правила заполнения:**
  - одна пользовательская история описывает одну потребность одной действующей роли и связывается с одним требованием уровня `L2`;
  - одна карточка содержит одну пользовательскую историю с уникальным `US-id`;
  - карточка не дублируется в отдельном реестре или сводной таблице;
  - одно требование `L2` может иметь несколько историй, если потребность или ценность различаются для разных ролей;
  - роль должна быть представлена в матрице стейкхолдеров либо связана с `Q-id`, если её статус ещё не определён;
  - «хочу» описывает наблюдаемую возможность для пользователя, а не техническую реализацию, экран, таблицу, API или компонент;
  - «чтобы» описывает самостоятельную ценность или результат и не повторяет часть «хочу»;
  - класс важности берётся из связанного `R-id` и не изменяется локально в пользовательской истории;
  - пользовательская история не имеет отдельного статуса: актуальное состояние определяется по связанному требованию в реестре требований;
  - многошаговый поток, альтернативы и исключения описываются в сценарии использования через `UC-id`;
  - критерии приёмки в формате «Дано / Когда / Тогда» ведутся в приёмочных тестах через `AC-id` и не дублируются внутри истории;
  - неясность по роли, потребности, ценности, охвату или проверяемому исходу связывается с `Q-id`;
  - при изменении истории соответствующие связи `R-id ↔ US-id ↔ UC-id ↔ AC-id` синхронизируются в реестре требований.
- **Что проверить перед контрольной точкой:** каждый `US-id` уникален; каждая история имеет `R-id` уровня `L2`; роль присутствует в матрице стейкхолдеров; формулировка содержит отдельные «хочу» и «чтобы»; класс важности совпадает с реестром требований; многошаговые истории имеют `UC-id`; истории текущего охвата имеют `AC-id` либо связанный `Q-id` с причиной отсутствия проверки.
- **Типовые ошибки:** история без `R-id`; собственный статус истории; класс важности, расходящийся с реестром требований; технический компонент вместо пользовательской роли; реализация вместо потребности; одинаковые «хочу» и «чтобы»; Gherkin-критерии, продублированные из приёмочных тестов; многошаговый поток без `UC-id`; изменение связи без обновления реестра требований.
