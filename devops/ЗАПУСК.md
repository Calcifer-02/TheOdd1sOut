# Запуск решения локально

## Паспорт артефакта

| Версия | Дата | Автор | Обоснование |
|---|---:|---|---|
| 1.0 | 18.09.2026 | Александр Прокошев | Плацдарм развёртывания: состав служб, одна команда запуска, переменные и порядок проверки по условиям трека (разд. 6.1) |

## Что это за состояние

В репозитории собран **плацдарм**, а не продукт: службы поднимаются, видят друг
друга и отвечают на запросы проверки работоспособности. Предметной логики расчёта,
сценариев чат-бота и экранов мини-приложения здесь ещё нет — они добавляются внутрь
уже готовых служб, не меняя порядка запуска.

## Состав

| Служба | Что это | Образ или сборка | Порт внутри | Порт снаружи |
|---|---|---|---:|---|
| `db` | PostgreSQL, хранилище справочников и расчётов | `postgres:17-alpine` | 5432 | `POSTGRES_PORT` |
| `api` | Расчётная часть: справочники, расчёт, коммерческое предложение | `src/back/Imolt.Api/Dockerfile` | 8080 | `API_PORT` |
| `bot` | Чат-бот MAX: приём обновлений платформы | `src/back/Imolt.Bot/Dockerfile` | 8080 | `BOT_PORT` |
| `miniapp` | Мини-приложение MAX: статика и проксирование на `api` | `src/front/miniapp/Dockerfile` | 80 | `MINIAPP_PORT` |

Связи: `miniapp → api` по внутренней сети (`/api/…` проксирует nginx), `api → db`
по строке подключения, `bot → api` по адресу `API_BASE_URL`. Наружу отдаются
все четыре порта — для проверки каждой службы по отдельности.

## Запуск одной командой

```sh
cp .env.example .env    # один раз: подставьте пароль базы и токен чат-бота
docker compose up --build
```

Проверить без интерактивного вывода и дождаться готовности:

```sh
docker compose up --build --detach --wait
```

## Остановка и повторный запуск

```sh
docker compose stop            # остановить, данные и тома сохранить
docker compose start           # поднять снова
docker compose down            # снести контейнеры и сеть, тома оставить
docker compose down --volumes  # снести вместе с данными базы
```

Повторный запуск после `down` — та же команда `docker compose up --build`.

## Переменные окружения

Полный перечень с пояснениями — в [`.env.example`](../.env.example). Коротко:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `API_PORT`, `BOT_PORT`, `MINIAPP_PORT`, `POSTGRES_PORT` | Порты на машине разработчика | 18080, 18081, 15173, 15432 |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Учётные данные базы | `imolt`, `imolt`, заглушка |
| `MAX_BOT_TOKEN` | Токен чат-бота MAX, выдают организаторы | пусто |
| `MAX_API_BASE_URL`, `MINIAPP_PUBLIC_URL` | Адреса платформы и публичный адрес мини-приложения | пусто |

Порты по умолчанию смещены от привычных 8080, 5173 и 5432 намеренно: на машине
разработчика они обычно уже заняты, и запуск падает с `port is already allocated`.

**Секретов в репозитории нет.** Файл `.env` в git не попадает; в репозитории лежит
только образец без рабочих значений (условия трека, разд. 4 п. 9).

## Порядок проверки

```sh
sh tests/devops/проверка-запуска.sh
```

Скрипт разбирает `compose.yaml`, сверяет состав служб, поднимает решение одной
командой и проверяет ответы. Ожидаемый результат:

```text
расчётная часть: живость /health                ок (200)
расчётная часть: готовность /ready (видит базу) ок (200)
чат-бот: живость /health                        ок (200)
мини-приложение: страница                       ок (200)
мини-приложение → расчётная часть через /api    ок (200)
чат-бот принимает вебхук                        ок (200)
Плацдарм развёртывания проверен: отказов нет.
```

Проверка фальсифицируема: она падает, если убрать службу из `compose.yaml`,
разорвать проксирование `/api` в `nginx.conf` или отобрать у расчётной части
доступ к базе данных.

Вручную то же самое:

```sh
curl http://localhost:18080/health     # {"service":"api","status":"ok"}
curl http://localhost:18080/ready      # {"service":"api","status":"ready","database":"reachable"}
curl http://localhost:18081/health     # {"service":"bot","status":"ok","token_configured":false}
curl http://localhost:15173/api/health # ответ расчётной части через мини-приложение
```

## Зависимости

| Компонент | Чем зафиксированы версии |
|---|---|
| `api`, `bot` | `packages.lock.json` рядом с каждым проектом; сборка в образе идёт в режиме замка и падает при расхождении |
| `miniapp` | `package-lock.json`; в образе выполняется `npm ci` |
| Базовые образы | Теги закреплены в `Dockerfile`: `sdk:10.0`, `aspnet:10.0`, `node:24-alpine`, `nginx:1.29-alpine`, `postgres:17-alpine` |

Сборка с нуля (`docker compose build --no-cache`) заняла 16 секунд при уже
загруженных базовых образах — условия трека отводят на неё не более 5 минут.

## Статический анализ

```sh
SONAR_TOKEN=<токен> sh devops/sonar/анализ.sh
```

Анализ выполняется в контейнере, поэтому на машине нужен только Docker:
сканер SonarQube для .NET работает поверх Java, и ставить её отдельно
не требуется. Разбираются обе части решения: C# собирается сканером через
сборку решения, JavaScript и TypeScript мини-приложения разбираются попутно.

| Переменная | Назначение |
|---|---|
| `SONAR_HOST` | Адрес сервера анализа |
| `SONAR_PROJECT` | Ключ проекта на сервере |
| `SONAR_TOKEN` | Токен анализа проекта |

Значений по умолчанию нет: без любой из трёх переменных скрипт
останавливается. Сервер анализа принадлежит организации, поэтому его адрес
и ключ проекта в репозитории не хранятся, а лежат в локальном `.env`.

Токен в репозиторий не попадает и в команду не вписывается: он приходит
переменной окружения.

**Анализ запускается вручную и в конвейер не вынесен.** Секрет уровня
репозитория доступен любому прогону на любой ветке, а значит и каждому
участнику с правом записи: тот может отправить значение секрета куда угодно
своим же заданием. Токен корпоративный, поэтому он остаётся на машине
владельца, в файле `.env`, и анализ выполняется перед контрольными точками
и сдачей, а не на каждую отправку. Если анализ понадобится в конвейере,
токен кладётся в окружение с обязательным подтверждением, а не в секреты
репозитория.

Из анализа исключены зависимости, результаты сборки, макеты, документы
и обвязка разработки. Валидаторы `trip/` исключены намеренно: они приходят
с установкой инструментария и под действующей политикой неизменяемы, поэтому
их находки выглядели бы как долг команды, который нельзя закрыть.

Ссылка на панель с результатом печатается по завершении анализа.

## Известные ограничения плацдарма

1. **Предметной логики нет.** Расчёт, справочники полигонов и цен, сценарии
   чат-бота и экраны мини-приложения не реализованы; службы отвечают только
   на запросы работоспособности.
2. **Схемы базы данных нет.** Миграции не заведены — способ их ведения выбирается
   вместе с первой предметной областью и записью архитектурного решения.
3. **Подключение к платформе MAX не выполнено.** Мини-приложение подключается
   к MAX только по HTTPS, а вебхук чат-бота требует внешнего адреса: локально
   нужен туннель либо развёрнутый стенд. Внутри Docker это не воспроизводится —
   по условиям трека (разд. 6.1 п. 3) такой внешний сервис называется отдельно.
4. **Раскладка кода не объявлена средству.** `trip/cast-agreement.json` не заведён:
   объявление областей делается вместе с первой областью и её владельцем.
