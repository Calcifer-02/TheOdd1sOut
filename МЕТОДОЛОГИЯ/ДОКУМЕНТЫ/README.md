# Методология TRIP

Версия методического пакета: **1.25**
Дата: **27.08.2026**

TRIP помогает команде доводить инициативу от замысла до передаваемого продукта, сохраняя трассируемость решений и возможность безопасно остановить работу в любой момент.

## Основные правила

1. Не копируйте пакет целиком в проект. Берите только те шаблоны, которые нужны для доказуемого результата и передачи контекста.
2. Реестр требований — центральный источник формулировки, состояния и класса важности; матрица и граф трассируемости являются производными представлениями.
3. Код объявляет только локальные типизированные связи по стандарту трассируемости (подключается в Gate 2); класс важности и текст требования в код не копируются.
4. Требование связывается с решением, изменением и проверкой. Отдельная карта подтверждений для этого не нужна.
5. Доменные, продуктовые, технические и эксплуатационные угрозы ведутся в одном реестре рисков; матрица оценки строится из него.
6. Стадия — контрольная точка результата и безопасной остановки, а не отчётный ритуал.
7. На каждой контрольной точке и при внеплановой паузе проект собирается по одной схеме пакета заморозки.
8. В ежедневной записи вручную остаются только решения, блокеры, координация и сигнал к заморозке. Факты о коде и задачах берутся из Git и системы управления разработкой.
9. Значимое изменение завершается ближайшей проверкой, которая действительно упадёт при поломке.
10. Объём документов определяется риском и потребностью в передаче, а не нормативным количеством файлов.
11. Полномочия распределяются по RACI; состояние задачи не переносит ответственность автоматически.
12. Тип изменения и стратегическое направление коммита объявляются раздельно.
13. `main` остаётся упакованным источником истины; каждое изменение изолируется
    в проверяемой ветке с направлением, ролью `A` и контекстом возобновления.

14. Система описывается типизированными фактами `current`/`target`/`horizon`;
    правила активируются фактами, а применимость определяется покрытием
    обязательных возможностей без суммарного балла.

15. Агентный проход интерфейса сохраняет проверяемое свидетельство, а
    воспроизводимая находка переносится в детерминированную регрессию.

16. Инженерная практика подключается как навык только по наблюдаемой задаче;
    полный корпус инструкций не загружается в рабочий контекст.

17. Навык вызывает только фактически доступную возможность TRIP, связывает
    свидетельство с точной ревизией и не повышает зрелость прототипа словами.

18. Человеческая техника ведения работы публикуется практическим руководством;
    навык получает только выделенная повторяемая операция с наблюдаемым
    результатом и ближайшей проверкой.

## Быстрый старт

1. Прочитайте [инструкцию команде](ИНСТРУКЦИЯ_КОМАНДЕ.md) и [глоссарий](ГЛОССАРИЙ_МЕТОДОЛОГИИ.md).
2. Примите стандарт трассируемости (подключается в Gate 2) до первого изменения кода.
3. Пройдите профилирование в день 1 (подключается в Gate 1)
   и сохраните входную анкету (подключается в Gate 1).

4. Выберите нужные [артефакты аналитики](01_ПАКЕТ_АРТЕФАКТОВ_АНАЛИТИКИ/README.md).
5. Определите основной режим по [матрице режимов](09_РЕЖИМЫ_РАЗРАБОТКИ/МАТРИЦА_РЕЖИМОВ.md).
6. Согласуйте минимальные эксплуатационные доказательства по единой политике DevOps (подключается в Gate 3).
7. Ведите короткую ежедневную запись (подключается в Gate 2).
8. Для каждого изменения используйте руководство по проверкам и дефектам (подключается в Gate 3).
9. Назначьте `R/A/C/I` по регламенту зон ответственности (подключается в Gate 1).
10. Примите соглашение о ветках (подключается в Gate 2),
   соглашение о коммитах (подключается в Gate 2)
   и соглашение о журнале изменений (подключается в Gate 2).

11. Подключите библиотеку навыков (подключается в Gate 2),
    чтобы агент выбирал инженерную практику и нативный исполнитель TRIP по
    задаче, а не по памяти.

Ролевые маршруты собраны в [карте обязательного чтения](../КАРТА_ОБЯЗАТЕЛЬНОГО_ЧТЕНИЯ.md).

## Соглашения шаблонов

- `owner_functional_role` и `filled_by_functional_roles` содержат только
  отдельные значения закрытого перечня: Ведущий, Аналитик, Архитектор,
  Разработчик, QA, Заказчик, Методолог.

- Когнитивные роли — Исследователь, Реализатор, Теоретик, Архитектор моделей —
  фиксируются отдельно и не подставляются в поля функциональных ролей.

- Один человек может совмещать роли, но составное название не создаёт новую
  роль.

- Человекочитаемые даты в проектных артефактах записываются как
  `ДД.ММ.ГГГГ`. Формат `ДД.ММ.ГГГГ` допустим только в машинных полях и именах
  файлов.

- Архитектурное решение обозначается `ADR`, а конкретная запись —
  `ADR-NNNN`.

- Версия документа начинается с `1.0` и при содержательном изменении повышает
  младшую часть: `1.1`, `1.2`, …; префикс `v` в паспорте и метаданных документа
  не используется. Версии выпусков, протоколов, схем и навыков живут по своим
  контрактам.
