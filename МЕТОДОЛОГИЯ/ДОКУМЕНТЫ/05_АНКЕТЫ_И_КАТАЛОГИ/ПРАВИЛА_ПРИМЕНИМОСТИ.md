# Правила применимости

> Правила связывают наблюдаемые факты [профиля системы](ПРОФИЛЬ_СИСТЕМЫ.md) с обязательствами, требуемыми возможностями, практиками и доказательствами. Они не выбирают архитектуру по названию продукта и не принимают решения, закреплённые за человеком.

## Паспорт артефакта

| Параметр | Значение |
|---|---|
| Версия | 1.0 |
| Владелец | Методолог |
| Заполняют | Методолог; Архитектор и QA предлагают и проверяют кандидатов; профильный специалист подтверждает внешние основания |
| Появляется | до первого профилирования |
| Обновляется | при подтверждении нового взаимодействия признаков, изменении внешнего основания или устойчивом ложном срабатывании |

## 1. Цепочка вывода

```text
типизированные факты конкретного субъекта
    → условие правила
    → обязательства
    → требуемые возможности
    → требуемые практики
    → ожидаемые доказательства
    → пробел покрытия
    → supported / gray / outside
```

Правило не принимает на вход архетип, название отрасли, краткую `A–E`-сводку или суммарный балл.

## 2. Форма правила

```yaml
id: API-101
version: 1
title: Устойчивость критической внешней интеграции
strength: risk_triggered
criticality: high
when:
  fact: integrations.critical_external_api
  op: equals
  value: true
obligations:
  - определить тайм-ауты, повторы и допустимую деградацию
requiredCapabilities:
  - integration_resilience
requiredPractices:
  - контрактные проверки
requiredEvidence:
  - проверка недоступности и замедления зависимости
humanConfirmation: false
gapEffect: gray
sourceIds:
  - GOOGLE-SRE-GOLDEN-SIGNALS
  - TRIP-SYSTEM-PROFILE-V2
counterexamples:
  - необязательная аналитическая интеграция
```

Обязательны:

- устойчивый идентификатор и версия;
- одно проверяемое условие либо явная комбинация `all` / `any` / `not`;
- сила и критичность;
- хотя бы одно обязательство;
- источник основания;
- контрпример, различающий соседнее, но неприменимое условие;
- ожидаемое влияние непокрытого пробела.

## 3. Сила обязательства

| Код | Смысл | Кто может изменить |
|---|---|---|
| `mandatory_external` | внешнее правовое, договорное или отраслевое обязательство | только уполномоченный владелец основания; TRIP хранит ссылку и решение |
| `mandatory_internal` | обязательное правило поставки TRIP | Методолог через версионируемое изменение |
| `risk_triggered` | обязательство включается при конкретном рисковом сочетании фактов | Архитектор может предложить эквивалентное покрытие через запись решения |
| `recommended` | исходная рекомендация с объяснимым отклонением | Архитектор через запись решения |
| `optional` | выбирается режимом или командой | владелец соответствующей зоны |
| `prohibited` | условие несовместимо с заявленным способом поставки | только изменение охвата или внешнее расширение возможностей |

Сила правила и сигнал проверки различны. Например, внешнее обязательство может требовать решения человека, а не машинной ошибки.

## 4. Условия

Разрешены только атомарные сравнения фактов и логические композиции:

| Операция | Пример |
|---|---|
| `equals`, `not_equals` | роль сообщений равна `core` |
| `contains`, `contains_any` | перечень классов данных содержит персональные идентификаторы |
| `exists` | задана целевая задержка `p99` |
| `gte`, `lte` | пиковая интенсивность не ниже проверочного порога |
| `all` | автономная запись и несколько авторов присутствуют одновременно |
| `any` | высоко хотя бы одно последствие: конфиденциальность, целостность или доступность |
| `not` | исключение строго определённого признака |

Числовой порог активирует обязанность проверить нагрузочную гипотезу, но сам по себе не назначает число узлов, вид хранилища или статус `outside`.

## 5. Начальные правила взаимодействия

| Наблюдаемый признак или сочетание | Обязательство | Требуемая возможность | Пробел по умолчанию |
|---|---|---|---|
| сообщения являются ядром | семантика доставки, повторы, порядок, неисправимые сообщения | инженерия надёжной доставки | `gray` |
| модель транзакций — сага | частичные состояния, завершение и компенсации | восстановление многошаговых операций | `gray` |
| журнал событий — источник истины | эволюция событий и восстановление представлений | восстановление событийной модели | `gray` |
| критический внешний стык | тайм-ауты, ограниченные повторы, контракт и деградация | устойчивость интеграций | `gray` |
| персональные данные | правовая и защитная классификация | защита персональных данных | `gray` до решения специалиста |
| высокий уровень одного из последствий | профиль доказательств критичного свойства | обеспечение безопасности | `gray` |
| заявлен `p99` | измерительная модель и бюджет задержки | инженерия производительности | `gray` |
| заявлены `RTO` или `RPO` | проверяемое восстановление | инженерия восстановления | `gray` |
| автономная запись + несколько авторов | разрешение конфликтов | распределённая синхронизация | `gray` |
| ИИ применяет инструменты | ограничение полномочий, журнал, оценочные сценарии, остановка | обеспечение ИИ | `gray` |
| ИИ с инструментами + чувствительные данные | раздельные границы данных и полномочий | обеспечение ИИ на чувствительных данных | `gray` до решения человека |
| высокое влияние на физическую безопасность | независимый анализ опасностей и безопасное состояние | предметное обеспечение безопасности | `outside`, если возможности нет |
| обязательная внешняя оценка | подтверждённая независимая сторона и формальный допуск | независимое обеспечение | `outside`, если возможности нет |

Это исходный корпус, а не закрытый перечень. Каждое добавление проходит различающий контрпример.

## 6. Правовые и защитные правила

Класс данных активирует **классификацию**, а не готовый технический набор. В частности:

```text
персональные данные
    → определить применимые режимы, угрозы, роли обработки и риск
    → ответственное лицо выбирает соразмерные меры
    → команда проверяет выбранные меры
```

Нельзя автоматически выводить из одного признака:

- обязательное шифрование каждого поля и каждого хранилища;
- необходимость сертификации;
- конкретный уровень защищённости;
- применимость режима только по стране заказчика;
- критичность только по слову «медицина», «банкинг» или «транспорт».

Автоматизация обязана остановиться на `decision`, если вывод зависит от права, договора, полномочий, физической безопасности или принятия остаточного риска.

## 7. Покрытие и статус

Для каждого активированного правила проверяются требуемые возможности и человеческие подтверждения.

```text
available + источник состояния → покрыто
planned / missing / unknown / нет источника → пробел
```

На статус применимости влияют только `mandatory_external`, `mandatory_internal`,
`risk_triggered` и `prohibited`. Непокрытые `recommended` и `optional` выводятся
отдельными рекомендациями и не понижают статус, пока команда или режим не приняли
их как обязательство.

Если условие обязательного правила нельзя вычислить из-за отсутствующего факта,
оно не считается ложным: правило попадает в перечень с неопределённой применимостью,
а статус становится `gray`. Для составного условия заведомо ложная ветвь может снять
неопределённость; отрицание неизвестного факта не превращает его в истину.

Алгоритм не складывает баллы:

1. Сработавший запрет даёт `outside`.
2. Критичный пробел с `gapEffect: outside` даёт `outside`.
3. Иной пробел или ожидаемое подтверждение даёт `gray`.
4. Только отсутствие пробелов даёт `supported`.

Одна доступная возможность не покрывает другую по сходству названия. Возможность может предоставляться командой, самим TRIP, привлечённым экспертом или внешним сервисом, но её область и доказательство фиксируются явно.

## 8. Правила и проверки проекта

Правило применимости отвечает: **что становится обязательным и почему**. [Каталог правил проекта](КАТАЛОГ_ПРАВИЛ_ПРОЕКТА.md) отвечает: **какая конкретная проверка ловит нарушение в поставке**.

```text
правило применимости
    → активированная практика
    → правило проекта
    → исполнимая проверка и контрпример
```

Одно обязательство может иметь несколько проверок на разных стадиях. При этом источник обязательства хранится в правиле применимости, а технический способ обнаружения — в правиле проекта.

## 9. Отклонение и исключение

Отклонение оформляется [записью архитектурного решения](../01_ПАКЕТ_АРТЕФАКТОВ_АНАЛИТИКИ/архитектурные_решения/ШАБЛОН_АРХИТЕКТУРНОГО_РЕШЕНИЯ.md) и содержит:

- правило и версию;
- субъект и снимок;
- причину неприменимости либо эквивалентное покрытие;
- риск и владельца принятия;
- заменяющее доказательство;
- срок пересмотра.

Языковая модель не подтверждает исключение. Отсутствие ответа не считается согласием.

## 10. Проверка корпуса правил

Корпус пригоден, если:

- все пути фактов разрешаются в каноническом словаре;
- все источники существуют и имеют дату пересмотра;
- у каждого правила есть контрпример;
- событие без саги не включает компенсации;
- сага без событийного ядра не включает очередь неисправимых сообщений;
- малая аудитория с жёстким реальным временем не становится «высокой нагрузкой»;
- большой поток не означает автоматический выход;
- персональные данные не включают универсальный способ защиты;
- отрасль не назначает критичность;
- критичный непокрытый пробел не компенсируется;
- повторный прогон на тех же входах даёт тот же результат.
