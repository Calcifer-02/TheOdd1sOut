# Средства слоя B в проекте

> Как проект получает инструменты TRIP, не храня их копии у себя.

Методология (слой A) задаёт правила и контракты. Инструменты (слой B) — отдельные
продукты со своим жизненным циклом. Проект не копирует их исходники: он объявляет,
какие средства ему нужны и каких версий, и забирает готовые выпуски.

## Страховочные колёса

[training-wheels.json](./training-wheels.json) — страховочные колёса проекта, единственный источник
истины по средствам проекта. Для каждого средства объявлены:

| Поле | Что означает |
|---|---|
| `requirement` | обязательное, рекомендуемое или необязательное |
| `needed_from_gate` | с какой контрольной точки средство становится нужным |
| `version` | закреплённая версия выпуска |
| `source` | откуда берётся выпуск; единая форма — generic-пакет в реестре репозитория средства |
| `release_state` | выпускается ли средство сегодня или пока собирается из исходников |
| `sha256` | отпечатки файлов выпуска — карта по тем же ключам, что `files`; несовпадение прекращает установку |

Смена версии средства — правка страховочных колёс и проход гейта в запросе на слияние.
Молчаливое обновление инструмента ломает воспроизводимость проверок.

## Команды

```bash
node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs проверить     # что есть, чего нет
node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs план          # какие адреса будут вызваны
node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs установить    # получить выпуски
node ИНСТРУМЕНТЫ/скрипты/проверить-скелет.mjs          # зоны, плейсхолдеры, ссылки, описание конвейера
node ИНСТРУМЕНТЫ/скрипты/обновить-оснастку.mjs         # подтянуть оснастку и замок до состояния шаблона
node ИНСТРУМЕНТЫ/скрипты/обновить-оснастку.mjs --проверить   # то же, только отчёт и код возврата
node ИНСТРУМЕНТЫ/скрипты/навыки.mjs проверить          # навыки: имена, отпечатки, реестр
node ИНСТРУМЕНТЫ/скрипты/навыки.mjs установить-из <порция>
node ИНСТРУМЕНТЫ/скрипты/навыки.mjs разложить .claude/skills
node --test ИНСТРУМЕНТЫ/скрипты/проверки.test.mjs      # проверка самих проверок
```

Скрипты работают на Node 18 и выше и не требуют зависимостей. Полученные
выпуски раскладываются в `.trip/tools/<средство>/` и не версионируются.

## Расхождение с шаблоном

Проект создаётся из шаблона копией, и дальше они расходятся: шаблон получает
исправления, а проект о них не узнаёт — сам по себе он их не догонит.
`обновить-оснастку.mjs` переносит ровно те изменения, владельцем которых
остался шаблон: гейты, правила исключений, проверку скелета и закреплённую
версию `trip-cli` в страховочных колёсах. Содержание проекта не трогается.

Каждое обновление умеет ответить, применено ли оно, поэтому повторный запуск
безопасен и ничего не дублирует, а неприменимое обновление называется вслух, а
не выдаётся за применённое. Скрипт ничего не коммитит: часть изменений
затрагивает методологию и требует политики `policies-only`, часть — обычной
`generic`, и смешивать их в одном коммите нельзя. Предлагаемый порядок
фиксации печатается в конце.

Каталог выбран не произвольно: с версии `trip` 0.4.0 реестр средств единого
входа читает именно его. Распакованное туда средство `trip tools list` видит, а
`trip tools doctor` показывает готовую команду запуска — без установки в
систему и без имени в оболочке. `trip uninstall --purge` удаляет `.trip/`
целиком вместе со средствами; они восстанавливаются установкой по замку.

## Доступ без личных учётных записей

Инструменты живут во внутреннем GitLab, к которому есть доступ не у всех
участников. Личные учётные записи для получения выпусков не нужны: доступ даёт
один токен только на чтение реестра пакетов.

| Кто | Что использует | Откуда берёт токен |
|---|---|---|
| Сборка CI | переменную группы `TRIP_TOOLS_TOKEN` | администратор задаёт один раз на группу проектов, маскированной и защищённой |
| Участник на своей машине | ту же переменную окружения | получает у ведущего, либо работает с уже установленными в системе средствами |
| Ведущий | токен и права на подъём служб | администратор |

```bash
export TRIP_TOOLS_TOKEN=<токен на чтение реестра пакетов>
export TRIP_TOOLS_TOKEN_KIND=deploy   # deploy | private | job
node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs установить
```

Токен в репозиторий не попадает и в журнал сборки не печатается. Если переменная
не задана, установка останавливается с явной причиной, а не тихо пропускает
средство.

## Единая форма поставки

Все средства группы `TRIP/tooling` поставляются одинаково: **generic-пакет в
реестре пакетов своего репозитория**. Сборка по метке выпуска кладёт туда
собранные файлы и отпечатки SHA-256; публикация — отдельная ручная ступень
владельца, и версия публикуется один раз.

| Что за средство | Файл выпуска | Что делает скрипт |
|---|---|---|
| Командное средство (trip, линтер, КАСТА, трасса, trip-file) | архив на платформу: `<средство>-<платформа>.tar.gz` | скачивает файл своей платформы, сверяет отпечаток, распаковывает в `.trip/tools/<средство>/` |
| Служба проекта (Bug Loop, инспекторы) | бандл развёртывания: `<средство>-bundle.tar.gz` | скачивает и сверяет; подъём службы остаётся действием эксплуатации по `РАЗВЁРТЫВАНИЕ.md` внутри бандла |
| Платформонезависимое (коннектор SHIVA) | один файл `-any.tar.gz` | как командное средство |

Прочие виды источников (`job-artifact`, `npm-registry`, `container-image`)
скрипт продолжает понимать как переходные, но действующий замок ими не
пользуется: артефакт задания привязан к ветке и исчезает по сроку хранения,
а образ и npm требуют отдельных прав токена.

## Чего сегодня не хватает

- **Сборок под macOS на Apple Silicon.** `trip-doc-lint` и `trip-trace-service`
  выпускаются только под `linux-x64` и `win-x64`, `trip-customs` — ещё и под
  `darwin-x64`, но не под `arm64`. Установка называет это прямо: «выпуск под
  darwin-arm64 не публикуется; собирается под: …». Чужая архитектура не
  подставляется даже там, где её выполнил бы слой совместимости: подмена молча
  выглядит как «всё есть», а отказ приходит позже и не от установки.

  Обязательный `trip-doc-lint` при этом не остаётся без проверки: гейт
  документации выполняет его в linux-образе сборки, поэтому на Apple Silicon
  недоступен только локальный прогон, а не сама проверка. Посмотреть, что
  получит коллега на другой машине, можно не заводя её:
  `TRIP_TARGET_PLATFORM=darwin-arm64 node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs план`.

- Пакет MCP-серверов живёт в репозитории методологии (`TRIP/doc`), и его
  выпуск в реестр пакетов ещё не настроен — поле `release_state` называет это
  честно; до выпуска эти средства ставятся из исходников теми, у кого есть
  доступ.
- `db-diff-inspector` в страховочные колёса не включён: это отладочный инструмент одной
  сессии, он запускается из исходников и дистрибутива не имеет.
- `TRIP Reviewer` и `TRIP Anchor` — центральные службы контура ведущего, а не
  средства команды: разворачиваются один раз из своих бандлов выпуска, а
  проекты подключаются к ревьюеру настройкой GitLab — push-вебхуком на группе
  (рекомендуемый режим `git_mirror`) либо CI-заданием из
  `.gitlab-ci.example.yml` его репозитория. В страховочные колёса они не входят.
- `tuzic` в страховочные колёса не включён решением владельца методологии: продукт ещё не
  созрел. Исключение временное — снимается строкой в страховочных колёсах, когда решение
  изменится.
- Гейты, которым средства не хватает, сообщают «средство не настроено» и не
  выдают отсутствие проверки за пройденную проверку.

## Навыки агента

Навыки — не средство слоя B: это переносимые инструкции, которые приходят
с порцией методологии Gate 2, а не из реестра пакетов. Шаблон несёт порядок
установки, проверку и замок отпечатков; сама поставка в шаблоне не лежит,
иначе на Gate 2 в репозитории оказались бы две копии одних файлов.
Порядок — [.agents/skills/README.md](../.agents/skills/README.md).

Пользовательские инструкции к средствам страховочных колёс продублированы в
