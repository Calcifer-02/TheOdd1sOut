# TRIP Trace Service

Единый сервис трассируемости для экосистемы TRIP. Он должен отвечать не на
вопрос «встречается ли где-нибудь R-id», а на два независимых вопроса:

1. классифицированы ли применимые единицы кода;
2. имеет ли каждое применимое требование полный обязательный след до реализации
   и проверки с учётом класса важности.

Проект реализует существующий эпик **EB-21 / M17** методологии TRIP. Первый
поставляемый срез — детерминированный Trace Scanner и стабильный контракт
`trip.trace-scan/v2`. Тот же продукт уже сохраняет `trip.trace-graph/v2` и
отдаёт его через локальный HTTP; следующие срезы добавят diff графов, полный
анализ влияния и кандидатов на удаление. Отдельный эпик для сканера не создаётся.

Нормативная спецификация и стандарт не копируются в этот репозиторий: они
остаются в соседнем основном проекте `../TRIP`. Машинно проверяемые пути к
`TRIP_спецификация_v0.35.md`, `МЕТОДОЛОГИЯ/СТАНДАРТ_ТРАССИРУЕМОСТИ.md` и
бэклогу закреплены в `harness/toolchain.json`. Этот репозиторий содержит только
спецификацию и реализацию продукта слоя B.

## Состояние

Статус: **частично**.

Готов исполняемый вертикальный срез: полный Markdown-реестр TRIP → структурный
анализ TypeScript/JavaScript, Python и C# → уровни модуль/тип/символ →
канонический `trip.trace-scan/v2` → CLI/HTTP → неизменяемый двунаправленный
`trip.trace-graph/v2`. Режим `change` сравнивает базовый и новый полные следы,
а `trip-cli` предоставляет команду `trip trace` и условный pre-push-барьер.
Потребители получают срезы отчёта командой `trip-trace view`, свидетельства
принимаются в форматах `trip.test-run/v1`, JUnit XML, TRX, LCOV и Cobertura.
Остаются pin поставки, diff графов и пилотная калибровка на подопытных
проектах.

## Серверный барьер

Обязательной границей доверия считается конвейер `.gitlab-ci.yml`: он повторяет
`verify`, сборку и полное сканирование ветки со свидетельствами собственного
прогона, а для запроса на слияние — сканирование только диапазона изменения.
Локальные hook дают раннюю обратную связь, но обходятся, поэтому границей не
являются. Назначение задачи «трасса» обязательной проверкой защищённой ветки
выполняется в настройках проекта и остаётся за ведущим.

## Быстрый старт

~~~powershell
npm ci
npm run verify
npm run build
npm run toolchain:check
~~~

Полный локальный проход запускается с явно зафиксированным commit:

~~~powershell
npm run scan -- --mode full --head <git-sha> --repository <id> --output .trip/trace/report.json
~~~

Граф и HTTP:

~~~powershell
trip-trace graph save --mode full --head <git-sha>
trip-trace graph query --snapshot latest --node requirement:R-001
trip-trace serve --host 127.0.0.1 --port 8787
~~~

Через общий оркестратор те же аргументы передаются как `trip trace ...`; сам
алгоритм в `trip-cli` не дублируется.

Коды завершения: `0` — `pass`, `2` — `warn`, `3` — `fail`, `1` — техническая
ошибка. `npm run verify` выполняет строгую проверку типов, контрактов, ссылок и
положительных/отрицательных сценариев. `npm run toolchain:check`
проверяет основной TRIP и его нормативный стандарт, локальный trip-cli,
закреплённые схемы всех трёх Inspectors, версию File Level Tooling, корень
Anchor и `/health` Reviewer.
`TRIP_REVIEWER_URL` переопределяет адрес, но Reviewer является обязательной
частью локального стенда.

Перед каждым commit staged-срез проверяется через:

~~~powershell
npm run toolchain:file
~~~

Reviewer остаётся будущим потребителем отчёта и проверяется по `/health`, но
обычные коммиты проекта на оценку не отправляются. Локальные отчёты проверок
сохраняются в `.trip/evidence/` и не версионируются.

## Граница ответственности

Trace Service вычисляет факты трассируемости и публикует доказуемый отчёт.
Reviewer принимает отчёт как доказательство ревью, trip-cli организует запуск,
Inspectors добавляют профильные свидетельства, File Level Tooling показывает
находки у файлов, а Anchor использует уже подтверждённые показатели. Ни один
потребитель не дублирует парсер маркеров или формулу покрытия.
