## Установка

Средство поставляется одним архивом на все системы: `trip-lint.tar.gz` в
реестре пакетов репозитория `TRIP/tooling/trip-lint`. Отдельной сборки под
Windows, Linux или macOS нет — нужен только Node.js 22 или новее.

**Проект из шаблона TRIP.** Средство объявлено в ходунках, и его
ставит тот же скрипт, что и остальные:

```bash
export TRIP_TOOLS_TOKEN=<токен на чтение реестра пакетов>
export TRIP_TOOLS_TOKEN_KIND=deploy          # deploy | private | job
node ИНСТРУМЕНТЫ/скрипты/инструменты.mjs установить trip-lint
node .trip/tools/trip-lint/bin/trip-lint.mjs --version
```

**Проект, созданный из шаблона раньше появления гейта.** Оснастку переносит
скрипт обновления из шаблона: он кладёт `.gitlab/ci/code-lint.yml`, подключает
его в `.gitlab-ci.yml` и добавляет запись средства в ходунки.

```bash
node ИНСТРУМЕНТЫ/скрипты/обновить-оснастку.mjs --проверить   # что будет сделано
node ИНСТРУМЕНТЫ/скрипты/обновить-оснастку.mjs               # применить
```

Скрипт ничего не коммитит и повторный запуск ничего не дублирует.

**Проект без шаблона.** Архив забирается из реестра пакетов тем же токеном:

```bash
VER=0.4.0
curl -fsSL --header "DEPLOY-TOKEN: $TRIP_TOOLS_TOKEN" \
  "https://git-internal.imbalanced.tech/api/v4/projects/TRIP%2Ftooling%2Ftrip-lint/packages/generic/trip-lint/$VER/trip-lint.tar.gz" \
  -o trip-lint.tar.gz
mkdir -p .trip/tools/trip-lint && tar -xzf trip-lint.tar.gz -C .trip/tools/trip-lint
node .trip/tools/trip-lint/bin/trip-lint.mjs --version
```

Заголовок токена зависит от его вида: `DEPLOY-TOKEN` у токена развёртывания,
`PRIVATE-TOKEN` у личного, `JOB-TOKEN` у токена задания конвейера. Отпечаток
архива сверяется с `ВЫПУСК.json` внутри него и с записью замка шаблона.

**Из исходников** (разработка самого средства):

```bash
git clone https://git-internal.imbalanced.tech/TRIP/tooling/trip-lint.git
cd trip-lint && npm ci && npm i -g .
trip-lint --version
```

Движки стека (ESLint, Prettier, SDK .NET 10, squawk для миграций) ставятся в
проекте, не в средстве; анализаторы .NET приходят пакетом `Trip.CodeStyle`
проверяемого решения.

### Доступ к пресетам: один токен на чтение

Пресеты `@trip/*` лежат в реестре npm того же репозитория, пакет
`Trip.CodeStyle` — в реестре NuGet группы `TRIP`. Права нужны те же, что и для
архива: **чтение реестра пакетов**, поэтому годится тот же `TRIP_TOOLS_TOKEN`.
Значение в репозиторий не попадает: `trip-lint init` выпускает `.npmrc` и
`nuget.config`, которые читают переменные окружения.

```bash
export TRIP_TOOLS_USER=gitlab+deploy-token-<номер>   # имя пользователя токена развёртывания
export TRIP_TOOLS_TOKEN=<тот же токен>
npm i -D @trip/eslint-config @trip/eslint-plugin @trip/prettier-config
dotnet restore
```

Токен участнику выдаёт ведущий, конвейеру — переменная группы; это два разных
токена с одинаковыми правами, чтобы отзыв одного не останавливал другой.

## Подключение к проекту

```bash
trip-lint init --root . --frontend frontend --write
```

Команда кладёт черновик `.trip-lint.toml` в корень репозитория,
`eslint.config.js` и `.prettierrc.json` в корень фронтенда и печатает
зависимости разработки. Фронтенд ищется по `package.json`, .NET — по файлу
решения; ключи `--frontend` и `--dotnet` задают корни явно. Существующие
файлы не перезаписываются. Затем:

```bash
cd frontend
npm i -D eslint@10.10.0 prettier@3.9.6 @trip/eslint-config@0.2.0 @trip/eslint-plugin@0.2.0 @trip/prettier-config@0.2.0
```

Проектные слои ESLint дописываются после пресета в `eslint.config.js`.
Пресет несёт корпоративный стандарт фронтенда: Prettier с точками с запятой и
шириной 120, именование без префиксов `I`, `T`, `E`, запрет `any` и вложенных
тернарников, суффикс `Async` у асинхронных функций, только `script setup`.

Для решения .NET та же команда кладёт рядом с файлом решения
`Directory.Build.props` со ссылкой на `Trip.CodeStyle` и
`RestorePackagesWithLockFile`, `nuget.config` с реестром группы TRIP и, если
его нет, `.editorconfig` слоя стиля в корень репозитория. Затем:

```bash
dotnet restore            # появятся packages.lock.json рядом с проектами — закоммитьте их
trip-lint check --root . --mode observe
```

Правила дисциплины (`CA1031`, `RS0030`, `VSTHRD002`, `VSTHRD100`,
`VSTHRD110`, `CA1502`, `CA1505`) в сборке — предупреждения, в trip-lint —
ошибки; подавление любого из них требует причины (`// причина: …`) или
строки реестра. Слой стиля — корпоративный стандарт C# с именованием по мировой практике:
приватные поля `_имя`, статические `s_имя`, параметры без префикса, `internal`
явно, суффикс `Async`, имена тестов `Given_<что>_When_<когда>_Then_<тогда>`
строчными частями с разметкой Arrange, Act, Assert (или Подготовка, Действие,
Проверка); всё это предупреждения. Состав — `dotnet-discipline.md`, источники —
`analytics/knowledge-base-rules.md`.

Для миграций PostgreSQL в `**/migrations/**/*.sql` движок `sql` включается
сам; поставьте `squawk-cli` в devDependencies проекта:

```bash
npm i -D squawk-cli@2.65.0
```

Безопасность миграции (удаление столбцов, индексы без `CONCURRENTLY`,
ограничения без `NOT VALID`) — ошибка, типы и форма (`timestamptz`, `text`,
`identity`, `bigint`, таймауты) — предупреждение; состав — `sql-rules.md`.
Раздел `[sql]` конфигурации задаёт образцы миграций и, при нужде, свою
команду squawk.

## Ежедневные команды

```bash
trip-lint check --root .                       # режим из [gate].mode
trip-lint check --root . --mode observe        # отчёт без остановки работы
trip-lint check --root . --staged              # перехват коммита: только индекс
trip-lint check --root . --base origin/main    # запрос на слияние
trip-lint check --root . --format json         # отчёт в стандартный вывод
trip-lint check --root . --signal .trip/lint-signal.json
trip-lint rules                                # карточки правил
trip-lint explain TEST-001                     # карточка правила каталога
trip-lint explain trip/comment-language        # карточка правила движка
```

Отчёт всегда пишется в `.trip/lint-report.json` (или `--report`).

## Осмотр конфигурации

Пресеты можно переопределить своим слоем конфигурации, и обычная проверка
этого не увидит: она читает уже вычисленный свод правил. Осмотр сравнивает
конфигурацию проекта с пресетами средства:

```bash
trip-lint doctor --root .
```

Находка осмотра — правило пресета, выключенное или понижённое проектом,
изменённое значение Prettier, понижение правила дисциплины .NET в
`.editorconfig`, `.globalconfig` или через `NoWarn`. Если отступление
осознанное, объявите его с записью решения, и осмотр замолчит:

```toml
[[frontend.overrides]]
rule = "no-nested-ternary"
decision = "ADR-0042"

[[dotnet.overrides]]
rule = "VSTHRD100"
decision = "ADR-0007"
```

Отклонение на правило, которого в пресете нет, — устаревшая запись, и осмотр
говорит об этом отдельно. Правила стиля .NET (`IDE00xx`) проект меняет
свободно: дисциплину — нет.

## Сравнение снимков

В режиме `changed` блокируют находки изменённых файлов. Наследованному корпусу
это мешает: правка строки поднимает весь долг файла. Снимок решает иначе —
блокирует только то, чего не было в предыдущем отчёте:

```bash
trip-lint check --root . --previous trip/lint-previous.json
```

Находки предыдущего отчёта помечаются «известно» и в режиме `changed` не
блокируют; в `enforce` считаются наравне со всеми. Ключ находки не включает
номер строки, поэтому сдвиг строк не делает старый долг новым. Негодный
предыдущий отчёт — «не проверяли», код 1.

## Как читать отказ

```text
src/order.ts:1:1: —: пометка TODO без владельца и срока — скрытый долг; … (eslint:trip/todo-owner-deadline)
src/order.test.ts:4:4: TEST-001: имя теста «works» короче 12 символов … (eslint:trip/test-name-pattern)
движок eslint: не проверяли — ESLint не установлен в «frontend» …
режим: enforce; решение: ошибки; код выхода: 3; движки: …; находок: 7; ошибок: 6; предупреждений: 1; заморожено: 0; без карточки: 6; не проверено: 0
```

Строка находки: путь, строка и столбец, правило каталога (или «—», если
карточки нет), сообщение, производитель. Итоговая строка называет режим,
решение, код выхода и раздельные счётчики. Коды выхода: `0` чисто, `2` только
предупреждения, `3` ошибка, `1` не проверили.

## Четыре законных ответа на находку

1. Исправить код.
2. Уточнить конфигурацию, если правило применено не к тому: исключить
   порождаемое (`[comments].exclude`), внести термин глоссария
   (`[comments].terms`), объявить фронтенд неприменимым с причиной.
3. Повысить сигнал проектом (`[gate].raised_to_error`) — принятое обязательство.
4. Рассрочка долга: `--write-baseline --owner <кто> --until <ДД.ММ.ГГГГ>`,
   затем заменить `ДОЛГ-?` строками реестра технического долга. Заглушка
   делает рассрочку негодной; советующее в рассрочку не попадает.

Понизить сигнал настройкой нельзя.

## Порядок ввода

Новый проект начинает с режима `changed`. Наследованный проект: `observe`
(снять исходный уровень) → рассрочка со строками реестра долга → `changed` →
`enforce` на контрольной точке. Бессрочный `observe` внедрением не считается.
