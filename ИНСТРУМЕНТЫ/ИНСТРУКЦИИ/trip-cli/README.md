# trip

CLI на **.NET 10 / C# 10** для управления методологией и **политиками проверки Git-следа**.
Разворачивает инфраструктуру внутри репозитория (`trip init`) и через git hooks
(`pre-commit`, `commit-msg` и `pre-push`) ограничивает, что можно фиксировать
и отправлять. Скрипты проверок исполняются встроенным **ClearScript V8**. Есть
веб-панель мониторинга (`trip serve`) на Vue 3 / FSD.
Раскраска CLI — [Spectre.Console](https://spectreconsole.net).

Ставится в систему как глобальная команда `trip` (macOS и Windows) **через npm** —
команда попадает в npm'овский глобальный `bin`, который всегда в `PATH`, так что
никакой возни с `~/.dotnet/tools` и dotnet global tools больше нет.

При сборке проект компилируется в **self-contained single-file** бинарь (`dist/trip`),
поэтому для *запуска* готовой команды .NET уже не нужен — только для сборки.

Первое знакомство и ежедневный сценарий работы:
[руководство пользователя TRIP-CLI](./РУКОВОДСТВО_ПОЛЬЗОВАТЕЛЯ.md).

## Требования

- [.NET SDK 10](https://dotnet.microsoft.com/download) (`dotnet --version` → `10.x`) — только для сборки
- [Node.js](https://nodejs.org) ≥ 18 + npm; для браузерных тестов — ≥ 20
- [Python](https://www.python.org/) 3 с `pip` — только для API-тестов Robot Framework

Зависимости API-тестов закреплены отдельно от runtime-зависимостей:

```bash
python -m pip install -r requirements-test.txt
```

На Windows `npm run test:api` использует Git Bash из Git for Windows; если он
установлен нестандартно, путь можно передать переменной `GIT_BASH`.

Для первого запуска браузерных тестов установите dev-зависимости и Chromium:

```bash
npm install
npx playwright install chromium
```

## Установка

Из корня проекта одной командой:

```bash
npm run setup
```

Это `npm run build` (собирает автономный бинарь в `./dist`) + `npm install -g .`
(ставит команду глобально). После этого `trip` доступен из любого каталога:

```bash
trip
```

> Идемпотентно: повторный `npm run setup` пересоберёт и обновит установленную версию.

<details>
<summary>Почему двумя шагами, а не просто <code>npm install -g .</code></summary>

npm 11 по умолчанию блокирует lifecycle-скрипты пакетов (`allow-scripts`), поэтому
авто-сборка через `prepare` при `npm install -g .` не выполнится. `npm run build`
вызывается вручную и не блокируется — отсюда связка `build && install`, обёрнутая
в `npm run setup`.

Если на npm 11 всё же нужен один вызов, разрешите скрипт только этому пакету:

```bash
npm install -g . --allow-scripts=trip
```

Не добавляйте `allow-scripts=true` в `.npmrc`: актуальный npm ожидает список
одобренных пакетов, а не безусловное включение всех скриптов.
</details>

### Разработка: `npm link`

Для локальной разработки удобнее симлинк вместо копии:

```bash
npm run build   # собрать dist/
npm link        # слинковать команду trip на этот каталог
```

## Качество кода

Анализаторы .NET и правила стиля включены на сборке, а нарушения — **ошибки компиляции**:
собрать «мимо анализа» нельзя.

- `Directory.Build.props` — `AnalysisMode=Recommended`, `EnforceCodeStyleInBuild`,
  `TreatWarningsAsErrors`
  ([опции анализа](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/configuration-options))
- `.editorconfig` — строгость конкретных правил и осознанные отступления с обоснованием

Строже всего трактуются правила культуры и сравнения строк (CA1305/CA1307/CA1309/CA1310):
пути и шаблоны политик обязаны сравниваться побайтово, иначе поведение trip зависело бы от
языка системы.

## Разработка и Git-ведение

Локальные правила коммитов, журнала изменений и веток собраны в
``doc/git-workflow.md`` (`doc/git-workflow.md` — в исходном репозитории средства). Кратко:

- коммит: `тип(направление[/область]): описание`, например
  `fix(development/api): устранить потерю события (BUG-14)`;
- ветка: `тип/направление[/область]/основание-краткое-имя`, например
  `fix/development/api/bug-14-event-loss`;
- наблюдаемый результат записывается в [`CHANGELOG.md`](CHANGELOG.md) в раздел
  направления, а служебный шум туда не копируется.

`front`, `back`, `data` (`db`) и `docs` — области, а не дополнительные
направления или разделы журнала. Функциональность панели обычно относится к
`development/front`, пользовательский опыт — к `ux/front`, серверная логика —
к `development/back`, данные — к `development/data`, требования — к
`analytics/requirements`. Направление `client` означает маршрут Заказчика и
материалы демонстрации, а не браузерный frontend.

`main` хранит проверенное передаваемое состояние. Изменения проходят через короткую
рабочую ветку, проверки и запрос на слияние с линейным слиянием. Карточка контекста
заготовлена в `шаблоне запроса на слияние` (`.gitlab/merge_request_templates/Default.md` — в исходном репозитории средства).
Правила применяются к новым изменениям; существующая история не переписывается.

## Доступ через туннель

По умолчанию `trip serve` слушает на всех интерфейсах и принимает запросы с **любым
`Host`**, поэтому панель открывается через туннель (ngrok/pgrok/cloudflared) с произвольного
домена без дополнительной настройки:

```bash
trip serve --port 7777          # принимает любой Host
pgrok http 7777                 # или ngrok http 7777 — панель доступна по выданному домену
```

Чтобы запереть панель только на loopback (как было раньше), добавьте `--localhost`:

```bash
trip serve --localhost          # только http://127.0.0.1:<порт>
```

Dev-сервер Vite тоже принимает любой Host (`server.allowedHosts: true`), так что туннель
работает и в режиме разработки.

## Использование

### `trip init [путь]`

Разворачивает инфраструктуру trip в git-репозитории (по умолчанию — текущий каталог `.`):

- создаёт `trip.json` в корне — **описание политик** + манифест методологии (под VC);
- создаёт каталог `trip/` — настройки и js-скрипты проверок/валидации (под VC);
- записывает `trip/toolchain.json` — какой версией trip поставлены эти скрипты
  (по нему `trip update` отличает устаревание от правки проекта);
- создаёт `.trip/` (state) и прописывает его в `.gitignore` — **единственная** игнорируемая папка;
- создаёт `.trip/policies.json` — хранит только имя активной политики;
- ставит `pre-commit` hook (правила файлов, имя ветки и структура changelog),
  `commit-msg` hook (валидация сообщения) и `pre-push` hook (ветка и обязательное
  изменение changelog, полнота legacy-пакета при настроенном `changeSet` либо
  нативный FREEZE выбранного WorkPackage v2).

Идемпотентно: повторный запуск не затирает существующие `trip.json` / `.trip/policies.json` /
файлы в `trip/`, обновляет hooks и игнор. Активную политику можно задать сразу:
`trip init --policy generic`.

Если `trip.json` был создан старой версией, `init` не дописывает в него новые
секции `branch` и `changelog`: их нужно осознанно добавить в выбранные политики
по [модели политик](./МОДЕЛЬ_ПОЛИТИК.md).

### `trip update [путь] [--check] [--force]`

Приводит поставляемые артефакты репозитория к версии установленного trip:

- переписывает валидаторы `trip/*.js`, отставшие от версии инструмента;
- переустанавливает управляемые hooks там, где trip их уже ставил;
- пишет происхождение в `trip/toolchain.json` (под VC) — версию trip и отпечаток
  каждого артефакта;
- называет выключенные правила `trip.json`, но **не досочиняет** их: карта зон
  описывает конкретный репозиторий.

Проверки выполняет не сам trip, а js-валидаторы из `trip/`. Отстав от версии
инструмента, они не падают — они молча не выполняют того, чего ещё не знают.
Поэтому обновление отделено от установки и имеет проверочный режим.

Валидатор, содержимое которого trip никогда не поставлял, считается правкой
проекта: без `--force` он не перезаписывается. Отличить его от устаревшего
позволяет каталог поставлявшихся редакций внутри бинарника.

`--check` ничего не пишет и отвечает кодом возврата: отсутствующий или
устаревший артефакт — код 1, правка проекта — предупреждение при коде 0. Хуки
влияют на код возврата только там, где trip их ставил: в чистом клоне их нет
по построению. Годится для конвейера — в `policy-gate` он и стоит.

### `trip uninstall [--purge]`

Снимает из `pre-commit`, `commit-msg` и `pre-push` **только управляемые trip
секции** (между маркерами `>>> trip … (managed) >>>`); чужое содержимое
сохраняется, пустой хук удаляется. `--purge` дополнительно удаляет локальный
state `.trip/`. `trip.json` и `trip/` (под VC) не трогаются.

### `trip serve [--port <n>]`

Открывает веб-панель мониторинга по адресу `http://127.0.0.1:7777` (порт
настраивается). По умолчанию сервер слушает внешние интерфейсы для работы через
туннель; для локального доступа используйте `trip serve --localhost`. См. раздел
[Панель мониторинга](#панель-мониторинга-trip-serve).

### `trip policy [имя]`

Без аргумента — показывает активную политику и список (из `trip.json`). С аргументом — переключает
(пишет `active` в `.trip/policies.json`):

```bash
trip policy methodology
```

### `trip work`

Локальный контекст одного логического результата и неизменяемых свидетельств.
Legacy-путь v1 сохранён:

```bash
trip work start CS-MIGRATION-42 --accountable lead
trip work role developer
trip work import artifacts/db-inspection.json
trip work show
trip work list
```

Нативный путь v2 начинается с импорта `WorkPackage`; импорт пакета сразу
выбирает его точную ревизию:

```bash
trip work import artifacts/work-package.json
trip work import artifacts/db-inspection-v2.json
trip work import artifacts/review-record.json
trip work import artifacts/decision-record.json
trip work import artifacts/policy-set.json
trip work use WP-MIGRATION-42 --fingerprint sha256:…
trip work freeze --json
trip work contracts
trip work show
trip work list
```

`changeSetId` имеет вид `CS-...` и состоит из прописных `A-Z`, цифр и дефисов.
`--accountable` принимает один из канонических кодов функциональных ролей:
`lead`, `analyst`, `architect`, `developer`, `qa`, `customer`,
`methodologist`. «Рецензент» — действие/профиль проверки, а не отдельная
функциональная роль. `trip work role` меняет только локальную рабочую
перспективу и не выдаёт полномочий. Профиль рецензирования выводится из
направления ветки: например, `development` → `trip-review-development`;
для `service` профиль не назначается.

Trip не запускает DB/Backend/Frontend Inspector. В v1 он принимает
`trip.inspection/v1`, сверяет `projectId`/`changeSetId` и привязывает отчёт к
текущему Git `HEAD`; данные лежат в `.trip/work-package.json` и
`.trip/inspections/`.

В v2 Trip сам проверяет embedded-схемы и семантику контрактов
`trip.work-package/v2`, `trip.inspection-request/v2`, `trip.inspection/v2`,
`trip.review-record/v2`, `trip.decision-record/v2` и `trip.policy-set/v2`.
Исходные байты сохраняются по SHA-256 в `.trip/contracts-v2/`, метаданные —
отдельно, выбранный fingerprint — в `.trip/work-mode.json`. Повторный stable
ID не может обозначать иное содержимое; WorkPackage допускает несколько
явно адресуемых ревизий. Подмена схемы или артефакта и неизвестная
major-версия дают fail-closed отказ без downcast.

`trip work freeze` сверяет пакет с доверенными текущими Git `HEAD` и UTC:
selection и freshness инспекций, source identity, подтверждённые checks и
evidence, зависимости, ReviewRecord, DecisionRecord и точного ответственного,
PolicySet, gates, состояния миграций, rehearsal/recovery и separation of
duties. `--json` выдаёт стабильные `code`, `path`, `message` для CI.
Исполнителем инспекции может быть человек, ИИ-агент, гибрид или
детерминированный движок; автоматический verdict остаётся свидетельством, а
человеческие рецензия и решение представлены отдельными документами.

### `trip trace <аргументы>`

Оркестрационный вход в отдельно устанавливаемый `trip-trace`:

```bash
trip trace scan --mode change --base <sha> --head <sha>
trip trace graph query --snapshot latest --node requirement:R-001
```

`trip-cli` не содержит второго сканера: он находит `trip-trace` через `PATH`
или `TRIP_TRACE_EXECUTABLE`, передаёт аргументы как есть и возвращает исходный
код завершения. Поэтому отчёт CLI, HTTP-сервиса и потребителей строится одним
алгоритмом.

### `trip verify`

Движок проверок вызывается из hooks и доступен вручную:

```bash
trip verify --staged --branch --changelog
trip verify --message <файл>
trip verify --branch --changelog --work-package --base main --require-changelog
trip verify --commits --base main
```

- `--staged` применяет правила файлов и lock-зоны к индексу;
- `--message <файл>` проверяет сообщение коммита;
- `--branch` проверяет имя текущей ветки;
- `--changelog` проверяет журнал по пути активной политики;
- `--base <ref>` задаёт основание сравнения для
  `--require-changelog`, по умолчанию `main`;
- `--require-changelog` требует изменение журнала на уровне ветки;
- `--work-package` проверяет legacy-группы файлов и свежие отчёты либо полный
  нативный FREEZE активного WorkPackage v2;
- `--commits` проверяет состав каждого коммита диапазона `merge-base..HEAD`:
  зоны, объявленное направление и бюджет среза.

`pre-commit` запускает первую команду, `commit-msg` — вторую, а `pre-push` —
предпоследнюю с `${TRIP_BASE_REF:-main}` в качестве основания; `--commits`
предназначен для гейта запроса на слияние, где проверяется история, уже
созданная в обход локальных hooks. В режиме
`--require-changelog` и при проверке рабочего пакета используются доверенные
данные Git, поэтому незаписанная рабочая копия не может замаскировать
отправляемое состояние. В legacy-режиме без `changeSet` проверка пакета ничего
не ограничивает; выбранный WorkPackage v2 всегда проверяется независимо от
этой секции политики. Ненулевой код возврата отменяет соответствующую
операцию Git.

### Состав коммита

Необязательная секция `commit` активной политики описывает, что может лежать в
одном коммите: зоны ответственности с допустимыми направлениями, несмешиваемые
сочетания зон и бюджет среза. Проверка перекрёстная — она сопоставляет
объявленное в сообщении направление с фактическим составом индекса, чего не
может ни проверка путей (она не видит сообщения), ни валидатор сообщения (он не
видит индекса). Модель данных и границы правила описаны в
[doc/policies-model.md](./МОДЕЛЬ_ПОЛИТИК.md).

## Политики проверок Git

Политика — именованный набор **проверок** и **правил** в `trip.json`; активная выбирается в
`.trip/policies.json`. Полная схема — в [`doc/policies-model.md`](./МОДЕЛЬ_ПОЛИТИК.md).

- **Проверка** — `wildcard` (`*.cs`), `regexp` или `script` (js-скрипт в `trip/`).
- **Правила** (`rules`) по операциям `add` / `modify` / `delete` / `rename` — наборы `allow` / `deny`.
- **Списки блокировок** (`lockMode` + `lockZones`) — пути, ограничивающие изменения при активной
  политике: `denylist` — перечисленное запрещено менять, `allowlist` — менять можно только
  перечисленное. В режиме `serve` защищаемые файлы дополнительно удерживаются на диске
  открытыми на чтение с запретом записи.
- **Валидатор сообщения** (`message.validator`) — js-скрипт, проверяющий структуру сообщения.
  По умолчанию `trip init` кладёт `trip/msg.js` с проверкой по
  [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/),
  согласованной с `соглашением о коммитах TRIP v1.5` (`doc/git-workflow.md#коммиты` — в исходном репозитории средства).
  Формат — `тип(направление[/область])[!]: описание`: один из 12 типов и обязательное
  направление `analytics`, `development`, `qa`, `ux`, `client` или `service`.
  Заголовок — до 100 символов, описание — на русском. Для содержательного изменения
  нужна ссылка на идентификатор трассируемости (`R`, `DR`, `US`, `UC`, `Q`, `AR`, `ADR`,
  `AC`, `TC`, `BUG`, `ФЗ`). Требования `trip-cli` используют единое семейство `R-*`;
  тип `FR`/`NFR` хранится в реестре, а не кодируется в идентификаторе. Без ссылки
  разрешены только `chore(service)` и `revert(<направление>)`.
  Обе преднастроенные политики на него ссылаются.
  Скрипт может вернуть строку — она покажется автору коммита как причина отказа.
- **Происхождение изменения** (`message.origin`) — необязательная секция,
  требующая, чтобы последний абзац сообщения назвал, кто вёл изменение:
  `Assisted-by: <средство>` либо `Assisted-by: none`, а для названного средства
  ещё `Model:` и `Session:`. Необязательный `Prompt-SHA256:` — якорь реплики
  (64 строчных шестнадцатеричных знака): git несёт обязательство, а открытый
  текст живёт во внешнем леджере с разграниченным доступом. Словарь средств
  объявляет `origin.agents`, обязательность якоря — `origin.requireAnchor`.
  Отсутствие секции сохраняет прежнее поведение. Проверяются наличие и форма:
  трейлер — заявление автора, а не свидетельство инструмента.
- **Валидатор ветки** (`branch.validator`) — `trip/branch.js`, проверяющий
  грамматику обычных и особых имён, допустимые направления, каноническое
  основание и предел 120 символов. `ФЗ-*` в имени нормализуется до `fz-*`;
  для `chore/service` без ID разрешены основания `branch`, `workflow`,
  `repository`, `dependencies`, `tooling` и `release`.
- **Валидатор журнала** (`changelog.validator`) — `trip/changelog.js`;
  `changelog.path` задаёт файл, а `changelog.baseRef` — базовый ref для
  сравнения результата ветки. Преднастроенные значения:
  `CHANGELOG.md` и `main`.
- **Рабочий пакет** (`changeSet`) — необязательные именованные группы путей и
  условия `whenAny → requireGroups + requireInspections`. Для отчёта можно
  потребовать конкретные `observe|analyze` и `current|result|changed`;
  сокращённое `requireInspectors` не ограничивает эти оси. Правила проверяются
  на результате всей ветки, поэтому draft-коммиты остаются дешёвыми, а
  `pre-push` блокирует доказуемо неполную legacy-поставку. Нативные правила v2
  приходят как версионированный `PolicySet`, а не расширяют эту секцию.

`trip init` заполняет `trip.json` двумя зеркальными политиками вокруг методологии
(`trip.json` + `trip/**`):

| Политика        | Режим        | Что можно менять                            |
| --------------- | ------------ | ------------------------------------------- |
| `generic`       | запретительный | всё, **кроме** файлов методологии          |
| `policies-only` | разрешительный | **только** файлы методологии               |

> Скрипты (`type: script`) исполняются **in-process встроенным ClearScript V8** — внешний
> Node.js в рантайме не нужен. Контракт скриптов — completion value как boolean (см.
> [`doc/policies-model.md`](./МОДЕЛЬ_ПОЛИТИК.md)). Описание политик (`trip.json`) и скрипты
> (`trip/`) отслеживаются git и едут с репозиторием; локальный state (`.trip/`) — нет, поэтому
> после `git clone` нужно один раз выполнить `trip init` (поднимет hooks и state).

## Панель мониторинга (`trip serve`)

`trip serve` поднимает встроенный веб-сервер на порту 7777 по умолчанию с
SPA-панелью (Vue 3 / TypeScript / Vite, Feature-Sliced Design, в стиле проекта
eyeb). Без `--localhost` сервер слушает внешние интерфейсы для работы через
туннель. Панель встроена прямо в бинарь. Возможности:

- **Файловая структура** проекта (с учётом `.gitignore`) и **изменения** (git status + diff);
- **Политики** — редактирование `trip.json` через Monaco с проверкой правил и wildcard **на месте**;
- **Журнал попыток** коммита/валидации — `trip verify` шлёт события в запущенный serve;
- **UI/UX-наблюдения** — встроенный на время локальной разработки Reporter из
  TRIP Bug Loop; собственных отчётов, снимков и второго реестра в `trip serve` нет.

```bash
trip serve            # http://127.0.0.1:7777
trip serve --port 7878
```

Кнопка Reporter входит в локальную сборку панели и отображается без отдельного
сервиса. Для регистрации, трассировки и анализа она ожидает TRIP Bug Loop на
`http://127.0.0.1:7788`. Первичная подготовка уже описана версионируемым
`trip-bug-loop.json`; запуск выполняется из соседнего репозитория одной командой:

```powershell
cd C:\projects\trip-bug-loop
dotnet run --project src/Trip.BugLoop -- --config C:\projects\trip-cli\trip-bug-loop.json
```

Если TRIP Bug Loop не запущен, кнопка остаётся на месте, а остальные функции
панели работают как обычно. Поставляемый снимок Reporter обновляется командой
`npm run sync:bug-loop-reporter`; её источник — соседний репозиторий, а не
редактируемая копия в `trip-cli`.
Reporter сразу выбирает требования из профиля текущего маршрута: перед регистрацией
достаточно снять неприменимые связи. Важность, стадия и выпуск уточняются при триаже,
поэтому технического блока с этими полями в форме наблюдения нет.
Старый каталог `.trip/issues/` новым контуром не читается и остаётся только для
ручного архива или контролируемой миграции.

При старте пишется `.trip/serve.json` (pid, port). `trip verify` проверяет наличие этого файла
и, если serve запущен, шлёт событие журнала (throttle 5 c, короткий таймаут — если serve нет,
коммит не тормозится).

Разработка фронта: `cd frontend && npm run dev` (dev-сервер проксирует `/api` на запущенный
`trip serve`).

## npm-скрипты

| Команда             | Что делает                                                       |
| ------------------- | ---------------------------------------------------------------- |
| `npm run build`     | собирает фронт (`frontend/dist`) + self-contained single-file бинарь в `./dist` |
| `npm run setup`     | `build` + `npm install -g .` — ставит `trip` глобально           |
| `npm run unsetup`   | удаляет `trip` из системы (`npm uninstall -g trip`)              |
| `npm test`          | xUnit-тесты движка и семантики правил                            |
| `npm run test:dist` | проверяет импорт, FREEZE и freshness v2 в собранном self-contained бинарнике |
| `npm run test:api`  | Robot Framework-сценарии HTTP API; на Windows Bash ищет Node-обёртка |
| `npm run test:ui`   | запускает собранную веб-панель на временном репозитории и проверяет её в Chromium |
| `npm run clean`     | удаляет `./dist`                                                  |

Команда `trip` регистрируется через поле `bin` в `package.json`: npm кладёт в свой
глобальный `bin` (гарантированно в `PATH`) шим на `cli/trip.js`, а тот запускает
автономный бинарь `dist/trip`. Один кросс-платформенный способ для macOS и Windows,
без зависимости от dotnet global tools и ручной правки `PATH`.
