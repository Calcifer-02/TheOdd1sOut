# Модель политик trip

Документ фиксирует схему данных и семантику политик. Требования — в `tz-v1.md` (`tz-v1.md` — в исходном репозитории средства).

## Где что хранится

| Путь                      | В git | Содержит                                                        |
| ------------------------- | :---: | -------------------------------------------------------------- |
| `trip.json`               |  да   | **описание политик** + манифест методологии                    |
| `trip/`                   |  да   | файлы настроек инструмента, в т.ч. **js-скрипты** проверок и валидации |
| `.trip/`                  |  нет  | локальный **state** инструмента (единственная игнорируемая папка) |
| `.trip/policies.json`     |  нет  | **только** активную политику (`{ "active": "<имя>" }`)         |
| `.trip/work-package.json` |  нет  | legacy v1: активный `projectId`/`changeSetId`, роль `A` и рабочая перспектива |
| `.trip/inspections/`      |  нет  | legacy v1: неизменяемые отчёты и отдельные привязки к Git `HEAD` |
| `.trip/work-mode.json`    |  нет  | режим v1/v2 и точный fingerprint активной ревизии WorkPackage v2 |
| `.trip/contracts-v2/`     |  нет  | v2: исходные документы по SHA-256 и отдельные индексные метаданные |

`.gitignore` (фрагмент, добавляется `trip init`):

```gitignore
# trip state
.trip/
```

## `trip.json` — определения политик

```jsonc
{
  "name": "my-project",
  "version": "0.1.0",

  // Основная (защищённая) ветка репозитория. Умолчание — "main".
  // Имя используется валидатором ветки как защищённое и служит основанием
  // сравнения по умолчанию. Инфраструктура может предписывать своё имя —
  // например "dev/1.0"; тогда оно объявляется здесь, один раз на репозиторий.
  "trunk": "main",

  "methodology": { "description": "Файл методологии проекта. Управляется trip." },

  "policies": {
    "<имя-политики>": {
      "title": "Человекочитаемое название",
      "description": "Что политика делает",

      // Правила по операциям над файлами в индексе.
      "rules": {
        "add":    { "allow": [ <check>, ... ], "deny": [ <check>, ... ] },
        "modify": { "allow": [ <check>, ... ], "deny": [ <check>, ... ] },
        "delete": { "allow": [ <check>, ... ], "deny": [ <check>, ... ] },
        "rename": { "allow": [ <check>, ... ], "deny": [ <check>, ... ] }
      },

      // Режим списка блокировок: "denylist" (по умолчанию) или "allowlist".
      "lockMode": "denylist",
      // Пути списка блокировок (трактуются согласно lockMode).
      "lockZones": [ <check>, ... ],

      // Валидаторы Git-следа (JavaScript), пути validator относительно trip/.
      "message": { "validator": "msg.js" },
      "branch": { "validator": "branch.js" },
      "changelog": {
        "validator": "changelog.js",
        "path": "CHANGELOG.md"
        // "baseRef": "release/next" — переопределение основной ветки
        // для этой проверки; без поля берётся "trunk" манифеста.
      },

      // Необязательная проверка полноты результата всей ветки.
      "changeSet": {
        "contractVersion": "trip.inspection/v1",
        "groups": [
          {
            "name": "database",
            "paths": [
              { "type": "wildcard", "pattern": "db/**" }
            ]
          },
          {
            "name": "database-tests",
            "paths": [
              { "type": "wildcard", "pattern": "tests/db/**" }
            ]
          }
        ],
        "requirements": [
          {
            "name": "database-evidence",
            "whenAny": [ "database" ],
            "requireGroups": [ "database-tests" ],
            "requireInspections": [
              {
                "inspector": "db",
                "activities": [ "analyze" ],
                "views": [ "changed" ]
              }
            ]
          }
        ]
      },

      // Необязательная проверка состава одного коммита.
      "commit": {
        "mode": "block",
        "exempt": [ { "type": "wildcard", "pattern": "CHANGELOG.md" } ],
        "zones": [
          {
            "name": "data",
            "title": "данные и миграции",
            "paths": [ { "type": "wildcard", "pattern": "db/**" } ],
            "directions": [ "development" ]
          },
          {
            "name": "ui",
            "title": "интерфейс",
            "paths": [ { "type": "wildcard", "pattern": "frontend/**" } ],
            "directions": [ "ux", "development" ]
          }
        ],
        "separate": [
          {
            "name": "ui-data",
            "zones": [ "ui", "data" ],
            "reason": "интерфейс и схема данных откатываются порознь"
          }
        ],
        "budget": { "maxFiles": 25, "maxLines": 1500 }
      }
    }
  }
}
```

Все поля политики опциональны: отсутствующий `rules`, `lockZones`, `message`,
`branch`, `changelog`, `changeSet` или `commit` означает, что соответствующая проверка не
применяется. Это не отключает FREEZE выбранного WorkPackage v2: его правила
приходят из самого пакета и импортированных `PolicySet`.

## Основная ветка (`trunk`)

Имя основной (защищённой) ветки репозитория. Поле корневое: ветка — свойство
репозитория, а не политики, и от переключения политики не меняется. Без поля
берётся `main`.

Имя используется в двух местах:

- валидатор ветки получает его глобальной переменной `trunk` и объявляет
  защищённой именно её — прямой коммит туда отклоняется с названным именем;
- проверки, судящие результат ветки (`--changelog`, `--work-package`,
  `--fixups`, `--messages`, маршрут ветки, барьер трассы), берут его основанием
  сравнения, когда основание не названо иначе.

Старшинство: флаг `--base <ref>` старше объявления проверки
(`changelog.baseRef`, `changeSet.baseRef`), объявление проверки старше `trunk`.
Управляемый `pre-push` передаёт основание пустым (`--base "$TRIP_BASE_REF"`):
назвать основную ветку — дело trip, читающего `trip.json`, а не сочинённого
однажды файла хука, который после смены настройки устаревал бы молча. Пустое
значение `--base` в порту `trip trace` означает то же.

Репозиторий, где инфраструктура предписывает своё имя (например `dev/1.0`),
объявляет его здесь один раз. Прежде имя было вбито в средство, и такой
репозиторий получал неправду: защищённой считалась отсутствующая `main`, прямой
коммит в настоящую основную ветку отклонялся как рабочая — «неизвестный тип
„dev“», — а сравнение либо не находило базу, либо уходило к одноимённой
устаревшей ветке, если та сохранилась. Последнее хуже отказа: проверка шла по
чужому основанию и отчитывалась успехом.

## Проверка (`<check>`)

Три типа. Все шаблоны сопоставляются с **git-относительным путём** файла (forward slash).

```jsonc
{ "type": "wildcard", "pattern": "*.cs" }              // glob; поддержка ** для вложенности
{ "type": "regexp",   "pattern": "^src/.*\\.cs$" }     // регулярное выражение
{ "type": "script",   "path": "checks/check.js" }      // путь относительно trip/
```

## Семантика правил (`rules`)

Для каждого файла в индексе определяется операция (`add` | `modify` | `delete` | `rename`)
по данным git, и применяется соответствующий набор:

1. Набор для операции **отсутствует** → операция **не ограничена** (файл проходит).
2. Набор **присутствует**:
   - файл допускается, только если совпал **хотя бы с одной** проверкой из `allow`;
   - если совпал с любой проверкой из `deny` — отклоняется, даже будучи в `allow`
     (`deny` приоритетнее `allow`);
   - `allow: []` (пустой) → операция **запрещена полностью** (ни один файл не совпадёт).

Итог: файл нарушает политику, если для его операции набор задан и файл не прошёл allow,
либо попал в deny. Любое нарушение → `pre-commit` отменяет коммит.

## Списки блокировок (`lockMode` + `lockZones`)

`lockZones` — список проверок; как он трактуется, задаёт `lockMode`:

| `lockMode`  | Смысл                                                                 |
| ----------- | --------------------------------------------------------------------- |
| `denylist`  | (по умолчанию) перечисленное **запрещено** менять, остальное свободно  |
| `allowlist` | менять разрешено **только** перечисленное, всё остальное блокируется   |

Действует в двух местах:

- **Коммит** — нарушение фиксирует `pre-commit`: при `denylist` — если staged-путь попал в
  список; при `allowlist` — если staged-путь в список НЕ попал.
- **Файлы на диске** — режим `serve` при активации политики открывает защищаемые файлы
  на чтение с запретом записи (см. «Блокировка файлов при активации»).

## Валидация сообщения (`message.validator`)

Путь (относительно `trip/`) к JavaScript-скрипту. Применяется в `commit-msg` hook.

## Происхождение изменения (`message.origin`)

Необязательная секция. Объявляет, что сообщение обязано назвать, кто вёл
изменение, трейлерами последнего абзаца: `Assisted-by`, `Model`, `Session` и
якорь `Prompt-SHA256`.

| Поле | Значение |
|---|---|
| `mode` | `off` (по умолчанию) либо `required` |
| `agents` | словарь допустимых средств; пусто — принимается любой корректный слаг |
| `requireAnchor` | требовать `Prompt-SHA256`; по умолчанию `false` |

```json
"message": {
  "validator": "msg.js",
  "registry": ["doc/tz-v1.md"],
  "origin": {
    "mode": "required",
    "agents": ["claude-code", "codex", "cursor"],
    "requireAnchor": false
  }
}
```

Отсутствие секции сохраняет прежнее поведение: правило вводит проект, а не
версия инструмента. Иначе обновление валидатора заблокировало бы коммиты в
репозиториях, которые о правиле не решали.

Неизвестное значение `mode` и неразобранная секция — отказ, а не разрешение:
поле, заведённое ради запрета, не снимает запрет своей непонятностью.

Проверяются наличие и форма. Правдивость заявления не проверяется: текст
сообщения подделывается, и доказательную силу даёт якорь вместе с внешним
леджером, а не трейлер сам по себе. Подробности соглашения —
в `git-workflow.md` (`git-workflow.md#происхождение-изменения` — в исходном репозитории средства).

Границу трейлерного блока задаёт git, а не проверка: последний абзац целиком,
и только если он состоит из строк «Ключ: значение». Проверка повторяет это
правило буквально — пропущенное ею сообщение обязано читаться
`git log --format=%(trailers)`, иначе указатель есть на вид и отсутствует для
сборщика.

## Валидация ветки (`branch.validator`)

Путь (относительно `trip/`) к JavaScript-скрипту, который проверяет имя текущей
ветки. Применяется командами `trip verify --branch`, управляемым `pre-commit`
hook и перед отправкой в удалённый репозиторий.

Скрипту доступны глобальные переменные `branch` (имя текущей ветки) и `trunk`
(имя основной ветки из `trip.json`), а также объект `trip` с теми же полями.
Валидатор, написанный до появления `trunk`, переменную не читает и работает
по-прежнему.

### Маршрут ветки (`branch.route`)

Отвечает на вопрос, на который не отвечает ни валидатор имени (он не видит
коммитов), ни карта зон (она не видит имени ветки): **делалась ли в ветке работа
того направления, которое ветка объявила**.

| Поле | Значение |
|---|---|
| `mode` | `block` (по умолчанию) — маршрут без подтверждения отклоняет ветку; `advisory` — сообщается, но не блокирует |

Направление берётся вторым сегментом имени ветки и сравнивается с множеством
направлений, объявленных коммитами диапазона `merge-base..HEAD`. Достаточно
одного совпадения: рядом с работой направления законны и `test(qa/...)`, и
`chore(service/...)`, и требовать совпадения каждого коммита значило бы либо
дробить ветку ради отчётности, либо подталкивать автора объявить тест
разработкой.

Проверяется на гейте слияния, вместе с `--commits`: правило судит законченную
ветку, и отказ в середине работы был бы отказом за незаконченность. Коммиты,
направления не объявляющие, — слияние, откат, заплатка автосжатия — в счёт не
идут; диапазон без единого объявления не судится. Имя без известного направления
оставлено проверке имени: одно нарушение не сообщается дважды.

Цена неподтверждённого маршрута не в отчётности: направление имени выбирает
профиль рецензирования, и ветка уезжает к рецензенту направления, работы
которого в ней нет.

## Валидация журнала (`changelog`)

| Поле | Значение |
|---|---|
| `validator` | путь к JavaScript-валидатору относительно `trip/` |
| `path` | git-относительный путь журнала; по умолчанию `CHANGELOG.md` |
| `baseRef` | переопределение основной ветки для этой проверки; без поля — `trunk` манифеста, а без него `main` |

`trip verify --changelog` проверяет текущий снимок журнала.
`--require-changelog` требует изменение журнала в проверяемой ветке
относительно merge-base, а `--base <ref>` переопределяет `baseRef` для этого
сравнения.

## Legacy-рабочий пакет v1 (`changeSet`)

`changeSetId` обозначает один логический результат ветки независимо от числа
промежуточных коммитов и соответствует `^CS-[A-Z0-9-]{4,}$`. Trip проверяет не
порядок этих коммитов, а совокупный diff `merge-base..HEAD`.

| Поле | Значение |
|---|---|
| `baseRef` | переопределение основной ветки для рабочего пакета; без поля — `trunk` манифеста, а без него `main` |
| `contractVersion` | версия legacy-конверта инспекторов; эта секция принимает только `trip.inspection/v1` |
| `groups[].name` | уникальное имя логической группы изменений |
| `groups[].paths` | проверки путей, определяющие присутствие группы в результате ветки |
| `requirements[].whenAny` | правило включается, если присутствует хотя бы одна из перечисленных групп |
| `requirements[].requireGroups` | все перечисленные группы должны присутствовать |
| `requirements[].requireInspections` | требуемые инспекторы и допустимые `activities`/`views`; нужен завершённый отчёт текущего `HEAD` |
| `requirements[].requireInspectors` | сокращённая совместимая форма, если activity/view не ограничиваются |

Допустимые инспекторы: `db`, `backend`, `frontend`. Неизвестная группа,
инспектор, деятельность (`observe`/`analyze`), представление
(`current`/`result`/`changed`) или некорректная конфигурация отклоняют
проверку. Отсутствующий `changeSet` сохраняет прежнее поведение legacy-режима.
Указание `contractVersion: trip.inspection/v2` не включает нативный режим и
не разрешает обрезать v2 до полей v1: режим выбирается импортом/выбором
WorkPackage v2.

Команда `trip verify --work-package [--base <ref>]`:

1. читает только уже созданный `HEAD`, а не незаписанную рабочую копию;
2. агрегирует изменения всей ветки;
3. проверяет обязательные сопутствующие группы;
4. принимает только отчёт с теми же `projectId`, `changeSetId` и версией
   контракта, импортированный для точного текущего `HEAD`;
5. считает свидетельство готовым только при `run.status = completed`.

`summary.verdict` отчёта показывается человеку, но не превращается Trip в
решение о приёмке: автоматический `pass` и человеческое `approved` — разные
факты. Управляемый `pre-push` запускает эту проверку вместе с проверками ветки
и changelog. Тяжёлые инспекторы в hook не запускаются.

## Состав коммита (`commit`)

Секция отвечает на вопрос, на который поодиночке не отвечают ни проверка путей
(она не знает объявленного направления), ни валидатор сообщения (он не знает
состава индекса): **соответствует ли содержимое коммита тому, чем коммит себя
объявил**.

| Поле | Значение |
|---|---|
| `mode` | `block` (по умолчанию) — нарушение отклоняет коммит; `advisory` — сообщается, но не блокирует |
| `zones` | именованные дома артефактов: `paths` (список `<check>`) и `directions` — направления, которым дом принадлежит |
| `separate` | сочетания зон, недопустимые в одном коммите: `zones` и `reason` |
| `budget` | `maxFiles` и `maxLines`; значение `0` или отсутствие поля снимают предел по этой оси |
| `exempt` | пути-попутчики (журнал изменений, файлы блокировок): не относятся к зонам и не расходуют бюджет |

Три правила и три момента применения:

| Правило | Когда проверяется | Что нужно знать |
|---|---|---|
| несмешение зон | `trip verify --staged` (`pre-commit`) | только состав индекса |
| бюджет среза | `trip verify --staged` (`pre-commit`) | только состав индекса |
| направление ↔ зоны | `trip verify --message` (`commit-msg`) | состав индекса и заголовок сообщения |

Разделение по стадиям задано git, а не вкусом: состав индекса известен до того,
как написано сообщение, а объявленное направление — только после. Готовый
коммит проверяется всеми тремя правилами сразу — `trip verify --commits`.

Границы правила выбраны так, чтобы оно не создавало ложных отказов:

- путь, не попавший ни в одну зону, не нарушает ничего;
- зона без `directions` в правиле направления не участвует — только в
  несмешении;
- файл, попавший в несколько зон, проходит, если направление допускает хотя бы
  одна из них;
- переименование учитывается по обоим путям: файл, уехавший из зоны в зону,
  меняет обе;
- заголовок, который не разобрался, и сообщения, сформированные git (слияние,
  откат, `fixup!`), правило направления не включают: грамматику сообщения судит
  `message.validator`, и второй грамматики здесь нет;
- двоичный файл входит в бюджет как файл, но не как строки — их у него нет.

`git commit --amend` виден правилу лишь частично: в индексе на стадии
`commit-msg` лежит только досылаемая часть, а не итоговый коммит целиком. Полный
состав такого коммита проверяет `trip verify --commits` в гейте.

Ссылка на несуществующую зону в `separate`, повтор имени зоны и зона без `paths`
трактуются fail-closed: это ошибка конфигурации, а не повод молча отключить
разделение.

## Нативный contract pack и FREEZE v2

Нативный режим не является расширением объекта политики `changeSet`. Trip
содержит собственные JSON Schema Draft 2020-12 и semantic validator для
публичных контрактов:

| `contractVersion` | Назначение | Stable identity |
|---|---|---|
| `trip.work-package/v2` | пакет, slices, sources, требуемые инспекции, gates и FREEZE selection | `id`; разрешены разные ревизии по fingerprint |
| `trip.inspection-request/v2` | запрос инспектору | `id` |
| `trip.inspection/v2` | опубликованный InspectionEnvelope | `run.id` |
| `trip.review-record/v2` | неизменяемая человеческая рецензия | `id` |
| `trip.decision-record/v2` | неизменяемое человеческое решение gate | `id` |
| `trip.policy-set/v2` | версионированные правила FREEZE | `id@version` |

`trip work import <document.json>` выполняет schema и semantic validation до
записи. Исходные UTF-8 байты кладутся в
`.trip/contracts-v2/<kind>/<sha256>.json`, индекс — в соседний
`*.meta.json`. Хеши embedded-схем закреплены в коде и проверяются до чтения
пользовательского документа (`trip work contracts`). Для всех документов,
кроме WorkPackage, повторный stable identity с иными байтами является
конфликтом. WorkPackage допускает историю ревизий; импорт автоматически
выбирает новую ревизию, а
`trip work use <id> [--fingerprint <sha256:…>]` выбирает ранее импортированную
точно.

Режим и fingerprint выбранного пакета хранятся в `.trip/work-mode.json`.
Повреждение state, индекса, исходного файла, его SHA-256 либо подмена
embedded-схемы дают fail-closed отказ. Неизвестная major-версия не
понижается до известной.

`trip work freeze [--json]` и `trip verify --work-package` собирают контекст
только из импортированных документов и добавляют доверенные значения текущих
Git `HEAD` и UTC. Нативная проверка требует:

- точное совпадение candidate, inspected и subject revision с `HEAD`;
- явную FREEZE selection без дубликатов, пропусков и посторонних stable ID;
- совпадение project/changeSet, source identity и fingerprints;
- `completed` у выбранных инспекций, выполненные зависимости и пригодные
  summaries;
- все обязательные activities/views/checks, причём checks и evidence должны
  быть `passed+confirmed` с человеческим подтверждением;
- ReviewRecord нужного профиля и направления, `accept`, `confirmed`,
  трассировку выбранных run и причинную допустимость времени;
- DecisionRecord с `approved`, точным gate/decision zone/accountable
  principal, subject revision, evidence refs и действующим сроком;
- активные `PolicySet` по точным ссылкам, применимые error-правила,
  обязательные inspections/checks/evidence kinds/gate zones;
- закрытые gates, корректные состояния миграций, rehearsal и recovery
  evidence, а при требовании политики — separation of duties.

`--json` возвращает `valid`, идентификатор и fingerprint пакета, доверенные
HEAD/время, число документов и массив стабильных диагностик
`{ code, path, message }`. При активном пакете v2 `--base` и legacy-секция
`changeSet` не ослабляют FREEZE: проверяется именно выбранный пакет и текущий
HEAD.

### Независимые инструменты и трассируемость

Trip, DB Inspector, Backend Inspector и Frontend Inspector не вызывают друг
друга. Инспектор получает baseline/candidate своим способом и публикует
неизменяемый `InspectionEnvelope`; Trip принимает файл командой
`trip work import <document.json>`. Связь обеспечивают только:

- `contractVersion`;
- `projectId` и `changeSetId`;
- stable ID (`run.id` для InspectionEnvelope);
- отпечаток исходного JSON;
- revision/`HEAD`.

Исходный документ не переписывается. В v1 человеческое решение gate остаётся
внешним состоянием; в v2 рецензия и решение представлены отдельными
неизменяемыми ReviewRecord и DecisionRecord. Gate внутри InspectionEnvelope
остаётся снимком, а не правом инспектора принять поставку. Так сохраняются
независимость инструментов и аудит решения.

### Роли, действия и представления

В TRIP остаётся закрытый перечень функциональных ролей:

`lead`, `analyst`, `architect`, `developer`, `qa`, `customer`,
`methodologist`.

«Рецензент» не добавляется восьмой функциональной ролью. Рецензирование — это
действие и профиль проверки: рецензировать качество может QA, архитектуру —
Архитектор, контрольную точку — Ведущий. Для каждого результата роль `A`
определяется его зоной решения по RACI.

Профиль выводится из стратегического направления, а не из папки:

| Направление | Профиль |
|---|---|
| `analytics` | `trip-review-analytics` |
| `development` | `trip-review-development` |
| `qa` | `trip-review-qa` |
| `ux` | `trip-review-ux` |
| `client` | `trip-review-client` |
| `service` | профиль отсутствует |

Не следует смешивать четыре независимые координаты:

| Координата | Примеры | На что влияет |
|---|---|---|
| функциональная роль | `qa`, `architect`, `lead` | ответственность и маршрутизация |
| деятельность | `observe`, `analyze`, `review`, `complete` | доступный сценарий работы |
| представление | `current`, `result`, `changed` | проекция baseline/candidate |
| решение | `pending`, `approved`, `rejected` | состояние человеческого gate |

`trip work start <changeSetId> --accountable <роль>` объявляет единственного
`A` именно для передаваемого результата рабочего пакета. `trip work role
<роль>` меняет локальную рабочую перспективу, но не аутентификацию и не
полномочия. Trip проверяет каноничность кода роли; реальное право принять
решение обеспечивается Git/CI/MR.

Исполнитель инспекции — ещё одна независимая ось. Один и тот же инспектор
может работать в режиме `human`, `ai_agent`, `hybrid` или `deterministic`.
Frontend внутри инспектора является рабочим местом человека; отдельный
Frontend Inspector проверяет пользовательский интерфейс проекта. Trip не
различает эти режимы при проверке полноты: все они обязаны выпустить один
совместимый неизменяемый конверт. Исполнитель инспекции не получает полномочие
`A` автоматически.

### Момент применения инструментов

```text
draft-коммиты
  → дешёвые правила файлов и структуры (pre-commit)
  → observe: посмотреть current/result/changed
  → analyze: независимо получить отчёты инспекторов
  → trip work import: сохранить точные свидетельства
  → профильное ревью и отдельный Human Gate
  → импорт ReviewRecord/DecisionRecord и фиксация FREEZE selection
  → проверка полноты/FREEZE результата (pre-push)
```

Для миграции стадия `draft` может переписывать один файл с устойчивым
`migrationId` внутри рабочего пакета. На `reviewed` рецензент проверяет
изменения, на `sealed` политика запрещает переписывание опубликованной
миграции, на `applied` отдельный изолированный runner применяет baseline и
candidate, на `verified` инспектор публикует свидетельства схемы/данных, а
ответственная роль принимает отдельное человеческое решение. В native v2
FREEZE допустим только для заявленных финальных состояний и при наличии
rehearsal/recovery evidence. Trip отвечает за границы фиксации и полноту
пакета, но не исполняет SQL и не подменяет инспекторы.

## Контракт js-скриптов

Скрипты исполняются **in-process** встроенным движком **ClearScript V8** — внешний Node.js
не нужен. Файл скрипта берётся как `trip/` + значение пути из политики.

Движок готовит **глобальные переменные** и вычисляет скрипт; **результат** — значение
последнего выражения скрипта (completion value), приводимое к boolean.

**Скрипт-проверка** (`{ "type": "script" }` в `rules`/`lockZones`):
- глобальные переменные: `path` (git-относительный путь, forward slash), `op`
  (`add`|`modify`|`delete`|`rename`); также объект `trip = { path, op }`;
- результат: `true` — файл **совпадает** с проверкой (подпадает под неё), `false` — нет.
- пример: `path.startsWith("src/") && path.endsWith(".cs")`

**Валидатор сообщения** (`message.validator`):
- глобальные переменные:
  - `message` — текст сообщения коммита;
  - `registry` — идентификаторы требований, заведённые в проекте, по одному
    в строке; пустая строка означает «источник не найден», и проверка
    существования ссылки не выполняется, а не объявляет её несуществующей;
  - `registrySource` — какие именно файлы прочитаны, чтобы отказ мог назвать
    основание сверки;
  - `gitOperation` — выполняемая сейчас операция git: `merge`, `revert`,
    `cherry-pick` либо пустая строка. Опознаётся по служебным файлам каталога
    git, а не по тексту: git вызывает `commit-msg` и при слиянии, поэтому без
    этой переменной валидатор блокировал бы любое слияние, а освобождение по
    тексту сообщения было бы лазейкой;
  - `originPolicy` — секция `message.origin` в виде JSON; пустая строка означает
    «правило происхождения не объявлено», и валидатор трейлеров не требует;
  - `referencePolicy` — секция `message.reference` в виде JSON; пустая строка
    означает «класс ссылки не объявлен», и годится любой вид словаря;
  - также `trip = { message, registry, registrySource, gitOperation,
    originPolicy, referencePolicy }`;
- результат: `true` — сообщение валидно; `false` — отклонить без пояснения;
  **непустая строка** — отклонить и показать её пользователю как причину;
- пример: `/^TRP-\d+: /.test(message.trim()) || 'ожидается «TRP-<номер>: описание»'`

**Источник требований** (`traceability.registry`, прежде `message.registry`) —
список файлов, в которых заведены требования, относительно корня репозитория.
Пусто — по соглашению: файлы `РЕЕСТР_ТРЕБОВАНИЙ*.md` в дереве репозитория, все
сразу. Собирать надо именно все: в репозитории с реестром подпроекта поиск по
первому совпадению объявляет чужие идентификаторы несуществующими. Проект,
ведущий требования в техническом задании, называет его здесь:

```json
"traceability": { "registry": ["doc/tz-v1.md"] }
```

`message.registry` продолжает работать и используется, когда секции
`traceability` нет: правило действует перспективно, а не ломает объявленное.

**Что источником не является.** Файл с паспортом шаблона методологии
(`template_id`, `template_name`, `template_version` в заголовке YAML) не
читается, даже будучи названным явно: проектный артефакт этих полей не несёт по
построению — сам шаблон объявляет
`rendering.hide_template_metadata_in_project_artifact: true`. Служебный каталог
`МЕТОДОЛОГИЯ/` (и `methodology/`) при обходе по соглашению не посещается вовсе;
объявленный путь этот отвод обходит — назвать файл внутри каркаса проект вправе.

Причина у обоих отводов одна. Идентификаторы шаблона — примеры из инструкции по
заполнению (`R-001`, `R-002`, `R-999`, `R-1000`), и они ничем не отличаются от
настоящих ссылок. Принятый за реестр шаблон делает проверку не строже, а
вреднее: она начинает отвергать живые требования проекта и пропускать те, что
случайно совпали с примером. Отведённые файлы называются в отчёте — молчание
прочиталось бы как «реестра нет».

**Прочие канонические источники** (`traceability.sources`) — критерии приёмки,
тестовые сценарии, реестр дефектов. Существование ссылки сверяется для **всех**
видов, представленных в источниках, а не только для `R`: иначе девять
префиксов остаются без источника, и ссылка на несуществующий критерий проходит
вечно — то есть оказывается дешевле ссылки на требование. Вид, не встреченный в
источниках ни разу, не судится: пустой набор означает «проверить нечем».

**Класс ссылки** (`message.reference`) — какого класса идентификатор
засчитывается:

```json
"reference": {
  "mode": "any",
  "requirementKinds": ["R", "DR"],
  "requirement": {
    "directions": ["development"],
    "types": ["feat", "fix", "refactor", "perf"]
  }
}
```

- `mode`: `any` (по умолчанию) либо `requirement` — требование везде;
- `requirementKinds`: что считается классом требования; пусто — `R` и `DR`;
- `requirement.directions` / `requirement.types`: где именно нужен этот класс.
  Пустой список не ограничивает, поэтому два пустых списка равны `mode`.

Освобождение `chore(service)` и `revert` правилом не отменяется: подъём замка
средств не должен требовать выдуманного требования. Без секции поведение
прежнее — годится любой вид словаря.

**Барьер реестра** (`traceability.beforeCode`) — пока реестр требований не
заведён, изменение кода не принимается:

```json
"beforeCode": {
  "mode": "block",
  "code": [{ "type": "wildcard", "pattern": "src/**" }]
}
```

- `mode`: `block` (по умолчанию) либо `advisory` — сообщить, не останавливая;
- `code`: что считается кодом; пусто — правило ничего не покрывает и молчит.

Правило закрывает единственную последовательность, которую прочие проверки
пропускают по построению: код написан первым, требования дописаны под него
задним числом, и трасса выходит объяснением уже принятых решений вместо их
основания. Вопрос задаётся самый дешёвый — есть ли вообще, на что ссылаться;
правильность конкретной ссылки судят другие проверки. Работе над самими
документами барьер не мешает: иначе реестр нечем было бы завести.

Действует и на индексе (`--staged`), и на диапазоне коммитов (`--commits`) —
в том числе без секции `commit`: хук снимается флагом `--no-verify`, и то же
правило обязано работать на уже созданной истории.

**Разметка против документов** (`traceability.markers`) — маркер, появившийся
в коде, обязан ссылаться на заведённый идентификатор, а документ-владелец —
измениться тем же коммитом:

```json
"markers": { "mode": "block", "requireDocumentChange": true }
```

Покрыты `@req`, `@supports`, `@ac`, `@tc`, `@us`, `@uc`, `@bug`. `@shared`
называет компонент, `@adr` — решение; реестром они не разрешаются, и требовать
правки решения на каждую ссылку значило бы переписывать принятое при каждом
упоминании.

Сравниваются объявленные связи, а не строки диффа: прежняя редакция берётся из
`HEAD` (для диапазона — из родителя коммита), новая — из индекса. Перенос
маркера между строками, переформатирование комментария и правка соседнего
текста новой связи не создают — иначе документ пришлось бы трогать при каждом
коммите, и правило обесценилось бы за неделю.

Вид без представителей в источниках не судится — тот же закон, что и для ссылки
в сообщении. `requireDocumentChange: false` оставляет действующей только сверку
«маркер ссылается на заведённое».

Правило отвечает на расхождение, которое иначе накапливается молча: разметку в
коде ставят охотно, потому что она рядом с работой, а документ лежит в стороне
и правится «потом». Маркер объявляет связь локально и по построению не может
сказать, что требование перешло в «реализовано», — это поле документа. Trip не
судит содержательность правки: полноту следа считает trip-trace, смысл правки
смотрит рецензент.

**Граница освобождения служебной правки** (`traceability.serviceExemption`) —
коммит, объявленный направлением `service`, но несущий пути из карты кода,
отклоняется:

```json
"serviceExemption": { "mode": "block" }
```

`chore(service)` освобождён от ссылки на требование, и это единственное
освобождение, которое можно получить, ничего не объявляя. Пока оно не
ограничено составом, оно же и самый дешёвый обход: миграция, точка API и новый
экран проезжают служебной правкой, не назвав основания. Правило возвращает
освобождению его смысл, не отменяя его.

Проверяется в `commit-msg` — единственный момент, когда известны и объявление,
и состав будущего коммита, — и на диапазоне `--commits`. Карта зон
(`commit.zones`) решает ту же задачу подробнее, сопоставляя каждой зоне
допустимые направления; это правило работает и там, где карта зон не расписана.

**Общая карта кода** (`traceability.code`) — что считается кодом для всех трёх
правил. «Код» это одно понятие репозитория, и разводить его по секциям значило
бы завести два ответа на один вопрос. Отдельная карта внутри правила
(`beforeCode.code`, `markers.code`, `serviceExemption.code`) её переопределяет.

**Валидатор ветки** (`branch.validator`):

- глобальные переменные: `branch` (короткое имя текущей ветки); также
  `trip = { branch }`;
- результат: `true` — имя валидно; `false` или непустая строка — отклонить;
- в состоянии detached HEAD команда не вызывает скрипт и не блокирует
  служебную операцию Git.

**Валидатор журнала** (`changelog.validator`):

- глобальные переменные: `content` (проверяемое содержимое), `previous`
  (содержимое из merge-base либо пустая строка), `branch` и
  `requireChange`; также одноимённые поля объекта `trip`;
- результат: `true` — структура и требуемое изменение валидны; `false` или
  непустая строка — отклонить;
- без `--require-changelog` проверяется снимок индекса; с этим флагом
  используются `HEAD` и merge-base, чтобы рабочая копия не влияла на
  результат pre-push.

Строка-причина печатается под сообщением об отклонении, поэтому автор коммита сразу
видит, что именно не так.

Ошибка компиляции/исполнения скрипта, таймаут или отсутствие файла трактуются как
**нарушение** (fail-closed) с понятной диагностикой. Исполнение ограничено таймаутом.

## Преднастроенные политики (seed при `trip init`)

Две зеркальные политики вокруг **методологии** (`trip.json` + `trip/**`).
Исключение — настройки средств самого проекта (`trip/cast-agreement.json`,
`trip/trace-policy.json`): средства ищут их в `trip/` по умолчанию, но принадлежат
они проекту, а не методологии, и правятся обычной политикой. Исключение задано
выражением, а не перечислением разрешённого: всякий новый файл в `trip/` закрыт
по умолчанию, и открыть его — отдельное решение (`R-093`):

```jsonc
{
  "generic": {
    "title": "Generic-изменения",
    "description": "Менять можно всё, кроме файлов методологии.",
    "lockMode": "denylist",
    "lockZones": [
      { "type": "wildcard", "pattern": "trip.json" },
      { "type": "regexp", "pattern": "^trip/(?!(?:cast-agreement\\.json|trace-policy\\.json)$).*" }
    ],
    "message": { "validator": "msg.js" },
    "branch": { "validator": "branch.js" },
    "changelog": {
      "validator": "changelog.js",
      "path": "CHANGELOG.md"
    }
  },

  "policies-only": {
    "title": "Только политики",
    "description": "Менять можно только файлы методологии, всё остальное заблокировано.",
    "lockMode": "allowlist",
    "lockZones": [
      { "type": "wildcard", "pattern": "trip.json" },
      { "type": "regexp", "pattern": "^trip/(?!(?:cast-agreement\\.json|trace-policy\\.json)$).*" }
    ],
    "message": { "validator": "msg.js" },
    "branch": { "validator": "branch.js" },
    "changelog": {
      "validator": "changelog.js",
      "path": "CHANGELOG.md"
    }
  }
}
```

Рядом с политиками заготовка пишет корневое поле `"trunk": "main"` — настройка
называется явно, иначе о ней узнаёт только тот, кто читал эту страницу.

Активная по умолчанию — `generic`.

Обе политики ссылаются на общие валидаторы `trip/msg.js`, `trip/branch.js` и
`trip/changelog.js`, которые `trip init` раскладывает из встроенных шаблонов.

Повторный `trip init` не переписывает существующий `trip.json`. Поэтому проект,
созданный до появления `branch` и `changelog`, включает новые проверки
явным добавлением этих секций в нужные политики; одних файлов валидаторов и
нового hook недостаточно.

## Валидатор сообщения по умолчанию — Conventional Commits

`trip/msg.js` реализует [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/),
согласованный с `соглашением о коммитах TRIP v1.5` (`git-workflow.md#коммиты` — в исходном репозитории средства):

```
<тип>(<направление>[/<область>])[!]: <описание>

[тело]

[футеры]
```

Тип описывает характер изменения, а направление выбирает маршрут профильного
ревью. Они задаются независимо:

| Часть | Допустимые значения |
|---|---|
| Тип | `req`, `docs`, `feat`, `fix`, `refactor`, `perf`, `build`, `ci`, `style`, `test`, `revert`, `chore` |
| Направление | `analytics`, `development`, `qa`, `ux`, `client`, `service` |

После направления можно указать необязательную область: `development/api`,
`analytics/requirements`, `ux/frontend`. Область уточняет часть результата, но
не заменяет направление.

Проверяется:

| Правило | Пример отказа |
|---|---|
| тип из разрешённого списка | `feature(development): …` |
| обязательное известное направление | `feat: …`, `feat(product): …` |
| ровно один пробел после двоеточия | `feat(development):добавить` |
| описание непустое, не короче 10 символов, со строчной буквы, без точки в конце | `fix(development): Поправить отступы.` |
| описание на русском (хотя бы одна кириллическая буква) | `feat(development): add SSO login (R-1)` |
| ссылка на идентификатор трассируемости (`R`, `DR`, `US`, `UC`, `Q`, `AR`, `ADR`, `AC`, `TC`, `BUG`, `ФЗ`) | `feat(development): добавить вход по SSO` |
| необязательная область в нижнем регистре (`a-z0-9._-`) | `feat(development/Моя Область): …` |
| заголовок не длиннее 100 символов | — |
| пустая строка между заголовком и телом | тело сразу со второй строки |
| `!` требует пояснения в теле или футера `BREAKING CHANGE:` | `feat(development)!: сменить формат` |

В реестре `trip-cli` требования получают глобальные `R-*`; признак `FR`/`NFR`
хранится отдельно и не входит в идентификатор.

Без ссылки разрешены только `chore(service)` и `revert(<направление>)`.
Свободные сообщения слияния и отката не пропускаются: линейная `main` не требует
merge-коммитов, а откат оформляется обычным типом `revert`. Строки-комментарии
Git (`#`) при разборе игнорируются.

Верхние константы скрипта (`TYPES`, `DIRECTIONS`, `MAX_HEADER`,
`MIN_SUBJECT`, `REQUIRE_RU_SUBJECT`, `REQUIRE_REF`, `REF_PATTERN`) — точки
настройки под проект. Полный рабочий процесс описан в
`правилах Git-ведения` (`git-workflow.md` — в исходном репозитории средства).

## Валидатор ветки по умолчанию

`trip/branch.js` проверяет обычную грамматику
`тип/направление[/область]/основание-краткое-имя`, предел 120 символов и
особые ветки `experiment`, `hotfix` и `release`. Прямая работа из основной ветки
(`trunk` в `trip.json`, по умолчанию `main`) и машинных указателей `env/test`,
`env/stage`, `env/prod` отклоняется; отказ называет объявленное имя.
Канонические основания транслитерируются только в имени ветки: в частности,
`ФЗ-007` становится `fz-007`. Для `chore/service` без канонического ID
разрешены только основания `branch`, `workflow`, `repository`, `dependencies`,
`tooling` и `release`.

`front`, `back`, `data` (или совместимый алиас `db`) и `docs` являются
областями, а не направлениями. Например, функциональность панели использует
`development/front`, изменение пользовательского опыта — `ux/front`,
серверная логика — `development/back`, данные — `development/data`, а
требования — `analytics/requirements`. Направление `client` относится к
Заказчику и демонстрациям, а не к браузерному приложению.

## Валидатор журнала по умолчанию

`trip/changelog.js` проверяет корневой журнал по стратегическим направлениям:
«Аналитика», «Разработка», «QA и тесты», «UX и эстетика», «Клиент» и
«Служебные изменения». Технические области не создают собственных разделов.

В режиме `requireChange` обычная ветка должна добавить хотя бы одну запись в
подраздел своего доминирующего направления и сослаться в ней на каноническое
основание из имени ветки. Дополнительные записи коммитов других направлений
остаются в их подразделах. `experiment` и `chore/service` могут не менять
журнал; `release` обязана изменить валидный журнал.
