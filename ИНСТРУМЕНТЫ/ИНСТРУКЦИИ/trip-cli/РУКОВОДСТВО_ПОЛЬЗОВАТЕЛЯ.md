# Руководство пользователя TRIP-CLI

Руководство соответствует TRIP-CLI 0.5.1 и предназначено для разработчиков,
аналитиков, архитекторов, тестировщиков, заказчиков и методологов, которые
работают с Git-репозиторием под управлением TRIP.

TRIP-CLI помогает договориться о правилах работы в репозитории и автоматически
проверяет их перед коммитом и отправкой ветки. Он не заменяет Git, систему
управления задачами или рецензента.

## 1. Что делает TRIP-CLI

После подключения к репозиторию TRIP-CLI:

- хранит общие правила команды в `trip.json` и каталоге `trip/`;
- хранит локальное состояние пользователя в `.trip/`;
- проверяет подготовленные к коммиту файлы и состав среза;
- проверяет имя ветки и сообщение коммита, включая указатель происхождения;
- требует описать проверенный результат в `CHANGELOG.md`;
- собирает реестр доступных средств по их манифестам и отвечает, что и под
  каким именем можно запустить;
- может собрать результаты независимых инспекций в единый рабочий пакет;
- блокирует отправку ветки, если обязательные проверки не пройдены;
- показывает репозиторий, изменения, политики и историю проверок в веб-панели.

### Основные понятия

| Понятие | Простое объяснение |
|---|---|
| Политика | Набор правил: какие файлы можно менять и какие проверки нужно пройти |
| Активная политика | Политика, которая применяется на этом компьютере прямо сейчас |
| Зона ответственности | Группа путей, за которую отвечает одно направление работы |
| Срез | Состав одного коммита: какие зоны он затрагивает и сколько в нём файлов и строк |
| Происхождение | Указатель на того, кто вёл изменение: средство, модель и сеанс |
| Рабочий пакет | Контекст одного логического результата: что меняется, кто отвечает и какие подтверждения нужны |
| Инспекция | Независимая проверка результата, например Backend, Frontend или DB Inspector |
| Свидетельство | Неизменяемый JSON-документ с результатом проверки |
| Отпечаток | SHA-256 содержимого документа; позволяет заметить любую подмену |
| Финальная проверка | Проверка полноты и согласованности рабочего пакета перед передачей результата |

### Какие файлы появляются в репозитории

| Путь | Назначение | Добавлять в Git |
|---|---|---|
| `trip.json` | Описание политик и методологии проекта | Да |
| `trip/` | Скрипты проверки сообщений, веток и changelog | Да |
| `CHANGELOG.md` | Проверенные результаты по направлениям | Да |
| `.trip/` | Активная политика, локальные отчёты, состояние сервера | Нет |
| `.trip/tools/` | Распакованные под проект выпуски средств | Нет |

Не переносите `.trip/` между компьютерами вручную и не добавляйте его в коммит.
Средства в `.trip/tools/` не версионируются: их восстанавливает повторная
установка по закреплённым версиям проекта.

## 2. Установка

Начиная с 0.4.0 средство поставляется **собранным файлом выпуска**, а не сборкой
из исходников. Путь установки зависит от того, кто вы в этой истории.

### Требования

- Git;
- Node.js 18 или новее — для проектов на Node и для сборки самого TRIP-CLI;
- .NET SDK 10 — **только** для сборки TRIP-CLI из исходников;
- Python 3 — только для API-тестов самого проекта.

Готовый бинарник самодостаточен: для его запуска установленный .NET не нужен.

### Участнику проекта: выпуск из реестра пакетов

Выпуск лежит generic-пакетом в реестре пакетов репозитория средства
(`TRIP/tooling/trip`). Для каждой платформы — свой архив, рядом с ним отпечаток
SHA-256:

```text
trip-cli-linux-x64.tar.gz
trip-cli-win-x64.tar.gz
trip-cli-darwin-arm64.tar.gz
```

Читает их токен развёртывания с единственным правом `read_package_registry`;
личная учётная запись во внутреннем GitLab участнику не нужна.

В проекте TRIP скачиванием, сверкой отпечатка и распаковкой занимается
установщик проекта по закреплённой версии — своя команда описана в материалах
проекта. Результат один и тот же: распакованное средство лежит в
`.trip/tools/trip-cli/`, а версия одинакова у всех, кто собирает этот проект.

Вручную: скачайте архив своей платформы, сверьте отпечаток, распакуйте и либо
добавьте каталог в `PATH`, либо вызывайте бинарник по пути. Распакованный выпуск
имени в оболочке не заводит — это не забывчивость установщика, а свойство
поставки файлом.

### Разработчику самого TRIP-CLI: сборка из исходников

В корне репозитория `trip-cli`:

```bash
npm run setup
```

Это `npm run build` (собирает автономный бинарь в `./dist`) плюс
`npm install -g .` (ставит глобальную команду). Повторный запуск пересобирает и
обновляет установленную версию.

На npm 11 lifecycle-скрипты пакетов заблокированы. Если нужна установка одним
вызовом, разрешите скрипт только этому пакету:

```bash
npm install -g . --allow-scripts=trip
```

Не используйте `allow-scripts=true`: актуальный npm ожидает точный список
разрешённых пакетов, а не безусловное включение всех скриптов.

### Проверка установки

```bash
trip --version
trip --help
```

Ожидаемый результат для этого выпуска:

```text
trip 0.5.1
```

Если терминал не видит команду сразу после установки, закройте его, откройте
заново и повторите `trip --version`.

## 3. Быстрый старт

### Шаг 1. Перейдите в Git-репозиторий

```bash
cd path/to/project
git status
```

Если проект ещё не является Git-репозиторием:

```bash
git init
```

### Шаг 2. Подключите TRIP

```bash
trip init
```

Чтобы сразу выбрать политику:

```bash
trip init --policy generic
```

Повторный `trip init` безопасен: пользовательские настройки не перезаписываются,
а управляемые Git hooks обновляются.

После первого запуска проверьте:

```bash
git status --short
```

В новом проекте обычно нужно добавить в первый коммит:

- `trip.json`;
- каталог `trip/`;
- изменение `.gitignore`;
- `CHANGELOG.md`, если он принят в проекте.

> **Место для изображения 01.** Терминал после успешного `trip init`: созданные
> каталоги, активная политика и установленные hooks.
>
> Рекомендуемый файл: `doc/images/user-guide/01-init.png`.

### Шаг 3. Проверьте активную политику

```bash
trip policy
```

Для нового репозитория обычно активна политика `generic`.

### Шаг 4. Посмотрите, какие средства доступны

```bash
trip tools list
trip tools doctor
```

Список пуст — это нормально для проекта, который ещё не объявил средств.
Подробности — в разделе [Средства единого входа](#7-средства-единого-входа).

### Шаг 5. Откройте веб-панель

Для локальной работы безопаснее явно ограничить доступ текущим компьютером:

```bash
trip serve --localhost
```

Откроется адрес наподобие:

```text
http://127.0.0.1:7777
```

Остановить сервер можно сочетанием `Ctrl+C`.

> **Место для изображения 02.** Главный экран веб-панели: сайдбар, активная
> политика, дерево файлов и текущая ветка.
>
> Рекомендуемый файл: `doc/images/user-guide/02-panel-overview.png`.

## 4. Ежедневная работа с веткой

Ниже показан рекомендуемый цикл одного логического изменения.

### 4.1. Обновите основную ветку

```bash
git switch main
git pull --ff-only
```

### 4.2. Создайте рабочую ветку

Формат:

```text
<тип>/<направление>[/<область>]/<основание>-<краткое-имя>
```

Пример:

```bash
git switch -c feat/development/back/r-024-local-panel
```

Часто используемые типы:

| Тип | Когда использовать |
|---|---|
| `feat` | Новая возможность |
| `fix` | Исправление дефекта |
| `docs` | Документация |
| `test` | Тесты |
| `refactor` | Перестройка без изменения поведения |
| `chore` | Служебное изменение |

Стратегические направления:

| Направление | Смысл |
|---|---|
| `analytics` | Требования и анализ |
| `development` | Реализация |
| `qa` | Проверка качества |
| `ux` | Пользовательский опыт и визуальная часть |
| `client` | Маршрут и материалы для заказчика |
| `service` | Служебная инфраструктура |

`front`, `back`, `data` и `docs` — области внутри направления, а не отдельные
направления.

### 4.3. Убедитесь, что выбрана нужная политика

```bash
trip policy
```

Для обычной разработки:

```bash
trip policy generic
```

Для изменения только методологии:

```bash
trip policy policies-only
```

### 4.4. Внесите изменения и подготовьте индекс

```bash
git add path/to/file
git status --short
```

До коммита запустите ту же проверку, которую выполнит hook:

```bash
trip verify --staged --branch --changelog
```

Проверка индекса смотрит не только на права доступа к файлам, но и на **состав
среза**. Политика может объявить зоны ответственности, несмешиваемые сочетания
зон и бюджет коммита по числу файлов и строк. Смысл правила простой: коммит,
собранный из двух несвязанных зон, нельзя ни отревьюить одним профилем, ни
откатить целиком.

Что при этом нарушением **не** является:

- путь, не попавший ни в одну объявленную зону;
- вертикальный срез одного направления — он остаётся одним коммитом;
- файлы-попутчики, объявленные в `exempt`: журнал изменений, файлы блокировок.

### 4.5. Обновите changelog

Опишите наблюдаемый результат в разделе `Невыпущено`, например:

```markdown
### Разработка

- Веб-панель показывает состояние рабочей ветки (`R-024`).
```

Не копируйте в changelog список коммитов и не обещайте поведение, которое ещё
не проверено.

Добавьте changelog в индекс и повторите проверку:

```bash
git add CHANGELOG.md
trip verify --staged --branch --changelog
```

### 4.6. Создайте коммит

Формат сообщения:

```text
<тип>(<направление>[/<область>]): <описание> (<ID требования>)

Тело: что и зачем.

Assisted-by: <средство или none>
```

Сообщение пишется по-русски. Содержательное изменение должно ссылаться на
существующий `R-*` или `DR-*` из ТЗ проекта. Последний абзац — трейлерный блок с
указателем происхождения; он обязателен, если проект объявил правило
происхождения (раздел [5](#5-происхождение-изменения)).

Многострочное сообщение удобнее писать файлом, а не ключом `-m`:

```bash
git commit -F .git/СООБЩЕНИЕ
```

Проверить сообщение до коммита:

```bash
trip verify --message .git/СООБЩЕНИЕ
```

Проверка сообщения сверяет и объявленное направление с составом индекса:
заголовок `fix(qa/...)` при индексе из чужой зоны будет отклонён.

### 4.7. Проверьте итог ветки

```bash
trip verify --branch --changelog --work-package --base main --require-changelog
```

Затем выполните профильные тесты проекта и отправьте ветку:

```bash
git push -u origin HEAD
```

> **Место для изображения 03.** Успешная финальная проверка ветки перед push:
> имя ветки, changelog и рабочий пакет прошли проверку.
>
> Рекомендуемый файл: `doc/images/user-guide/03-branch-verified.png`.

## 5. Происхождение изменения

Раздел появился в 0.5.0 и уточнён в 0.5.1. Он отвечает на один вопрос: **кто
вёл это изменение** — человек или средство, и если средство, то по какому
сеансу его можно найти.

### Как это выглядит

Ответ живёт в трейлерном блоке — последнем абзаце сообщения коммита:

```text
feat(development/msg): требовать указатель сеанса (R-088)

Тело коммита. Сюда же — проза, оговорки и «BREAKING CHANGE: …».

Assisted-by: claude-code
Model: claude-opus-5
Session: https://claude.ai/code/session_01Det4MaxXe5
Prompt-SHA256: 3f2a…c19b
```

| Трейлер | Значение |
|---|---|
| `Assisted-by` | слаг средства, которое вело сеанс, либо `none` для правки без средства |
| `Model` | идентификатор модели |
| `Session` | указатель на сеанс: URL либо непрозрачный идентификатор |
| `Prompt-SHA256` | якорь реплики: 64 строчных шестнадцатеричных знака |

### Правила

- `Assisted-by: none` — коммит сделан человеком без средства; остальные трейлеры
  происхождения при этом **не допускаются**: сеанса, на который можно сослаться,
  не было.
- Названо средство — `Model` и `Session` обязательны. Средство без модели и
  сеанса называет исполнителя, но не даёт к нему дороги.
- Каждый трейлер встречается не более одного раза.
- **Весь последний абзац состоит только из трейлеров.** Это не вкусовщина:
  `git log --format=%(trailers)` читает только последний абзац, и одна
  посторонняя строка в нём отбрасывает абзац целиком — указателей для сборщика
  не остаётся вовсе. Проза, заметки и переносы значения с отступа идут в тело
  коммита, выше пустой строки.
- Отдельный случай — `BREAKING CHANGE:`. Ключ с пробелом трейлером не является и
  уносит с собой все указатели. В трейлерном блоке пишется `BREAKING-CHANGE:`
  через дефис; форма с пробелом остаётся допустимой в теле коммита.
- Освобождены только сообщения, сочинённые самим git: слияние, откат и заплатки
  автосжатия. Написанные человеком `chore(service)` и `revert` от происхождения
  **не** освобождаются, хотя от ссылки на требование освобождены: служебная
  правка тоже кем-то сделана.

Проверить, что git действительно видит указатель, можно до коммита:

```bash
git interpret-trailers --parse .git/СООБЩЕНИЕ
```

Пустой вывод означает, что блок не собрался и сборщик из этого коммита не
прочитает ничего.

### Правило вводит проект, а не версия инструмента

Требование включается секцией `message.origin` в `trip.json`:

```json
"message": {
  "validator": "msg.js",
  "registry": ["doc/tz-v1.md"],
  "origin": {
    "mode": "required",
    "agents": ["claude-code", "codex", "cursor"],
    "requireAnchor": false
  }
}
```

| Поле | Значение |
|---|---|
| `mode` | `off` (по умолчанию) либо `required` |
| `agents` | словарь допустимых средств; пусто — принимается любой корректный слаг |
| `requireAnchor` | требовать `Prompt-SHA256`; по умолчанию `false` |

Нет секции — валидатор трейлеров ничего не требует, и обновление инструмента не
блокирует коммиты в репозиториях, которые о правиле не решали. Неизвестное
значение `mode` и неразобранная секция — отказ, а не разрешение.

Средства нет в списке `agents` — его добавляют решением проекта, отдельным
коммитом в методологию, а не догадкой на месте.

### Что трейлер доказывает, а что нет

Проверяются **наличие и форма**. Правдивость заявления не проверяется: текст
сообщения подделывается, и `Assisted-by: none` в сообщении, написанном
средством, проверка от правды не отличит. Доказательную силу даёт якорь
`Prompt-SHA256` вместе с внешним леджером, а не трейлер сам по себе.

Трейлер несёт указатель, а не содержимое. Текста реплик в репозитории нет и не
будет: git остаётся тонким индексом указателей, а редактированный текст с
разграниченным доступом живёт во внешнем леджере.

## 6. Политики

Политика определяет:

- какие файлы разрешено добавлять, изменять, удалять и переименовывать;
- какие пути защищены от записи;
- как проверяются имя ветки, сообщение коммита и changelog;
- нужен ли указатель происхождения и какие средства допустимы;
- какие зоны ответственности несмешиваемы и каков бюджет среза;
- какие группы файлов и результаты инспекций обязательны.

### Преднастроенные политики

| Политика | Назначение |
|---|---|
| `generic` | Обычная работа: методология `trip.json` и `trip/` защищена |
| `policies-only` | Изменение методологии: разрешено менять только `trip.json` и `trip/` |

### Просмотр и переключение

Показать активную политику:

```bash
trip policy
```

Переключить:

```bash
trip policy generic
```

Если смена запрещена, веб-панель могла включить блокировку CLI. В этом случае
TRIP покажет причину; обратитесь к ответственному за методологию или снимите
блокировку через панель, если у вас есть такое право.

### Редактирование политики

Политики можно редактировать:

- вручную в `trip.json`;
- через раздел «Политики» веб-панели.

Перед сохранением проверьте правило на тестовом пути. Подробная техническая
модель описана в [модели политик](./МОДЕЛЬ_ПОЛИТИК.md).

> **Место для изображения 04.** Раздел «Политики»: список политик, активная
> политика и модальное окно редактирования правил.
>
> Рекомендуемый файл: `doc/images/user-guide/04-policies.png`.

## 7. Средства единого входа

Появилось в 0.4.0. TRIP-CLI читает манифесты средств по контракту
`trip.tool-manifest/v1` и собирает из них реестр: что доступно и под каким
именем. Реестр ничего не запускает — он отвечает на вопрос «что есть», и
отвечает одинаково для командной строки и для MCP.

### Три источника, в порядке старшинства

| Источник | Где лежит | Почему такой порядок |
|---|---|---|
| Выпуски под проект | `.trip/tools/<средство>/` | версию под проект закрепил проект, и она одинакова у всех, кто его собирает |
| Установленное на машине | `PATH` и каталоги установки | это то, что оказалось у одного человека |
| Манифест самого проекта | `trip/tool-manifest.json` | средства, объявленные проектом для себя |

Исполняемый файл ищется сначала в доме средства (сам каталог и `bin/`), и лишь
затем в `PATH`: распакованный выпуск имени в оболочке не заводит, и поиск только
по `PATH` нашёл бы чужую установку или не нашёл ничего.

### Команды

```bash
trip tools list              # что доступно и под каким именем
trip tools describe <имя>    # операции, пути вызова и совместимость средства
trip tools doctor            # разрешается ли команда запуска целиком
```

`doctor` разрешает команду запуска **до** предметного вызова: в предметном
запуске отсутствие установки выглядит отказом средства, а не отказом установки.
Объявленный адрес службы при этом не опрашивается — осмотр не ходит в сеть без
спроса.

Если средство запускается интерпретатором, манифест объявляет интерпретатор
исполняемым файлом, а свой вход — аргументом, начинающимся с `./`. Такой
аргумент разворачивается от дома средства; аргумент, уводящий за его пределы,
отклоняет манифест целиком.

### Когда манифест отклоняется

- **Дубль имени** — занятый `toolId`, идентификатор операции, путь CLI или имя
  MCP. Отклоняется весь манифест, а не одна операция: реестр с половиной
  средства отвечал бы «доступно» там, где вызов приведёт не туда. Совпадение
  внутри одного манифеста — тот же конфликт.
- **Несовместимость** — версия `trip` вне объявленного диапазона, незнакомая
  старшая редакция контракта, неразобранная запись диапазона. Последнее
  намеренно: поле совместимости заведено ради запрета, и молчаливое согласие с
  непонятной записью снимало бы ровно ту защиту, ради которой оно существует.

Проектная конфигурация адаптер не определяет: `trip.json` не читается на
`executable`, `endpoint` и происхождение вовсе, а попытка их там объявить
называется замечанием — молчание выглядело бы согласием.

## 8. Веб-панель

### Запуск

Локальный режим:

```bash
trip serve --localhost
```

Указать точный порт:

```bash
trip serve --localhost --port 7878
```

Если порт не указан и `7777` занят, TRIP пробует `7778`, `7779` и далее. Если
порт указан явно и занят, команда завершается с ошибкой. Ключ `--no-open` не
открывает браузер автоматически.

### Доступ через туннель

Без `--localhost` сервер принимает внешний `Host` и может использоваться через
ngrok, pgrok или cloudflared:

```bash
trip serve --port 7777
pgrok http 7777
```

Не публикуйте панель в недоверенную сеть без внешней защиты доступа. Панель
работает с файлами и политиками текущего репозитория.

### Разделы панели

| Раздел | Для чего нужен |
|---|---|
| Файлы | Дерево проекта, просмотр файла, состояние относительно Git |
| Рецензии | Комментарии к файлам, папкам и участкам кода |
| Изменения | Незакоммиченные изменения и подсвеченный diff |
| Проверка | Проверка изменений или всего дерева на согласие с политикой |
| Политики | Просмотр, переключение, создание и редактирование политик |
| Журнал | Попытки проверки и причины блокировки |
| Коммиты | История коммитов и состав изменений |
| Настройки | Палитра и компоненты дизайн-системы |

### UI/UX-наблюдения

С 0.4.0 UI/UX-отчёты, снимки и их жизненный цикл принадлежат отдельному
TRIP Bug Loop, а `trip serve` перестал быть вторым источником `BUG-id`. Кнопка
регистрации наблюдения встроена в панель как зафиксированный артефакт этого
сервиса, поэтому остаётся видимой и без него; регистрация, трассировка и анализ
требуют его API на `http://127.0.0.1:7788`.

Собственного реестра, API и хранилища снимков в `trip serve` нет. Старые файлы
`.trip/issues/` не удаляются автоматически. Маршруты панели, кандидаты
требований и команды проверки заданы в `trip-bug-loop.json`. Кандидаты текущего
маршрута выбраны заранее, ненужную связь можно снять нажатием. Класс важности и
остальные служебные параметры назначаются на триаже, а не в форме наблюдения.

При запуске создаётся `.trip/serve.json` с PID и портом. Когда панель работает,
`trip verify` отправляет в неё события проверок. Если сервер не запущен,
проверка Git продолжает работать самостоятельно.

> дерево проекта, открытый файл и diff.
>
> Рекомендуемый файл: `doc/images/user-guide/05-files-and-changes.png`.

## 9. Рабочий пакет и результаты инспекций

Этот раздел нужен командам, в которых результат перед передачей проверяют
независимые Backend, Frontend или DB Inspector.

Важно: TRIP-CLI не запускает инспекторов. Инспектор или ответственный участник
создаёт JSON-документ, а TRIP проверяет его, сохраняет без изменений и связывает
с текущим состоянием Git.

### 9.1. Современный формат пакета

В JSON этот формат обозначается суффиксом `/v2`. Пользователю важен не номер
формата, а результат: все документы связаны друг с другом, защищены отпечатками
и проверяются вместе.

В пакет могут входить:

| Документ | Что подтверждает |
|---|---|
| WorkPackage | Состав результата, источники, ответственного и правила передачи |
| InspectionRequest | Какую проверку и для какого состояния нужно выполнить |
| Inspection | Что именно проверено и какие свидетельства получены |
| ReviewRecord | Результат независимой рецензии |
| DecisionRecord | Решение ответственного о передаче результата |
| PolicySet | Набор обязательных gates и правил |

Проверить встроенные схемы:

```bash
trip work contracts
```

### 9.2. Импорт документов

Сначала импортируйте WorkPackage:

```bash
trip work import artifacts/work-package.json
```

Он сразу становится активным. Затем импортируйте связанные документы:

```bash
trip work import artifacts/inspection-request.json
trip work import artifacts/db-inspection.json
trip work import artifacts/backend-inspection.json
trip work import artifacts/frontend-inspection.json
trip work import artifacts/review-record.json
trip work import artifacts/decision-record.json
trip work import artifacts/policy-set.json
```

Посмотреть активный пакет:

```bash
trip work show
```

Посмотреть все импортированные документы:

```bash
trip work list
```

TRIP сохраняет исходные байты документов. Не исправляйте импортированный JSON
«на месте»: получите новый документ от его владельца и импортируйте его как
новую ревизию.

### 9.3. Выбор точной ревизии

Если WorkPackage с одним идентификатором имеет несколько ревизий, выберите
нужную по отпечатку:

```bash
trip work use WP-MIGRATION-42 --fingerprint sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

Без `--fingerprint` выбор допустим только тогда, когда нужная ревизия
определяется однозначно.

### 9.4. Финальная проверка

Понятный человеку вывод:

```bash
trip work freeze
```

Машинный JSON для CI:

```bash
trip work freeze --json
```

Проверка подтверждает, что:

- выбран правильный пакет и точная ревизия;
- инспекции относятся к текущему Git `HEAD`;
- обязательные проверки завершены и подтверждены;
- рецензия и решение относятся к тем же исходным данным;
- ответственный, сроки, gates и миграции согласованы;
- один участник не совмещает несовместимые роли.

После нового коммита меняется Git `HEAD`. Ранее импортированная инспекция может
стать устаревшей — это нормальная защита от передачи непроверенного результата.
Запустите соответствующую инспекцию заново и импортируйте новый документ.

> **Место для изображения 06.** Два результата `trip work freeze`: успешный и
> отклонённый с кодом, путём и понятным сообщением о причине.
>
> Рекомендуемый файл: `doc/images/user-guide/06-final-check.png`.

### 9.5. Упрощённый совместимый режим

Если проект ещё не формирует полный WorkPackage, создайте локальный контекст:

```bash
trip work start CS-MIGRATION-42 --project my-project --accountable lead --role developer
```

Идентификатор `changeSetId` начинается с `CS-` и содержит только прописные
латинские буквы, цифры и дефисы.

Допустимые роли:

```text
analyst, architect, customer, developer, lead, methodologist, qa
```

Импортируйте отчёт инспектора:

```bash
trip work import artifacts/db-inspection.json
trip work list
```

Команда `trip work role <роль>` меняет только рабочую перспективу интерфейса и
не выдаёт дополнительных полномочий.

## 10. Ручные проверки, hooks и CI

`trip init` устанавливает три управляемых hook:

| Hook | Что проверяет |
|---|---|
| `pre-commit` | Подготовленные файлы, состав среза, имя ветки и структуру changelog |
| `commit-msg` | Формат и содержание сообщения, происхождение, направление против состава индекса |
| `pre-push` | Итог ветки, changelog, рабочий пакет и вклеенность заплаток автосжатия |

### Три правила состава коммита и три момента

Разделение по стадиям задано git, а не вкусом: состав индекса известен до того,
как написано сообщение, а объявленное направление — только после.

| Правило | Когда проверяется | Что нужно знать |
|---|---|---|
| несмешение зон | `trip verify --staged` (`pre-commit`) | только состав индекса |
| бюджет среза | `trip verify --staged` (`pre-commit`) | только состав индекса |
| направление ↔ зоны | `trip verify --message` (`commit-msg`) | состав индекса и заголовок |

Готовый коммит проверяется всеми тремя правилами сразу:

```bash
trip verify --commits --base main
```

Эту команду ставят в гейт слияния: там обход локального хука через `--no-verify`
уже не помогает.

### Что git делает сам, то не проверяется как авторская правка

Состав индекса не проверяется во время операции git. Коммит слияния, отката и
переноса пишет не автор — он складывается из двух уже проверенных историй, и
требование однородности зон делало бы слияние невозможным в принципе.
Освобождение опирается на состояние каталога git, а не на текст сообщения: текст
подделывается, состояние — нет.

По той же причине отправка без коммитов проходит без полной проверки: git
передаёт хуку нулевой локальный `sha`, когда коммитов в пуше нет вовсе, и уборка
отработанных веток на origin не требует записи в журнал. Пуш с коммитами
проверяется по-прежнему.

### Проверки в CI: «не проверяли» — не «проверено»

Применяется ли trip к репозиторию, решает `trip.json` — он отслеживается git и
есть в каждом клоне. Локальный `.trip/policies.json` только выбирает активную
политику; он в `.gitignore`, поэтому в свежем клоне и на агенте CI его нет.

В репозитории без `trip.json` проверки не блокируют работу, но и не выдают себя
за пройденные: trip печатает, что политика не найдена. Там, где отсутствие
политики само является нарушением, состояние переводится в отказ:

```bash
trip verify --staged --branch --require-policy
```

Ставьте этот флаг в CI и на слиянии. Без него код `0` от непроведённой проверки
неотличим от пройденной — а именно это и есть худший исход для средства,
которым подтверждают соблюдение.

Флаг объявляет запуск **подтверждающим**, поэтому отказом становится всякое
состояние «проверить не смогли»:

| Состояние | Обычный запуск | Подтверждающий |
|---|---|---|
| нет `trip.json` | сообщение | отказ |
| запуск вне git-репозитория | сообщение | отказ |
| база сравнения недоступна (поверхностный клон) | сообщение | отказ |
| отсоединённый HEAD при проверке ветки | пропуск | отказ |
| политика не объявляет валидатор | тихо | перечисляется, не отказ |

Последняя строка отличается намеренно: не объявить валидатор — выбор проекта,
а не авария. Остальные четыре означают, что проверка не выполнилась там, где
её ждали.

Пример шага конвейера:

```yaml
проверка-политики:
  stage: test
  script:
    - trip verify --branch --changelog --fixups --require-policy --base "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
```

Конвейер обычно берёт рабочую копию с отсоединённым HEAD; имя ветки trip
восстанавливает из переменных `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`,
`GITHUB_HEAD_REF` или `CI_COMMIT_REF_NAME`. Если рабочая копия получена
поверхностным клоном, базовую ветку нужно получить отдельно — иначе сравнение
с базой невыполнимо, и подтверждающий запуск об этом скажет.

Хуки отключаются и обходятся; шаг конвейера — нет. Именно поэтому гарантия
живёт здесь, а хуки лишь делают правильный путь дешёвым.

### Заплатки автосжатия

`git commit --fixup <sha>` и `--squash <sha>` остаются рабочим приёмом: git
пишет таким коммитам собственный заголовок (`fixup! …`), и валидатор сообщения
их пропускает.

Заплатка по замыслу живёт только до `git rebase --autosquash`, поэтому уехать
ей не даёт `pre-push`: если в диапазоне `merge-base..HEAD` осталась хотя бы
одна, отправка останавливается со списком таких коммитов. Проверка доступна и
вручную:

```bash
trip verify --fixups --base main
```

Именно этот барьер делает освобождение `fixup!` безопасным: обойти проверку
сообщения его префиксом можно ровно до первой отправки. Команда не зависит от
активной политики и работает даже там, где `trip init` ещё не выполнялся.

### Основные ручные команды

Проверить индекс:

```bash
trip verify --staged
```

Проверить имя ветки:

```bash
trip verify --branch
```

Проверить структуру changelog:

```bash
trip verify --changelog
```

Проверить сообщение, записанное в файл:

```bash
trip verify --message path/to/message.txt
```

Проверить корпус документации внешним trip-doc-lint (режим срабатывает,
только когда в корне репозитория объявлен `.trip-doc-lint.toml`; бинарник
ищется сначала в `node_modules/.bin`, затем в `PATH`):

```bash
trip verify --doc-lint
```

Вердикт линтера читается из его итоговой строки, а не из кода возврата: код у
линтера неоднозначен и под единицей прячет и блокирующие находки, и чистый
корпус. Нераспознанная итоговая строка есть неизвестное состояние и не
пропускается.

Проверить весь результат ветки:

```bash
trip verify --branch --changelog --work-package --base main --require-changelog
```

Код возврата `0` означает успех. Ненулевой код означает, что операция должна
быть остановлена; TRIP печатает причину и, где возможно, способ исправления.

Если целевая ветка MR отличается от `main`, задайте основание перед push:

```bash
TRIP_BASE_REF=release/next git push
```

В PowerShell:

```powershell
$env:TRIP_BASE_REF = "release/next"
git push
Remove-Item Env:TRIP_BASE_REF
```

### Запуск трассировщика требований

`trip-cli` является общим оркестратором, а вычисление связей принадлежит
самостоятельному CLI `trip-trace`. После установки обоих средств одна и та же
проверка доступна через семейный вход:

```bash
trip trace scan --mode change --base <sha> --head <sha>
trip trace graph save --mode full --head <sha>
trip trace serve --host 127.0.0.1 --port 8787
```

Команда `trip trace` не разбирает отчёт и не меняет его решение: она передаёт
аргументы дочернему процессу и возвращает его код `0`, `2`, `3` или `1`.
Обычно `trip-trace` находится через реестр средств или `PATH`; для закреплённой
сборки или стенда задайте абсолютный путь в `TRIP_TRACE_EXECUTABLE`.

После повторного `trip init` управляемый `pre-push` автоматически включает
этот барьер, если в проекте есть `trip/trace-policy.json`. Отчёт сохраняется в
`.trip/trace/pre-push-report.json`: `pass` и миграционный `warn` разрешают
отправку, `fail` и техническая ошибка останавливают её. Проекты без политики
трассируемости продолжают работать как раньше.

## 11. CHANGELOG и merge request

### Что писать в changelog

Запись должна отвечать на вопрос: «Что теперь проверенно умеет продукт или
процесс?»

Хорошо:

```markdown
- Проверка ветки блокирует отправку результата без записи в changelog (`R-065`).
```

Плохо:

```markdown
- Обновлён файл VerifyCommand.cs.
- Сделано несколько коммитов.
```

### Что указать в merge request

- цель изменения;
- основание: `R-*`, `DR-*` или согласованная служебная причина;
- затронутые направления и области;
- выполненные команды и их фактический результат;
- миграции или явно указать, что их нет;
- риски и ограничения;
- нужные профили рецензирования;
- решение ответственного.

По умолчанию результат сливается в `main` через rebase merge без отдельного
merge-коммита.

## 12. Частые проблемы

### `trip` не найден

Распакованный выпуск имени в оболочке не заводит. Проверьте, где лежит
средство, и вызовите его по пути либо добавьте каталог в `PATH`:

```bash
ls .trip/tools/trip-cli
trip tools doctor
```

Если TRIP-CLI собран из исходников — повторите `npm run setup` и перезапустите
терминал, чтобы обновился `PATH`.

### `не найден git-репозиторий`

Запускайте TRIP внутри каталога с `.git`:

```bash
git status
trip init
```

### Ветка отклонена

Сверьте имя с форматом:

```text
<тип>/<направление>[/<область>]/<основание>-<краткое-имя>
```

Проверить отдельно:

```bash
trip verify --branch
```

### Сообщение коммита отклонено

Проверьте обязательные части:

- допустимый тип;
- стратегическое направление;
- русское описание;
- существующий идентификатор требования для содержательного изменения;
- трейлерный блок происхождения, если проект объявил `message.origin`.

### Указатель происхождения не читается

Отказ называет мешающую строку. Чаще всего в последний абзац попала проза или
`BREAKING CHANGE:` с пробелом — тогда git не видит трейлеров вовсе. Перенесите
прозу в тело коммита, а ключ запишите через дефис, и сверьтесь с git:

```bash
git interpret-trailers --parse .git/СООБЩЕНИЕ
```

Пустой вывод означает, что блок не собрался.

### Смешаны зоны или превышен бюджет среза

Коммит собран из зон, которые политика объявила несмешиваемыми, либо в нём
больше файлов или строк, чем позволяет бюджет. Разложите изменение на отдельные
коммиты по зонам. Вертикальный срез одного направления делить не нужно — он
остаётся одним коммитом.

### Файл запрещено менять

Покажите активную политику:

```bash
trip policy
```

Не обходите защиту автоматически. Либо переключитесь на согласованную политику,
либо обсудите изменение правил с владельцем методологии.

### Push требует changelog

Добавьте проверенный результат в `## Невыпущено`, затем создайте новый коммит.
Незакоммиченное изменение changelog не маскирует отсутствие записи в ветке.

### Средство не видно в `trip tools list`

Посмотрите, какой манифест отклонён и почему:

```bash
trip tools list
trip tools doctor
```

Частые причины — дубль имени с другим средством и объявленная несовместимость
версий. И то и другое отклоняет манифест целиком, а не одну операцию.

### Отчёт инспекции устарел

Git `HEAD` изменился после инспекции. Получите новый отчёт для текущего коммита
и импортируйте его:

```bash
trip work import artifacts/new-inspection.json
```

### Неизвестная версия или конфликт документа

Не редактируйте документ вручную и не меняйте его идентификатор. Попросите
владельца документа сформировать поддерживаемую версию или новую ревизию.

### Порт панели занят

Без явного порта TRIP ищет следующий свободный автоматически:

```bash
trip serve --localhost
```

Либо задайте другой:

```bash
trip serve --localhost --port 7878
```

### Панель сообщает, что SPA не встроен

Панель отдаётся из встроенного в бинарник артефакта. Если её нет, у вас
неполная сборка: возьмите файл выпуска заново либо, при работе из исходников,
пересоберите:

```bash
npm run build
npm run setup
```

### Hooks используют старую команду

Приведите проверки к версии инструмента:

```bash
trip update
```

Пользовательские `trip.json` и правленные вами файлы в `trip/` при этом не
перезаписываются.

## 13. Обновление и удаление

### Обновление

Если средство поставляется выпуском, обновление — это новая закреплённая версия
в проекте и повторная установка по ней. Молчаливое обновление инструмента ломает
воспроизводимость проверок, поэтому смена версии проходит запросом на слияние,
как всякое изменение.

При работе из исходников:

```bash
git pull --ff-only
npm run setup
```

Затем в каждом подключённом проекте приведите проверки к новой версии:

```bash
trip update
```

Команда переписывает валидаторы `trip/*.js`, отставшие от версии инструмента,
переустанавливает управляемые hooks и записывает происхождение в
`trip/toolchain.json`. Раньше эту роль пытался играть `trip init`, но он
артефакты только создаёт: однажды разложенный валидатор не обновлялся никогда,
и репозитории расходились молча — устаревшая проверка не падает, она просто не
выполняет того, чего ещё не знает.

Файлы `trip/` и `trip.json` заблокированы политикой `generic`, поэтому
результат обновления коммитится в режиме методологии:

```bash
trip policy policies-only
git add trip/
git commit -F .git/СООБЩЕНИЕ   # chore(service/repository): обнови проверки до версии trip
trip policy generic
```

Посмотреть, что разошлось, ничего не меняя:

```bash
trip update --check
```

Проверка отвечает кодом возврата и потому годится для конвейера. Валидатор,
который проект правил сам, она называет, но не трогает: перезаписать его можно
только явным `trip update --force`.

### Снять hooks с проекта

```bash
trip uninstall
```

Команда удаляет только секции hooks, которыми управляет TRIP. Чужое содержимое
hooks сохраняется.

Удалить также локальное состояние `.trip/`:

```bash
trip uninstall --purge
```

`--purge` уносит `.trip/` целиком, вместе с распакованными в `.trip/tools/`
средствами; они восстанавливаются повторной установкой по закреплённым версиям.
`trip.json` и каталог `trip/` остаются в репозитории.

### Удалить глобальную команду

Если TRIP-CLI ставился из исходников:

```bash
npm run unsetup
```

Если он лежит распакованным выпуском — достаточно удалить его каталог.

## 14. Краткий справочник команд

| Команда | Назначение |
|---|---|
| `trip --version` | Показать версию |
| `trip --help` | Показать общую справку |
| `trip init [путь]` | Подключить TRIP к репозиторию |
| `trip init --policy <имя>` | Подключить TRIP и выбрать политику |
| `trip update` | Привести валидаторы и hooks к версии trip |
| `trip update --check` | Показать расхождение версий, ничего не меняя |
| `trip update --force` | Перезаписать в том числе правленные проектом валидаторы |
| `trip policy` | Показать активную политику |
| `trip policy <имя>` | Переключить политику |
| `trip tools list` | Показать доступные средства единого входа |
| `trip tools describe <имя>` | Показать операции и совместимость средства |
| `trip tools doctor` | Проверить, разрешается ли команда запуска |
| `trip serve --localhost` | Открыть локальную веб-панель |
| `trip serve --port <n>` | Запустить панель на точном порту |
| `trip trace <аргументы>` | Передать команду самостоятельному `trip-trace` |
| `trip verify --staged` | Проверить подготовленные к коммиту файлы и состав среза |
| `trip verify --branch` | Проверить имя ветки |
| `trip verify --changelog` | Проверить структуру changelog |
| `trip verify --message <файл>` | Проверить сообщение коммита |
| `trip verify --fixups --base <ref>` | Проверить, что заплатки автосжатия вклеены |
| `trip verify --commits --base <ref>` | Перепроверить состав каждого коммита ветки |
| `trip verify --require-policy` | Считать отсутствие политики отказом (CI) |
| `trip verify --doc-lint` | Проверить документацию внешним trip-doc-lint |
| `trip verify --work-package --base main` | Проверить рабочий пакет |
| `trip work start ...` | Начать упрощённый рабочий пакет |
| `trip work import <файл>` | Импортировать неизменяемый JSON-документ |
| `trip work show` | Показать активный пакет |
| `trip work list` | Показать импортированные документы |
| `trip work contracts` | Проверить встроенные схемы формата v2 |
| `trip work use <ID> --fingerprint <SHA>` | Выбрать точную ревизию пакета |
| `trip work freeze` | Выполнить финальную проверку пакета |
| `trip work freeze --json` | Выдать результат проверки для CI |
| `trip uninstall` | Снять управляемые hooks |
| `trip uninstall --purge` | Снять hooks и удалить локальное состояние вместе с `.trip/tools/` |

Нормативные правила Git-ведения находятся в
`Git-ведении trip-cli` (`git-workflow.md` — в исходном репозитории средства), а структура `trip.json` — в
[модели политик](./МОДЕЛЬ_ПОЛИТИК.md).
