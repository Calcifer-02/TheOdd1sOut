# Коннектор TRIP и SHIVA: инструкция пользователя

Документ для команды проекта. Описывает, что нужно для запуска, какие команды
есть и как читать то, что коннектор пишет в ответ.

Общая идея одной строкой: **реестры проекта в Git — источник истины, трекер —
их отражение.** Правки вносятся в реестр, а коннектор доводит их до трекера.
Обратный порядок ломает трассируемость.

## 1. Что нужно, чтобы он заработал

| Что | Зачем | Проверка |
|---|---|---|
| Python 3.9 и новее | сам коннектор; внешних зависимостей нет | `python --version` |
| `git` в `PATH` | атрибуция исполнителя и сводки изменений | `git --version` |
| Служебный токен SHIVA | доступ к трекеру | `echo %SHIVA_TOKEN%` |
| Файл настройки проекта | привязка репозитория к проекту трекера | `проекты/<имя>.json` |

Токен задаётся переменной окружения и **в репозитории не хранится**:

```bash
export SHIVA_TOKEN=...          # Linux, macOS, Git Bash
set SHIVA_TOKEN=...             # Windows cmd
$env:SHIVA_TOKEN = "..."        # PowerShell
```

Токен должен быть **отдельным служебным**, а не личным: все автоматические
действия подписываются им, и по нему же видно, что сделала машина, а что человек.

## 2. Куда его ставить

Сервер коннектору не нужен: у SHIVA нет исходящих вызовов, поэтому коннектор
никогда не принимает входящих запросов. Он запускается по событию и завершается.

**Для одного человека — локально.** Скопировать `хуки/post-commit` в
`.git/hooks/` рабочего репозитория и сделать исполняемым. Хук работает
только на рабочей ветке и ведёт два контура: привязку коммитов — на каждом
коммите, проекцию реестров — только при изменении одного из трёх наблюдаемых
реестров; обычный коммит кода задачи в трекере не двигает.

**Для команды — задание сборочного конвейера.** Ставить хук каждому участнику
не нужно и вредно: тогда токен окажется у всех, а поведение будет зависеть от
того, у кого какой Python. Правильнее одно задание в `.gitlab-ci.yml` на ветке
интеграции, с токеном в защищённой переменной проекта:

```yaml
синхронизация-трекера:
  stage: .pre
  rules:
    - if: $CI_COMMIT_BRANCH == "dev/1.0-stage"
      changes:
        - docs/analysis/РЕЕСТР_ТРЕБОВАНИЙ.md
        - docs/analysis/РЕЕСТР_БАГ_ОТЧЕТОВ.md
        - docs/analysis/ЖУРНАЛ_КОНТРОЛЬНЫХ_ТОЧЕК.md
  script:
    - python -m trip_shiva.cli --конфиг проекты/<имя>.json план --применить
```

Отказ синхронизации не должен ронять сборку: реестр в Git остаётся источником
истины, а расхождение устраняется следующим прогоном.

## 3. Настройка проекта

`проекты/<имя>.json`:

```json
{
  "имя": "Мой проект",
  "корень": "C:/Проекты/<проект>",
  "проект": 123,
  "схема": 456,
  "реестр_требований": "docs/analysis/РЕЕСТР_ТРЕБОВАНИЙ.md",
  "реестр_дефектов": "docs/analysis/РЕЕСТР_БАГ_ОТЧЕТОВ.md",
  "журнал_точек": "docs/analysis/ЖУРНАЛ_КОНТРОЛЬНЫХ_ТОЧЕК.md",
  "привязки": "привязки-<имя>.json",
  "авторы": {"почта@пример": 789},
  "не_исполнители": ["gitlab.sync.bot@imbalanced.tech"]
}
```

`авторы` — соответствие почты автора коммита и профиля в трекере. Без него
исполнитель не назначается: коннектор не угадывает, кому принадлежит работа.
`не_исполнители` — служебные учётные записи, которые не должны становиться
исполнителями.

Таблица привязок `привязки-<имя>.json` лежит рядом с настройкой и создаётся
сама. Её нельзя терять: в ней хранится соответствие кода артефакта и задачи.
Если она потеряна, повторное заведение остановит сам трекер — у полей `R-id` и
`BUG-id` включена проверка на дубликаты.

## 4. Команды

Все команды по умолчанию **ничего не пишут** в трекер.

### `стадия` — на какой стадии проект

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json стадия
```

Показывает стадию и решения по контрольным точкам. Стадия не хранится
отдельным полем: это стадия ближайшей точки, по которой ещё нет вердикта
`пройдено`.

### `план` — что коннектор собирается сделать

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json план
python -m trip_shiva.cli --конфиг проекты/<имя>.json план --применить
python -m trip_shiva.cli --конфиг проекты/<имя>.json план --только R-031 --применить
```

Без `--применить` — предпросмотр. `--только` ограничивает охват перечисленными
кодами; удобно, чтобы проверить поведение на одной задаче.

### `сверка` — не разошлось ли

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json сверка
```

Показывает расхождения между трекером и источниками истины. Запускать после
любой ручной работы в трекере.

### `релизы` — соответствие релизов контрольным точкам

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json релизы
python -m trip_shiva.cli --конфиг проекты/<имя>.json релизы --выпустить
```

Показывает все стадийные срезы: закрытые вердиктом, текущий и будущие.

```text
Точка    Релиз                    Вердикт            Состояние      Задач в срезе
Gate 4   Демонстрация (Gate 4)    пройдено           Выпущен        0
Gate 5   МЖП (Gate 5)             текущий срез       Запланирован   60
Gate 6   МБП (Gate 6)             не выносился       Запланирован   0
```

Выпуск релиза необратим, поэтому требует явного ключа. Обратное расхождение —
релиз выпущен, а вердикта в журнале нет — команда показывает, но не исправляет:
снять выпуск нельзя, а записать принятое решение в журнал можно.

### Срез — это зрелость, а не положение проекта в портфеле

Релиз в трекере закрывается **вердиктом контрольной точки**. Поэтому задача
лежит в срезе той стадии, до которой продукт дозрел, и переставляется в
следующий срез, когда вердикт вынесен.

Положение проекта в портфеле — упакован, заморожен, передан в поддержку — на
срез не влияет: по §29 упаковать можно то, что уже есть, с любой стадии
зрелости, и вердиктом контрольной точки это не является. Положение читается по
карточке проекта в портфеле; коннектор его показывает и в задачи не переносит.

Переставляются только **незакрытые** задачи. Закрытая задача была закрыта в
своём срезе, и это факт о прошлом: перенести её — значит задним числом
переписать, к какой контрольной точке относилась работа.

### `портфель` — карточка проекта и вердикты

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json портфель
python -m trip_shiva.cli --конфиг проекты/<имя>.json портфель --записать
```

Читает положение карточки проекта на портфельной доске, выводит вердикты
контрольных точек из её истории и дописывает недостающие решения в журнал.
Заодно проставляет на карточке состав команды из устава.

### `коммиты` — связь коммитов с задачами

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json коммиты
python -m trip_shiva.cli --конфиг проекты/<имя>.json коммиты --диапазон origin/main..HEAD --применить
```

Распознаёт **все** идентификаторы канона (`R`, `DR`, `US`, `UC`, `Q`, `AR`,
`ADR`, `AC`, `TC`, `BUG`, `ФЗ`) и разрешает их в задачи: `R` и `BUG` — прямо,
`AC`, `TC`, `US`, `UC` — через матрицу трассируемости. `ADR`, `Q`, `AR`, `DR` и
`ФЗ` остаются контекстом: собственной задачи у них нет и быть не должно.
Ключ задачи трекера в сообщении коммита писать не нужно.

### `приёмка` — подтверждение заказчиком

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json приёмка
python -m trip_shiva.cli --конфиг проекты/<имя>.json приёмка --создать
```

Создаёт для задач в статусе «Приёмка» внешнюю ссылку, по которой заказчик без
учётной записи в трекере подтверждает или отклоняет результат. Разрешены только
два перехода: «Принято» и «Не принято».

### `возвраты` — метрика возвратов на доработку

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json возвраты
python -m trip_shiva.cli --конфиг проекты/<имя>.json возвраты --записать
```

Показывает возвраты по участникам и по основанию. `--записать` проставляет
счётчик в карточки.

### `метрики` — срез аналитического контура

```bash
python -m trip_shiva.cli --конфиг проекты/<имя>.json метрики
python -m trip_shiva.cli --конфиг проекты/<имя>.json метрики --сохранить срез.json
```

Считает: возвраты на доработку (RR, норматив ≤ 15%, выше 25% — брак),
суммарное время задач в статусах, время цикла Гейта (GCT — от решения по
предыдущей точке) и долю закрытого критического ядра Гейта (CDR_K1).
`--сохранить` отдаёт срез в JSON с источником `trip-shiva` — его подхватывает
TRIP Anchor. Команда тяжёлая: на каждую привязанную задачу читается история
и карточка, поэтому она только ручная, не для хука и конвейера.
Спринтовый индекс SCI не считается намеренно: спринтов в модели TRIP нет,
есть контрольные точки.

## 5. Что коннектор заполняет сам

| Поле карточки | Откуда берётся |
|---|---|
| Наименование и описание | формулировка требования, критерии приёмки |
| Тип | уровень требования: `L1` — эпик, `L2` — задача; дефект — инцидент |
| Приоритет | класс важности: `К1` → Наивысший, `К2` → Средний, `К3` → Низкий |
| Исполнитель | автор коммитов, затронувших код требования |
| Метки | направления §B5.2 из префиксов коммитов; «Отложено» по статусу |
| Релиз | срез текущей стадии зрелости из журнала контрольных точек |
| `R-id` / `BUG-id` | код артефакта — ключ привязки |
| Уровень, Класс важности, Стадия | реестр и журнал |
| Ссылка на трассу | адрес реестра в репозитории |
| Статус | выводится из статуса в реестре, проводится по маршруту |
| Возвратов на доработку | команда `возвраты --записать` |

**Автор задачи** остаётся служебной учётной записью коннектора. Это сделано
намеренно: автором значится тот, кто завёл карточку, и это действительно
машина. Ответственность за содержание несёт реестр, а не поле «Автор».

**Эпик и спринт коннектор не заполняет.** Принадлежность задачи способности
продукта — смысловая связь, и её подтверждает человек.

## 6. Как читать ответы

| Слово в выводе | Что произошло | Что делать |
|---|---|---|
| `создано` | задача заведена | ничего |
| `обновлено` | карточка приведена к реестру | ничего |
| `проведено` | задача прошла по маршруту | ничего |
| `перенесено` | задача переставлена в срез текущей стадии | ничего |
| `исполнитель` | назначен по коммитам | ничего |
| `остановлено` | переход отклонён проверкой трекера | прочитать основание, дополнить данные |
| `расхождение` | реестр и трекер разошлись | решить в источнике истины |
| `отказ` | операция не выполнена | прочитать основание |
| `ошибка` | сбой обращения к трекеру | повторить прогон |

Пример остановки:

```text
остановлено R-031  переход «Сделано» отклонён: Поле "Исполнитель" должно быть
                   заполнено. — нужен человек
```

Это не сбой. Коннектор дошёл по маршруту до места, где правило проекта требует
данных, которых нет, и остановился. **Обходных маршрутов у него нет намеренно:**
объезд по другому переходу обошёл бы то самое правило, ради которого проверка
поставлена.

## 7. Если кто-то поправил в трекере руками

Так бывает и это нормально. Правило простое:

> **Коннектор не откатывает ручные действия.** Он показывает расхождение,
> а устраняется оно в источнике истины — в реестре или журнале, а не встречной
> правкой карточки.

| Что сделал человек | Как читать | Что делать |
|---|---|---|
| Двинул задачу вперёд | решение принято, но не записано | обновить статус требования в реестре |
| Выпустил релиз | точка пройдена, вердикта в журнале нет | записать решение в журнал |
| Завёл задачу вручную с кодом | появился второй носитель кода | принять её в привязки либо удалить дубль |
| Стёр или изменил `R-id` | потерян адрес задачи в реестре | вернуть код: связь автоматически не восстановима |
| Отменил задачу | требование живо, задачи нет | снять требование в реестре либо вернуть задачу |

Запускать `сверка` после ручной работы — самый дешёвый способ не накопить
расхождений.

## 8. Чего коннектор не делает

- не удаляет задачи — даже если требование исчезло из реестра;
- не выпускает релиз без явной команды;
- не выставляет вердикт контрольной точки;
- не присваивает дефекту состояние выше `кандидат`;
- не связывает задачу со способностью продукта по догадке;
- не переписывает поля, которые человек изменил в трекере.

Всё перечисленное — решения человека в роли `A`.

## 9. Если что-то не работает

| Признак | Причина | Решение |
|---|---|---|
| `Трекер отказал: не задан токен` | пустая `SHIVA_TOKEN` | задать переменную окружения |
| `403 FORBIDDEN` | токен без префикса `Bearer` или отозван | выпустить новый служебный токен |
| `Найден дубликат задачи по кастомному полю` | задача под этим кодом уже есть | восстановить или дополнить таблицу привязок |
| Прогон идёт несколько минут | большая история репозитория | нормально: история читается один раз, около 30 секунд на 60 кодов |
| `нет разрешённого маршрута` | статус задачи вне объявленного маршрута типа | вернуть задачу на маршрут вручную |
| План пуст, хотя реестр менялся | изменение не затронуло проецируемые поля | так и задумано: отпечаток не изменился |

## 10. Проверки

```bash
python -m unittest discover -s tests
```

Проверки не используют сеть. Падение проверки означает, что сломано
поведение, а не покрытие: каждая привязана к конкретному решению — разбор
реестров, вывод стадии, маршруты по типу, разбор основания возврата,
устойчивость таблицы привязок, отделение документации от кода при атрибуции,
перенос незакрытых задач в срез текущей стадии.
