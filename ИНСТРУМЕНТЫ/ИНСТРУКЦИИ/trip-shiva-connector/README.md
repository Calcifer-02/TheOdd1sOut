# Коннектор TRIP и корпоративного трекера SHIVA

Отражает реестры проекта TRIP в задачах корпоративного трекера, чтобы отчётность
велась без роли менеджера. В TRIP решения о заведении, возврате и приёмке работы
уже принимаются — в реестре требований, в проверках и на контрольной точке.
Менеджер в обычном процессе нужен, чтобы записать эти решения второй раз, руками.
Коннектор убирает вторую запись, а не решение.

**Трекер — проекция, а не источник истины.** Свойства требования остаются в
реестре; в трекере они отражаются. Обратный порядок сделал бы трекер вторым,
расходящимся источником.

## Что читает и во что превращает

| Источник в репозитории проекта | Сущность трекера |
|---|---|
| Требование уровня `L1` (способность продукта) | Эпик |
| Требование уровня `L2` (сценарий или история) | Задача |
| Требование уровня `L3` (критерий приёмки) | пункт описания задачи, отдельной сущности нет |
| `BUG-id` из реестра дефектов | Инцидент |
| Стадия из журнала контрольных точек | Релиз |

Подзадачи не заводятся: внутренняя декомпозиция работы живёт в ветке, коммитах
и бэклоге, а не в отчётности.

## Три наблюдаемых файла

```text
docs/analysis/РЕЕСТР_ТРЕБОВАНИЙ.md        эпики и задачи
docs/analysis/РЕЕСТР_БАГ_ОТЧЕТОВ.md       инциденты
docs/analysis/ЖУРНАЛ_КОНТРОЛЬНЫХ_ТОЧЕК.md стадия и релиз
```

Стадия не объявляется, а выводится: это стадия ближайшей контрольной точки, по
которой ещё нет вердикта `пройдено`. Отдельного поля «текущая стадия» нет
намеренно — объявленное поле расходится с действительностью, как это и было
в пилотном проекте: стадия была записана в трёх артефактах и во всех устарела.

Разбор реестров строгий и прибит к канону методологии (АА-05, АА-15, АА-16):
записи читаются только из объявленных разделов (`## Реестр`, `## Сводный
реестр` / `## Реестр баг-отчётов`, `## Решения`) и только по точным именам
колонок; признанные варианты имён объявлены в `registry.py` явно. Реестр не
по канону не угадывается — команда `сверка` показывает нераспознанное как
расхождение уровня «важно».

## Как коннектор двигает задачи

Статус не назначается, а выводится из статуса в реестре. Коннектор не пишет
статус напрямую: он выполняет **объявленный для типа маршрут**, поэтому проверки
на переходах продолжают действовать.

```text
Требование  Новая → Анализ → Бэклог → Разработка → Тестирование → Приёмка → Завершено
Дефект      Новая → Разработка → Тестирование → Завершено          (экспресс-маршрут §B23.5)
```

Обходных маршрутов нет намеренно. Если проверка на переходе отказала — данных не
хватает, и это решает человек. Объезд по другому ребру графа обошёл бы то самое
правило, ради которого проверка поставлена.

## Атрибуция

Исполнитель выводится из коммитов, упоминающих код требования, и сопоставляется
с профилем трекера по таблице в конфигурации. Свидетельства нет — исполнитель не
назначается, а задача попадает в расхождения. Возвраты на доработку считаются по
участникам, поэтому ошибочная атрибуция это ошибка в метрике человека, а не
косметическая неточность.

Документальные коммиты (правки реестров, аналитика) исполнителем не делают:
правка документа кодом требования не является реализацией. Но они
первоклассные для трассируемости: идентификаторы из сообщения привязываются
к задаче, направление из заголовка по канону trip-cli (`тип(направление)`) —
в метку задачи. Маркеры в документах не нужны: связь идёт через сообщение
коммита, как и для кода.

## Идемпотентность

Ключ источника — `R-id` или `BUG-id`; отпечаток — хеш проецируемых полей.
Повторный проход не создаёт дубль и не переписывает то, что человек изменил
в трекере: он показывает расхождение. Дополнительно страхует сам трекер —
у полей `R-id` и `BUG-id` включена проверка на дубликаты.

**Коннектор никогда не удаляет задачу.** Исчезновение требования из реестра
основанием для удаления не является: снятие требования — решение человека.

## Предохранитель записи

Токен SHIVA действует шире одного проекта, поэтому запись ограничена в два
рубежа. Первый — клиент: пишущий вызов принимается, только если задача или
релиз подтверждены трекером как принадлежащие проекту из конфига (и
портфельному проекту, если он подключён); создание задачи вне объявленного
проекта отклоняется до отправки запроса. Второй — операторский: переменная
`SHIVA_РАЗРЕШЁННЫЕ_ПРОЕКТЫ` задаёт перечень допустимых проектов на машине,
и конфиг вне перечня останавливает запуск. Полное ограничение даёт только
сама SHIVA — правами служебной учётной записи на проект; клиентский
предохранитель закрывает ошибку в конфиге, а не подмену токена.

## Команды

```bash
export SHIVA_TOKEN=...   # служебный токен, в репозитории не хранится

# Необязательный предохранитель оператора: перечень проектов, в которые
# этой машине разрешено писать. Конфиг, объявляющий другой проект,
# останавливается на старте.
export SHIVA_РАЗРЕШЁННЫЕ_ПРОЕКТЫ="123"

python -m trip_shiva.cli --конфиг проекты/<имя>.json стадия
python -m trip_shiva.cli --конфиг проекты/<имя>.json план
python -m trip_shiva.cli --конфиг проекты/<имя>.json план --применить
python -m trip_shiva.cli --конфиг проекты/<имя>.json план --только R-031 --применить
python -m trip_shiva.cli --конфиг проекты/<имя>.json возвраты
python -m trip_shiva.cli --конфиг проекты/<имя>.json возвраты --записать
python -m trip_shiva.cli --конфиг проекты/<имя>.json метрики
```

По умолчанию — предпросмотр. Запись включается ключом `--применить`: менеджера
нет, но и молчаливой записи в корпоративный трекер тоже нет.

## Метрики контура

Команда `метрики` считает срез аналитического контура: возвраты на доработку
(RR, норматив ≤ 15%), суммарное время задач в статусах, время цикла Гейта
(GCT) и долю закрытого критического ядра (CDR_K1). Срез читается из истории
карточек и журнала контрольных точек, ручного вклада не требует.
`метрики --сохранить срез.json` отдаёт тот же срез в JSON с источником
`trip-shiva` — его подхватывает TRIP Anchor для отчёта руководству.
Команда тяжёлая (чтение истории каждой привязанной задачи), поэтому в хук
и конвейер не входит: только ручной запуск.

## Запуск по событию

`хуки/post-commit` копируется в `.git/hooks/` проекта. Хук работает только на
рабочей ветке и ведёт два контура с разными условиями:

- **привязка коммитов** — на каждом коммите: идентификаторы трассируемости из
  сообщения разрешаются в задачи трекера, связь пишется на карточку;
- **проекция реестров** — только когда изменился один из трёх наблюдаемых
  реестров: обычный коммит кода задачи не двигает, иначе хук превращается в
  шум и его отключают целиком.

Отказ любого контура не отменяет коммит — реестр в Git остаётся источником
истины, а расхождение устраняется следующим прогоном.

## Настройка проекта

`проекты/<имя>.json`:

```json
{
  "имя": "Мой проект",
  "корень": "C:/Проекты/<проект>",
  "проект": 123,
  "схема": 456,
  "реестр_требований": "docs/analysis/РЕЕСТР_ТРЕБОВАНИЙ.md",
  "реестр_дефектов": "docs/analysis/РЕЕСТР_БАГ_ОТЧЕТОВ.md",
  "журнал_точек": "docs/analysis/ЖУРНАЛ_КОНТРОЛЬНЫХ_ТОЧЕК.md",
  "привязки": "привязки-<имя>.json",
  "авторы": {"почта@пример": 789},
  "не_исполнители": ["gitlab.sync.bot@imbalanced.tech"]
}
```

Таблица привязок лежит рядом с конфигурацией и хранится отдельно от домена
(`ADR-0005`).

## Граница

Коннектор не выпускает релиз, не отменяет и не удаляет задачи, не выставляет
вердикт контрольной точки и не присваивает дефекту состояние выше `кандидат`.
Это необратимые или смысловые решения, и их принимает ответственный человек
в роли `A`.

## Состояние

Первый рабочий срез. Проверено на пилотном проекте: заведение, проведение
по маршруту, атрибуция по коммитам, идемпотентность повторного прогона,
отказ проверки с остановкой. Проверки — `python -m unittest discover tests`,
гоняются конвейером (`.gitlab-ci.yml`) на каждый пуш.
