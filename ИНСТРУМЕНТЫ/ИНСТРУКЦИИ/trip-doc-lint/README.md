# Линтер документации TRIP — рабочая папка

Здесь разбирается один вопрос: **что машина может проверить в проектных
документах и где она обязана замолчать.**

Повод конкретный. ИИ-агент взял шаблон архитектурного решения из TRIP и
заполнил его механически: в поле «Связанные сущности» попало тридцать девять
записанных знаков, за которыми диапазонами скрыто **102 связи**, разделы
шаблона слились в три абзаца, а автором решения агент записал себя. Документ
выглядит заполненным и при этом не выполняет своей работы — по такой записи
нельзя понять, из чего решение выросло и кто за него отвечает. Проверить это
глазами на каждом документе каждой ветки невозможно, значит нужна проверка.

## Что лежит в папке

| Путь | Что это |
|---|---|
| `01_ИССЛЕДОВАНИЕ_СУЩЕСТВУЮЩИХ_ЛИНТЕРОВ.md` | Прямые соседи: линтеры документации и средства требований. Что решено чужими руками, что не решено никем. |
| `02_АНАЛОГИ_В_ДРУГИХ_ЭКОСИСТЕМАХ.md` | Та же задача под другими именами: управление требованиями, политика как код, барьеры качества, базы знаний. Язык аналога значения не имеет. |
| `03_ЗАМЫСЕЛ_ЛИНТЕРА_TRIP.md` | Каким будет наш линтер: место в экосистеме, уровни строгости, профиль и барьер, каталог правил. |
| `04_ПЕРВЫЕ_НАБЛЮДЕНИЯ_ПОДОПЫТНОГО_1.md` | Что видно в подопытном с первого прочтения — материал для разбора, не приговор. |
| `05_РЕАЛИЗАЦИЯ_НА_RUST.md` | Соседи по языку и выбор крейтов. |
| `06_ЗАДАНИЕ_РЕАЛИЗАТОРУ.md` | Что именно построить: типы, контракт отчёта, вехи, ловушки среды. |
| `07_РАСШИРЕНИЕ_КОРПУСА_ПОДОПЫТНЫХ.md` | Как отбирались подопытные 2–4, что доказывает каждый и что корпус изменил в замысле. |
| `ПОДОПЫТНЫЙ_1_TRIP_MIND/` | Снимок документации проекта trip-mind. Живой пример с настоящими болезнями. |
| `ПОДОПЫТНЫЙ_2_ДОСКА_ОБЪЯВЛЕНИЙ/` | Заполнено машиной по действующим шаблонам. Поля владельцев остались заглушками, пакет заполнен наполовину. |
| `ПОДОПЫТНЫЙ_3_СИСТЕМНЫЙ_СПЕЦИАЛИСТ/` | Корпус, который люди вели месяцами по шаблонам версии `1.0`. Дрейф, архив, свои идентификаторы. |
| `ПОДОПЫТНЫЙ_4_FILE_LEVEL_TOOLING/` | Артефакты рассыпаны по репозиторию, пакет шаблонов не вложен, решения написаны в собственном виде. |
| `СЛОВАРЬ_ФРАЗ.toml` | Образец профиля с запрещёнными формулировками. Каждая запись самопроверяема примерами «плохо» и «хорошо»; засеян тем, что выловлено на подопытных вручную. |
| `ПРОБА_ТАБЛИЦ.py` | Черновая проверка согласованности таблиц на Python: не часть поставки, а оракул для сверки с будущей реализацией на Rust. Имя не несёт номера правила намеренно — номера переезжают, как и номера шаблонов в `DOC-F07`. |
| `ПОЛИГОН/` | Рабочие копии всех подопытных. Линтер работает только здесь; разница с исходным снимком и есть отчёт о его работе. |
| `ЭТАЛОН_TRIP/` | Снимок пакета артефактов аналитики TRIP — то, с чем сравнивается подопытный. |

Средство пишется на **Rust** одним бинарником без внешних зависимостей: оно
работает в хуках и в конвейере, где требование «поставьте Node» убило бы
применение в половине проектов экосистемы.

## Как здесь работают

Подопытный — снимок, а не рабочая копия. Его не правят: он ценен именно тем,
что содержит ошибки в том виде, в каком их допускают. Когда линтер научится
находить очередную болезнь, доказательством служит находка на этом снимке.

Работает линтер не на снимке, а на его копии в `ПОЛИГОН/`. Разница между
снимком и копией после прогона и есть отчёт о том, что средство сделало: её
можно прочитать построчно и оспорить. Копию правят только машиной; перед чистым
прогоном её сбрасывают к снимку целиком.

Правило подопытных: один снимок — один проект. Очередной подопытный берётся из
другого проекта, чтобы правила не подгонялись под особенности одного корпуса.
Сейчас подопытных четыре, и они выбраны так, чтобы различаться по трём осям
сразу: кто писал документы, с каким пакетом шаблонов их сравнивать и где эти
документы лежат в репозитории. Отбор и находки — в
`07_РАСШИРЕНИЕ_КОРПУСА_ПОДОПЫТНЫХ.md`.

У подопытного, который вложил методологию в своё дерево, снимок хранит её рядом
— в `эталон_проекта/`. Это не дубль `ЭТАЛОН_TRIP`, а тот эталон, относительно
которого документы этого проекта только и имеет смысл проверять: подопытный 3
работает по шаблонам версии `1.0`, и по действующим его судить нельзя.

## Чего эта работа не делает

Линтер документов не считает покрытие требований и не проверяет, существует ли
в коде маркер `@req`. Это принадлежит TRIP Trace Service, и переносить расчёт
сюда нельзя: в экосистеме у каждого показателя один владелец. Здесь проверяется
сам документ — его форма, состав и наполнение.
